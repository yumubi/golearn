# 21 搜索、Feed 与 IM 的设计套路

> 详细程度：标准 · 约 20 分钟
> 材料：W17-1 W17-2 W17-3 W19-1 W19-2 W20-1 W20-2 W16-2、C:dachang/radic · 旧长版：无
> 前置：13 缓存与消息队列、19 微服务拆分

## 这一节要建立的认知

三个业务看起来不相干，骨架其实相同：**都是"数据在写入时多做一点，读取时就少做一点"的取舍**，再叠加"谁来扩散、扩散到哪里"的问题。

1. 搜索：写入时建倒排索引，换查询时不扫全表。
2. Feed：写入时把动态复制到粉丝收件箱（写扩散），换读取时只查一处；或反过来读取时现拼（读扩散）。
3. IM：连接在哪个节点上不确定，要么先登记再定向转发，要么干脆全节点广播。

后面每个范式都能回到这三句话上。

## 一、搜索：倒排索引与 ES 的写入路径

正排是"文档到词"，倒排是"词到文档"。每个字段一张 posting list 表，**列表必须有序**，否则查一个词就是全表扫。〔W17-1 p7-8〕查多词时，对有序列表做交集，双游标，较小的游标后移，不需要回头：

```go
func intersect(a, b []int) []int {
	var out []int
	for i, j := 0, 0; i < len(a) && j < len(b); {
		switch {
		case a[i] == b[j]:
			out = append(out, a[i])
			i++
			j++
		case a[i] < b[j]:
			i++
		default:
			j++
		}
	}
	return out
}
// "go" -> [1 2 3]，"接口" -> [2 3]，求交得 [2 3]
```

课程里的开源索引框架 radic 就是这个结构：key 是"字段:词"，值是跳表，多链交集用同样的游标算法；结构化属性（是否已发布、类别）编码成位图，遍历倒排链时顺手按位过滤，免去回表。〔C:dachang/radic/internal/reverse_index/skiplist_reverse_index.go:71-116〕

ES 的两个概念要分清：`text` 字段分词，用于全文搜索；`keyword` 不分词，用于精确匹配和聚合，互相不能替代。〔W17-1 p17〕

**近实时的原因（面试热点）**：文档先写内存 buffer，每秒 refresh 一次到 Page Cache，此时已可搜；再刷磁盘并记 Commit Point。所以写入后约 1 秒才可见，不是立刻。〔W17-1 p11〕

节点分三种角色：能被选主的、负责请求路由的协调节点、存数据的数据节点；生产环境建议不兼职。〔W17-1 p10〕

## 二、搜索平台化：统一接入

业务一多，每接入一个业务都要大改搜索模块，是平台型服务的典型失败。资料给的解法是**统一接入标准**：〔W17-2 p7-8〕

- 通用接口：传一个通用结构（索引名、文档 ID、JSON 数据），灵活但没有编译期检查。
- 专属接口：每个业务一个接口，有检查但接入慢。两者可以并存，紧急需求走通用的。
- 同步语义是 Upsert（有则更新无则插入），ES 的文档 ID 直接用业务 ID，保证同一份数据幂等。〔W17-2 p10〕

数据进 ES 有两条路：业务**主动**发消息给搜索服务；或搜索服务**被动**监听业务方已有的消息。业务方强势时用被动，把它的消息转成自己统一的 Event。〔W17-2 p19-20〕隔离部署用来保大不保小：同步服务和查询服务分集群，核心页面的搜索栏再独占一个集群，其他业务降级也不拖垮它。〔W17-2 p21〕

Service 层的聚合套路：预处理查询词（空格切分，容手抖），用 errgroup 并发查用户和文章再合并；完整的大平台链路是预处理、解析表达式生成搜索计划、执行、按策略调整输出。〔W17-2 p14〕

标签服务把这些串起来：〔W17-3 p13〕〔W17-3 p20〕

- 标签是"某人给某资源打的"，天然和个人挂钩，所以不适合并进文章索引，也就没法用 Nested 解决关联。
- 跨索引 JOIN（Nested、Parent-Child）都不建议用，**两次查询更好**：先查标签得到资源 ID 列表，再用这些 ID 去文章索引查。〔W17-3 p25-26〕
- 标签缓存前提是"创建后稳定不变"；应用启动时分批预加载，异步执行，否则启动要卡很久。〔W17-3 p11〕〔W17-3 p13〕
- 冗余字段的唯一目的是加速查询，风险是源字段可变时不一致，冗余不可变字段才安全。〔W17-3 p16〕

## 三、Feed：推、拉与它们的缺陷

两对术语等价，讨论前先对齐：读扩散等于拉模型等于发件箱；写扩散等于推模型等于收件箱。〔W19-1 p12〕

| | 拉（读扩散） | 推（写扩散） |
|---|---|---|
| 写入 | 一次，进作者发件箱 | 每个粉丝一次，进收件箱 |
| 读取 | 先查关注了谁，再查各发件箱，聚合排序分页 | 只查自己的收件箱 |
| 缺陷 | 每次读都放大成 N 个查询；分页难，每个库取前 20 条再内存排序 | 写放大，百万粉丝就是百万次瞬时写入 |

〔W19-1 p9-10〕〔W19-1 p15-17〕

实际用**推拉结合**：粉丝少的作者推，大 V 拉；进一步只对活跃用户推。读取时先查自己的收件箱，再补关注的大 V 的发件箱，合并排序。两个缺陷都还在，只是都变轻了；口诀是"读扩散查询慢，写扩散数据多"。〔W19-1 p18-19〕〔W19-1 p44〕

```go
func (f *Feed) Publish(e Event) {
	fs := f.followers[e.Author]
	if len(fs) > f.bigV { // 大 V：只写一份发件箱
		f.outbox[e.Author] = append(f.outbox[e.Author], e)
		return
	}
	for _, u := range fs { // 普通作者：推给每个粉丝
		f.inbox[u] = append(f.inbox[u], e)
	}
}
```

我跑了一个内存版：1000 粉丝的大 V 发一条走拉，只写 1 次；把阈值调到全推后，同一条要写 1000 次，累计 1002 次。

工程上的几个决定：

- **事件模型**：Type 加一个 map 形式的 Metadata，业务方自带个性化数据，存成 JSON 字段，不参与 WHERE 运算。新业务只需新增一个 Handler，是开闭原则。〔W19-1 p24〕〔W19-1 p30-33〕
- **一定异步**：Feed 只要求秒级实时，没强制同步的链路一律走消息队列，解耦、削峰、可用性都更好。〔W19-1 p35〕
- **关注关系**是上游：多对多中间表，唯一索引里 follower 列放前面，否则 `WHERE follower=?` 全表扫；关注数、粉丝数用 Redis 维护，两条命令放进 TxPipeline 一起执行。〔W16-2 p11〕〔W16-2 p16〕
- **压测**：用 k6 加 Prometheus 加 Grafana，脚本是 JS。看延迟分解：`req_blocked` 非零是压测机自己的问题，`req_waiting` 约等于总时长才正常。〔W19-2 p5〕〔W19-2 p12〕

## 四、IM：连接在谁手里

IM 的核心难题只有一个：A 和 B 连在不同节点上，怎么知道 B 在哪。两种答案：〔W20-1 p14-16〕

1. **注册**：连接后把用户登记到注册中心，发消息先查再定向转发。每个用户乘以多端登录，注册中心容易成为瓶颈。
2. **广播**：不知道就全节点广播，用 MQ 每个网关节点订阅同一个 topic。MQ 也可能成为瓶颈。

网关和后端分离：WebSocket 网关要稳定、轻量、易横扩（连接不能迁移），后端是普通微服务集群。〔W20-1 p17〕

用 WebSocket 而不是轮询，除了实时，还因为轮询会雪崩：服务端响应慢，前端就加轮询，压力更大。〔W20-1 p20-21〕连接通过 HTTP 升级建立，之后全双工；长连接有两层含义，TCP 层的 Keep-Alive 保活和应用层的心跳，不是一回事。〔W20-1 p22-23〕〔W20-1 p26-28〕

最简的单节点 Hub 就是一个并发 map：连上就存，收到消息遍历转发其他人。群聊分布式版：网关把消息转给后端，后端查群成员，**逐成员发 Kafka，Key 用成员 ID 保证单人有序**；每个网关节点是独立的消费者组（因为都要消费每条消息），命中本节点的连接就发，不在就忽略。〔W20-1 p34-35〕〔W20-1 p43-44〕

生产环境不自己写，用 OpenIM：服务端分 access、service、消息队列、msgtransfer 几层，业务系统只需要同步用户数据并嵌入前端 SDK。同步用户直接监听 Canal 读 binlog，用户服务零修改。〔W20-2 p5〕〔W20-2 p7〕〔W20-2 p16〕

## 常见坑

1. 倒排列表没排序：求交退化成嵌套循环。
2. 把搜索结果的"可见性"丢了：文章不可见（草稿、删除）仍被搜到，索引里要保留 status 并在查询里过滤。〔W17-2 p11〕
3. 大 V 全部写扩散，一次发文瞬时写入百万条。
4. 轮询当作实时手段，高并发时反向放大压力。
5. WebSocket 节点不加连接数监控：每节点连接数多了会显著拖慢性能。〔W20-2 p22〕
