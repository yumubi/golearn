## 先看一个长得像、行为相反的现象

下面两段代码做的事几乎一模一样：声明一个集合，赋给另一个变量，改新变量的第一个元素。唯一区别是类型，一个数组一个切片。先猜猜两行输出，再往下读。

```go
package main

import "fmt"

func main() {
	a := [3]int{1, 2, 3}
	b := a
	b[0] = 9
	fmt.Println("array:", a, b)

	s := []int{1, 2, 3}
	t := s
	t[0] = 9
	fmt.Println("slice:", s, t)
}
```

```text
array: [1 2 3] [9 2 3]
slice: [9 2 3] [9 2 3]
```

数组 `a` 原封不动，切片 `s` 却被"隔空"改了。`b := a` 和 `t := s` 写起来一模一样，行为完全相反，根源在于 Go 默认是**值语义**：赋值、传参、`range` 都拷贝。数组是"整块值"，拷贝它就是把每个元素复制一遍；切片却是一个小小的描述符，拷贝描述符并不拷贝它指向的那块数据。

所以读 Go 代码时要问：**这里拷贝了什么，共享了什么**？切片、map、channel、指针和函数值的副本可能仍指向共享数据；数组、结构体或接口里的值也可能包含这些引用。复制外层值不等于递归复制它指向的数据。

## 和你已知语言的差异

| 问题 | Java / Kotlin | Rust | TS | Go |
|---|---|---|---|---|
| 集合变量赋值的语义 | 引用（共享同一对象） | `[T; N]` 是值（T: Copy 时复制） | 引用（共享同一对象） | 数组是值，切片共享底层数组 |
| 默认可变性 | 对象可变，String 不可变 | 默认不可变 | 可变 | 字符串不可变，切片/map 可变 |
| 字符与字符串 | `char` 是 UTF-16 单元 | `char` 是 Unicode 标量 | `string` 是 UTF-16 | `rune` 是码点，`string` 是 UTF-8 |
| 隐式类型转换 | 有隐式拓宽 | 无隐式转换 | 宽松 | 无隐式转换（无类型常量除外） |
| 枚举 | `enum` | `enum` | `enum`/联合 | 没有 enum，用 `const` + `iota` |

表里最反直觉的是第一行和第三行：Go 同时有"值"的数组和"引用"的切片，两个长得像的集合语义相反；而 Go 的"字符"不是 `char`，字符串内部是 UTF-8 编码的字节序列，这决定了取长度和切片的很多坑。下面按值语义、切片、map、字符串、结构体的顺序逐个讲。

## 一、值语义与零值

先建立最底层的认知：Go 的类型分三类，基本数据类型（数值、字符串、布尔）、复合数据类型（数组、切片、map、结构体等）、接口类型。〔TB12 p1-2〕其中数值类型又分平台无关的和平台相关的，`int`、`uint`、`uintptr` 长度随平台变化，可移植的代码不要依赖它的长度。〔TB12 p4-5〕

类型之间要求"一模一样"，没有隐式转换，这是 01 节"显式"那条的延伸。更隐蔽的是整型溢出：结果超出边界就悄悄回绕，不报错也不 panic。`int8` 的 127 加 1 得 -128，`uint8` 的 1 减 2 得 255。〔TB12 p5〕所以选整型要看清取值范围，别随手用 `int8`、`uint8` 这类窄类型做计数或循环条件。

每个类型都有一个**零值**，也就是不初始化时自动得到的默认值：数值 0，布尔 false，字符串空串，指针、切片、map、channel、函数、接口为 nil，结构体是各字段零值的组合。Go 的设计主张"零值可用"：`var mu sync.Mutex` 就能直接 `Lock`，`var buf bytes.Buffer` 就能直接 `Write`，不用像 C 那样先调 `pthread_mutex_init`。〔TB17 p10-12〕

但零值可用有两个例外要记牢，它们是最常见的运行时 panic 来源。先看 nil map 和 nil 切片：

```go
package main

import "fmt"

func main() {
	var m map[string]int
	fmt.Println(m["x"], len(m)) // 读 nil map 没问题

	var ns []int
	ns = append(ns, 1) // nil 切片 append 没问题
	fmt.Println(ns)
}
```

```text
0 0
[1]
```

nil map 读和取长度都正常，nil 切片 append 也正常。但 nil map **不能写**：

```go
var m map[string]int
m["x"] = 1 // panic: assignment to entry in nil map
```

为什么读没事写就 panic？因为 map 的底层哈希表在 nil 时还没分配，读一个不存在的 key 可以直接返回零值，而写入必须往哈希表里插槽，没表可插，运行时只能 panic。map 必须先 `make` 或字面值初始化才能写。〔TB16 p4-6〕切片则不同，append 发现底层数组是 nil 时自己会去分配，所以零值切片可直接用。

## 二、数组是值，切片是窗口

数组要解决的是基本类型够不着的抽象：一组数量固定且连续的整型数、一个包含书名、页数、出版信息的书籍抽象、一张学号到学生姓名的映射表，这些问题基本数据类型都无法解决，所以需要一类新类型来建立这些抽象，丰富 Go 语言的表现力。〔TB15 p1〕这类新类型的共同特点是由多个元素的值组合而成：元素类型相同的叫同构，不同的叫异构，这类类型在 Go 中称为复合类型。〔TB15 p1-2〕Go 原生内置了多种复合数据类型：数组、切片（slice）、map、结构体，以及像 channel 这类用于并发程序设计的高级复合类型；map 和结构体分别在第三、五节展开，本节先讲最简单的复合类型数组，再进入与它关系密切的切片。〔TB15 p2〕

Go 的数组是一个长度固定的、由同构类型元素组成的连续序列，类型里带着两个重要属性：元素类型和数组长度（元素个数），声明形式是 `var arr [N]T`，元素类型可以是任意 Go 原生类型或自定义类型。〔TB15 p2〕长度 N 必须在声明数组变量时提供：编译器需要在编译阶段就知道数组类型的长度，所以 N 只能是整型数字面值或常量表达式；普通变量要到运行期才有值，满足不了这个要求，拿它当 N 编译不过。〔TB15 p2〕

两个数组类型等价的条件由定义直接给出：元素类型 T 与长度 N 都相同才等价，有一个属性不同就是两个不同的数组类型。拿函数参数当测试最直观：

```go fail
func foo(arr [5]int) {}
func main() {
	var arr1 [5]int
	var arr2 [6]int
	var arr3 [5]string
	foo(arr1) // ok
	foo(arr2) // 错误：[6]int 与函数 foo 参数的类型 [5]int 不是同一数组类型
	foo(arr3) // 错误：[5]string 与函数 foo 参数的类型 [5]int 不是同一数组类型
}
```

带 `fail` 标记的代码块是特意不让它通过编译的示例。arr1 原样通过；arr2 错在长度属性，arr3 错在元素类型属性，两者都不能作为调用 foo 时的实际参数。〔TB15 p2-3〕可见长度不是"长得像就行"的松匹配：它和元素类型一样是类型身份的一部分，[5]int 与 [6]int 之间，并不比 [5]int 与 [5]string 之间更近。

长度的编译期确定性还决定了内存布局。数组的连续不仅是逻辑上的：编译器为数组变量实际分配一整块可容纳其所有元素的连续内存，这块内存的全部空间都用来表示数组元素，所以数组内存大小等于各元素大小之和；分配内存大小不同的两个数组肯定是不同的数组类型，这是数组区别于其他类型、也是区分不同数组类型的根本依据。〔TB15 p3〕课程用 `len` 与 `unsafe.Sizeof` 验证：对 `var arr = [6]int{1, 2, 3, 4, 5, 6}`，`len(arr)` 为 6，`unsafe.Sizeof(arr)` 为 48；推导很简单：64 位平台上 int 大小为 8 字节，6 个元素就是 6×8=48。〔TB15 p3-4〕

通过数组变量和下标访问元素十分高效，不存在 Go 运行时带来的额外开销，下标从 0 开始。〔TB15 p5〕下标值超出数组长度范畴或为负数时，Go 编译器会给出错误提示，防止访问溢出：

```go fail
var arr = [6]int{11, 12, 13, 14, 15, 16}
fmt.Println(arr[0], arr[5]) // 11 16
fmt.Println(arr[-1])        // 错误：下标值不能为负数
fmt.Println(arr[8])         // 错误：下标值超出了 arr 的长度范围
```

两条注释是课程原文对这类编译错误的概括。注意编译期拦截的前提是下标为常量：长度和下标值都摆在明面上，编译器才能当场对质。把下标换成运行期才算出值的变量，编译期检查就无从下手，越界访问会在运行时 panic（runtime error: index out of range），改由运行期边界检查兜底（教学推导：原文示例只用了常量下标，未讨论变量下标的运行期行为，这半段按 Go 语言的一般语义补足）。〔TB15 p5〕

零值方面数组比 nil map 省心：不显式初始化时，各元素值就是其元素类型的零值，`var arr1 [6]int` 得到 `[0 0 0 0 0 0]`，声明即可直接用。〔TB15 p4〕显式初始化要在右值中显式放置数组类型，并用大括号给各元素赋值；右值长度可用 `...` 代替，编译器按元素个数自动计算；长度较大的稀疏数组逐一赋值太麻烦，用下标赋值只写非零项。一段代码看全：

```go
package main

import "fmt"

func main() {
	var arr1 [6]int // 不初始化：各元素取零值
	fmt.Println(arr1)

	arr2 := [6]int{11, 12, 13, 14, 15, 16} // 显式给出长度和全部元素
	arr3 := [...]int{21, 22, 23}           // ... 让编译器按元素个数定长度
	fmt.Printf("%T %v\n", arr2, arr2)
	fmt.Printf("%T %v\n", arr3, arr3)

	arr4 := [...]int{99: 39} // 下标赋值：稀疏数组
	fmt.Println(len(arr4), arr4[99], arr4[0])
}
```

预期输出（每个值都能从前面的规则推出来，建议实际跑一遍核对）：

```text
[0 0 0 0 0 0]
[6]int [11 12 13 14 15 16]
[3]int [21 22 23]
100 39 0
```

arr3 的 `%T` 打出 `[3]int`，长度是编译器数出来的；arr4 把第 100 个元素（下标 99）赋值为 39，得到 100 个元素的 `[100]int`，其余元素值均为 0。〔TB15 p4〕下标赋值适合"长度大、只有少数位置有值"的稀疏场景，省去把一长串零值逐一列出的麻烦。〔TB15 p4〕

最后回到本节开头的问题：数组变量的赋值为什么是整块拷贝？因为数组类型变量是一个整体，一个数组变量表示的是整个数组；这点与 C 完全不同，C 里数组变量可视为指向数组第一个元素的指针。〔TB15 p6〕所以 Go 中无论参与迭代（包括 range），还是作为实际参数传给函数或方法，传递数组的方式都是纯粹的值拷贝，会带来较大的内存拷贝开销；课程小结的说法是，值传递机制让数组在函数间传递比较"笨重"，且开销随数组长度的增加而增加。〔TB15 p6-7〕〔TB15 p14-15〕想避开这份开销，可以用指针的方式向函数传数组，但这更像是 C 语言的惯用法；Go 的答案是切片：更灵活、更地道，同时弥补数组"固定的元素个数"与"传值机制下开销较大"两点不足，成为 Go 最常用的同构复合类型。〔TB15 p6-7〕〔TB15 p14-15〕range 也不是例外：for range arr 每轮拿到的元素同样是拷贝，只是迭代本身不产生额外共享（教学推导：range 对数组同样整块拷贝，可由数组值语义直接推出）。切片怎么补上这两处短板，接着看。

切片是三元组：指向底层数组的指针、`len`、`cap`。〔TB15 p8-9〕拷贝切片只拷贝这个三元组，本机实测 `unsafe.Sizeof` 对 nil 切片、1000 个元素的切片、数组上切出的窗口都是 24 字节（三个机器字），与元素多少无关，所以传参开销恒定；代价是切片只是底层数组上的"窗口"：`arr := [10]int{1, ..., 10}` 切出 `sl := arr[3:7:9]`，执行 `sl[0] += 10` 后 `arr[3]` 变成 14，元素写在了共享的底层数组上。〔TB15 p8-10〕〔实测：work/run/TB15/E3/out.txt〕开头两段代码同一写法、结果相反，也是这一件事：数组 `b := a` 整块复制，`b[0] = 9` 改的是副本，`a` 打出来还是 `[1 2 3]`；切片 `t := s` 只拷贝描述符，`t[0] = 9` 穿透到 `s` 的底层数组，`s` 和 `t` 打出来都是 `[9 2 3]`。

`append` 的行为是两段式：容量够，就写进同一个底层数组；容量不够，就分配新数组、把旧数据拷过去，之后新旧切片脱钩。用代码看最清楚：

```go
package main

import "fmt"

func main() {
	base := make([]int, 3, 4)
	sub := base[1:3]
	sub = append(sub, 6) // 容量够，写进 base 的底层数组
	fmt.Println(base[:4])
	sub = append(sub, 7) // 超容量，换新数组
	sub[0] = 100
	fmt.Println(base[:4], sub)
}
```

```text
[0 0 0 6]
[0 0 0 6] [100 0 6 7]
```

`sub` 从 `base` 切出，cap 是 3（从下标 1 到数组末尾还有 3 个位置）。第一次 append 只写进第 4 个位置，`base` 被"顺带"改了；第二次 append 超出容量，`sub` 换了新数组，之后改 `sub[0]` 不再影响 `base`。所以"切片是否共享"取决于容量，不是谁都能一眼看穿。这也是为什么永远要写 `s = append(s, ...)`：append 可能换数组，返回值必须接住，别假定两个切片还共享。

扩容轨迹本机 go1.26.4 实测是 `1 2 4 8 16 32 64 128 256 512 848 1280 1792 2560`，小容量翻倍，256 之后增长放缓。**不要依赖这些具体数字**，只需要记住"可能换数组"这一件事。

想让函数改调用方切片的内容，直接传切片（共享底层数组）；想让函数增删元素（可能换数组），必须返回新切片，或传指向切片的指针。

## 三、map

map 是 Go 提供的抽象数据类型，表示一组无序的键值对，集合中每个 key 唯一，用途是把一个 value 唯一关联到特定的 key，实现按键的快速查找与更新。〔TB16 p1-2〕很多中文书把它译作映射、哈希表或字典，本手册保留英文名 map。它是继切片之后，第二个由 Go 编译器与运行时联合实现的复合数据类型：内部实现复杂，给开发者的接口却简单友好。〔TB16 p2〕类型写作 `map[key_type]value_type`，key 与 value 的类型可以相同（`map[string]string`），也可以不同（`map[int]string`）。两个 map 类型只有 key 元素类型相同、value 元素类型也相同，才算同一个 map 类型，否则就是不同的 map 类型。〔TB16 p3〕照这条规则检查 `map[string]string`、`map[int]string`、`map[string]int`：前两个 key 类型不同（string 与 int），后两个 key、value 类型都不同，三个互不相同。四条规则直接记住：

- key 必须支持 `==` 比较，切片、map、函数不能当 key。〔TB16 p3〕
- `v := m[k]` 查不到返回零值；要区分"不存在"和"值恰为零"，用 `v, ok := m[k]`。〔TB16 p8-9〕
- 遍历顺序不保证，而且运行时故意让每次遍历的起点随机，逻辑绝不能依赖遍历顺序；要稳定顺序，先把 key 取出来排序。〔TB16 p9-12〕
- map 变量本身只是一个指向运行时结构的描述符（材料称它是引用类型），传参只拷贝描述符，函数内的修改调用方可见。〔TB16 p12〕

**键的约束**。map 对 value 的类型没有任何限制，但对 key 的类型却有严格要求：map 要保证 key 的唯一性，要保证唯一，就得能比较任意两个 key 是否相同，所以 key 的类型必须支持 `==` 和 `!=` 两种比较操作符。〔TB16 p3〕但 Go 里函数类型、map 类型自身，以及切片类型只支持与 nil 比较，不支持同类型两个变量之间的比较：

```go fail
s1 := make([]int, 1)
s2 := make([]int, 2)
f1 := func() {}
f2 := func() {}
m1 := make(map[int]string)
m2 := make(map[int]string)
println(s1 == s2) // 错误：invalid operation: s1 == s2 (slice can only be compared to nil)
println(f1 == f2) // 错误：invalid operation: f1 == f2 (func can only be compared to nil)
println(m1 == m2) // 错误：invalid operation: m1 == m2 (map can only be compared to nil)
```

带 `fail` 标记的代码块是特意不让它通过编译的示例，三行 println 各自触发一条错误。这三种类型连"两个值是否相同"都答不了，map 也就无法用它们判重，所以函数类型、map 类型自身，以及切片类型不能作 map 的 key 类型。〔TB16 p3〕字段全部可比较的结构体也行，项目里的 DNS 缓存就是这么做的：`dnsproxi-go/cache/cache.go` 第 40-43 行定义了 `type Key struct{Name string; Type uint16}`，三张 map 都拿它当 key。

**nil 零值与两种初始化**。只声明、不赋初值的 map 变量，默认值是 nil。nil 切片可以借助 append 从零值直接生长，这种类型称为"零值可用"；map 因为内部实现的复杂性，做不到零值可用：对处于零值状态的 map 变量直接进行操作，会导致运行时异常（panic），进程异常退出：

```go
var m map[string]int
m["key"] = 1 // panic: assignment to entry in nil map
```

为什么读没事、写就 panic，第一节已经从哈希表的角度解释过：写要往哈希表里插槽，nil map 连表都没有。显式初始化有两种方式。方式一，复合字面值：`m := map[int]string{}`。此时变量 m 虽然没有任何键值对，但不等同于初值为 nil 的 map 变量，往里插入键值对不会引发运行时异常。方式二，make：可以指定键值对的初始容量提示，如 `make(map[int]string, 8)`，但 make 没法同时进行具体键值对的赋值。容量提示不是上限：键值对数量超过初始容量后，Go 运行时会自动增加 map 的容量，保证后续键值对的正常插入。〔TB16 p4-6〕

**comma ok 惯用法**。map 更多用在查找和读取场合。直接 `v := m[key]` 查询，若键不存在（哪怕 map 是空的），这行代码不报错，v 会被赋予 value 元素类型的零值（这里 int 是 0），拿到 0 之后，你无法区分它究竟是"键不存在返回的零值"，还是"键存在、它对应的 value 本来就是 0"。正确姿势是 comma ok 惯用法 `v, ok := m[key]`：ok 为 true 时键存在，v 被正确赋为该键对应的 value；ok 为 false 时键不存在，v 只是一个无意义的零值。只关心键是否存在、不关心 value，用空标识符忽略第一个返回值：

```go
m := map[string]int{"b": 1}

v, ok := m["b"] // ok 为 true：键存在，v 被正确赋为 1
fmt.Println(v, ok)

v, ok = m["c"] // ok 为 false：键不存在，v 只是无意义的零值
fmt.Println(v, ok)

_, ok = m["b"] // 只关心键是否存在，用空标识符忽略 value
fmt.Println(ok)
```

```text
1 true
0 false
true
```

原课的叮嘱值得原样记住：在 Go 语言中，请使用"comma ok"惯用法对 map 进行键查找和键值读取操作。〔TB16 p8-9〕项目里 `Cache.Get` 就是这么写的：`dnsproxi-go/cache/cache.go` 第 112-115 行先 `e, ok := c.m[k]`，再 `if !ok || e.Expired() { return nil, false }`，ok 为 false 直接当未命中处理。

**传参只拷贝描述符**。map 和切片一样是引用类型。map 变量作为参数传给函数或方法时，实质传递的只是一个"描述符"，而不是整个 map 的数据拷贝，所以传递的开销是固定的，而且也很小：不管 map 里有一对还是一百万对键值，传的都是同一个描述符。〔TB16 p12〕描述符指向的数据没有拷贝，所以函数内部对 map 参数的修改在函数外部可见：

```go
package main

import "fmt"

func foo(m map[string]int) {
	m["key1"] = 11
	m["key2"] = 12
}

func main() {
	m := map[string]int{
		"key1": 1,
		"key2": 2,
	}

	fmt.Println(m)
	foo(m)
	fmt.Println(m)
}
```

```text
map[key1:1 key2:2]
map[key1:11 key2:12]
```

这个描述符有名字：语法层的 map 变量一一对应一个 `runtime.hmap` 实例，hmap 是 map 的头部结构，存储后续 map 操作所需的全部信息。〔TB16 p14〕foo 拿到的副本描述符和调用方指向同一个运行时实例，改动自然穿透函数边界。

map 不支持在缺少同步时并发读写或并发写。运行时有时会检测到并以 `fatal error` 终止进程，但检测并不保证覆盖所有竞争；即使没有报错，代码仍不安全。要加锁或使用适合场景的 `sync.Map`（并发章详述）。

关于 map 的底层实现，老课程讲的是"哈希桶加 tophash、每个 bucket 8 个槽、溢出挂链"的版本。〔TB16 p14-15〕但本机 go1.26.4 的实现已经换成了基于 Abseil Swiss Table 的设计：源码头部注释明写 `The map design is based on Abseil's "Swiss Table" map design`，`grep -n "Swiss" $(go env GOROOT)/src/internal/runtime/maps/map.go` 就能看到。用法与语义不变，桶结构那套细节不用背。

## 四、字符串、字节与 rune

Go 原生支持 string 类型，和 C 的“以 `\0` 结尾的字符数组”不同。字符串不可变，`s[0] = 'k'` 编译不过，但可以整体重新赋值；`len` 是 O(1)。字符串保存任意字节，源码中的普通文本通常是 UTF-8，但从网络或 `[]byte` 构造的字符串不保证 UTF-8 合法。〔TB13 p3-6〕它在常见实现中是数据指针和长度组成的描述符，传参不复制内容。〔TB13 p10-12〕

最容易错的是"长度"。原文把看待字符串组成的方式分成两种视角〔TB13 p5-6〕：**字节视角**：字符串值是一个可空的字节序列，字节序列中的字节个数称为该字符串的长度；一个个字节只是孤立数据，不表意。**字符视角**：字符串是由一个可空的字符序列构成的；Go 源文件默认采用 Unicode 字符集，字符串中每个字符都是 Unicode 字符，在内存中以 UTF-8 编码存储，要表意就得切到这个视角。同一个 "中国人"，两个视角数出来的结果不同，用同一段代码把两边放在一起：

```go
package main

import (
	"fmt"
	"unicode/utf8"
)

func main() {
	str := "中国人"
	fmt.Println(len(str), utf8.RuneCountInString(str), str[0])
	for i, r := range str {
		fmt.Print(i, ":", string(r), " ")
	}
	fmt.Println()
}
```

```text
9 3 228
0:中 3:国 6:人
```

`len` 是字节数（"中国人"三个汉字各 3 字节），`s[i]` 取到的是单个字节（228 是"中"的第一个字节），`range` 才按 rune 迭代，索引是字节偏移 0、3、6。〔TB13 p5-6〕〔TB13 p12〕`rune` 是 `int32` 的别名，代表一个 Unicode 码点。所以处理中文、emoji 时别用下标切字符串，会从多字节字符中间切断。

先看字节视角的全貌。原文用常规 for 迭代把每个字节逐个打出来〔TB13 p5〕：

```go
var s = "中国人"
fmt.Printf("the length of s = %d\n", len(s)) // 9

for i := 0; i < len(s); i++ {
	fmt.Printf("0x%x ", s[i]) // 0xe4 0xb8 0xad 0xe5 0x9b 0xbd 0xe4 0xba 0xba
}
fmt.Printf("\n")
```

字节序列的长度是 9。原文紧接着点出关键观察：仅从输出的某一个字节来看，它不能与字符串中的任一个字符对应起来〔TB13 p5〕。9 个字节对应 3 个汉字，单挑出任何一个字节，它都只是某个汉字编码的片段，不表意。一个汉字为什么要摊到 3 个字节上，下面字面值部分揭晓。

切到字符视角，数出来的就完全是另一回事：`utf8.RuneCountInString(s)` 得到 3；`for _, c := range s` 逐个输出 0x4e2d、0x56fd、0x4eba，它们分别是"中""国""人"在 Unicode 字符集中的码点〔TB13 p6〕。两个"数长度"的手段就此分工：内置函数 len 只能获取字符串内容的长度，即字节个数；要数字符个数，专业方法是标准库 unicode/utf8 包的 RuneCountInString 函数〔TB13 p14〕。

字节视角看到的这串字节从哪来？答案藏在字符串字面值的写法里。字符串字面值用双引号包裹:把表示单个字符的单引号，换成表示多个字符组成的字符串的双引号即可，如 "abc\n"、"中国人"。字面值可以由单个 Unicode 字符字面值连在一起构成。原文示例 `"中\u56fd\u4eba"`，注释就是"中国人"。

`"\u4e2d\u56fd\u4eba"` 与 `"\U00004e2d\U000056fd\U00004eba"` 的注释同样是"中国人"〔TB13 p7-8〕。最有信息量的是示例最后一行 `"\xe4\xb8\xad\xe5\x9b\xbd\xe4\xba\xba"`，原文标注为"十六进制表示的字符串字面值：中国人"，并自设一问：这些字节的值与前面几行的码点值（0x4e2d 这些）完全对应不上，为什么？答案是：这个字节序列实际上是"中国人"这个 Unicode 字符串的 UTF-8 编码值〔TB13 p8〕。也就是说，\xNN 直写的不是码点，而是编码后的字节：中 0xe4 0xb8 0xad、国 0xe5 0x9b 0xbd、人 0xe4 0xba 0xba,正是字节视角迭代打出的那 9 个字节；而按码点写的 \u56fd 存储时同样落成这 3 个字节，所以写法不同的字面值得到的是同一个字符串值（`"中\u56fd\u4eba"` 与 `"中国人"` 本机 go1.26.4 实测相等）。

一个汉字为什么会编码成 3 个字节？UTF-8 编码解决的是 Unicode 码点在计算机中如何存储和表示的问题，它用变长字节对码点编码：前 128 个与 ASCII 重合的码点（U+0000~U+007F）用 1 个字节表示，带变音符号的拉丁文、希腊文、西里尔字母、阿拉伯文等用 2 个字节，东亚文字（包括汉字）用 3 个字节，其他极少使用的字符用 4 个字节〔TB13 p8-9〕。编码单元是一个字节，因此没有 UTF-32 那样的字节序问题，还顺带兼容了 ASCII 的内存表示〔TB13 p9〕。

最后解释程序输出里的 228。在字符串的实现中，真正存储数据的是底层数组，字符串的下标操作本质上等价于底层数组的下标操作〔TB13 p12〕。原文示例 `fmt.Printf("0x%x\n", s[0])` 输出 0xe4，注释写明这是字符"中"的 UTF-8 编码的第一个字节；原文的结论是：通过下标操作，我们获取的是字符串中特定下标上的字节，而不是字符〔TB13 p12〕,0xe4 换成十进制正是 228。留言区里作者对相关提问的答复确认了同样的两条边界：`s[0] = 'k'` 这种赋值不可以，go string 不可更改；字符串下标操作只能获得字节，而不是字符〔TB13 p22〕。想拿到"中"这个字符本身，得用 for range 迭代：每轮返回该字符的码点值，以及该字符在字符串中的起始字节偏移〔TB13 p13-14〕。

## 五、结构体、定义类型与别名

结构体把多个字段聚合成一个实体。在定义结构体之前，先分清 Go 自定义新类型的两种写法。

第一种是类型定义（Type Definition），也是最常用的：用关键字 `type` 定义一个新类型 T，形式 `type T S`。S 可以是任何一个已定义的类型，既包括 Go 原生类型，也包括其他已定义的自定义类型：先 `type T1 int`，再 `type T2 T1`，T2 就是基于 T1 再定义的新类型。类型定义得到的是与 S 不同的新类型。〔TB17 p2〕判断"不同类型能否互转"要看**底层类型**，而不是类型名：新类型基于某个 Go 原生类型定义时，该原生类型就是它的底层类型（T1 的底层类型是 int）；基于自定义类型定义时，就沿用其定义基础的底层类型：T2 基于 T1，所以 T2 的底层类型也是 int。〔TB17 p2-3〕底层类型被用来判断两个类型本质上是否相同（Identical）：T1 与 T2 是不同类型，但底层类型同为 int，本质相同；本质相同的两个类型，变量可以通过显式转型相互赋值；本质不同的两个类型，变量间连显式转型都不可能，更不要说相互赋值了：

```go
type T1 int
type T2 T1
type T3 string

func main() {
	var n1 T1
	var n2 T2 = 5
	n1 = T1(n2) // ok

	var s T3 = "hello"
	n1 = T1(s) // 错误：cannot convert s (type T3) to type T1
}
```

类型定义还可以基于类型字面值，多用于自定义新的复合类型，比如 `type M map[int]string`、`type S []string`；多条类型定义也可以像 var 块那样放进一个 type 块聚合书写。〔TB17 p3-4〕

第二种是类型别名（Type Alias）：`type T = S`，只比类型定义多一个等号。正是这个等号让 T 与 S 完全等价：别名没有定义出新类型，T 与 S 实际上就是同一种类型的两个名字，互相赋值不需要转型：

```go
type T = string

var s string = "hello"
var t T = s // ok：同一种类型的两个名字，直接赋值
fmt.Printf("%T\n", t) // string
```

别名的典型使用场景是项目的渐进式重构和对已有包的二次封装；两种写法差一个等号，差别就在是否产生新类型上。〔TB17 p4〕

初始化结构体推荐带字段名 `T{Field: v}`：顺序无关，以后新增字段不会破坏旧代码；常写 `T{}` 而少用 `new(T)`。〔TB17 p13-14〕

空结构体是不包含任何字段的结构体类型：`type Empty struct{}`。`unsafe.Sizeof` 对空结构体变量输出 0，即空结构体类型变量的内存占用为 0：

```go
type Empty struct{} // Empty 是一个不包含任何字段的空结构体类型
var s Empty
println(unsafe.Sizeof(s)) // 0
```

基于零内存开销的特性，日常开发常用空结构体类型元素作为一种"事件"信息在 Goroutine 之间通信，要传的只是"某件事发生了"这个信号，不携带数据：

```go
var c = make(chan Empty) // 声明一个元素类型为 Empty 的 channel
c <- Empty{}             // 向 channel 写入一个"事件"
```

以空结构体为元素类型的 channel，是目前能实现的、内存占用最小的 Goroutine 间通信方式：事件本身零字节，不必为"信号值"分配任何内存。〔TB17 p6-7〕项目里有两处现成的例子：`dnsproxi-go/tcp/server_test.go` 第 48-51 行 `done := make(chan struct{})`，`Serve` 返回后 `close(done)`；`dnsproxi-go/main.go` 第 255 行用同一个模式通知后台过期回收器退出。

结构体不能递归包含自身，除非通过指针、切片、map 间接包含。〔TB17 p8-9〕

最后是字段顺序影响大小这件事，很多人第一次听说时会愣一下：

```go
package main

import (
	"fmt"
	"unsafe"
)

type Bad struct {
	a bool
	b int64
	c bool
}

type Good struct {
	b int64
	a bool
	c bool
}

func main() {
	fmt.Println(unsafe.Sizeof(Bad{}), unsafe.Sizeof(Good{}))
}
```

```text
24 16
```

两个结构体字段完全一样，只是顺序不同，`Bad` 占 24 字节，`Good` 占 16。原因是编译器为了对齐，会在字段间插入填充：`int64` 必须放在 8 的倍数地址上，`Bad` 里 `bool` 后面要补 7 字节再放 `int64`，末尾再补 7 字节凑成 8 的倍数。〔TB17 p16-17〕〔TB17 p17-19〕对热路径上的大量小结构体，调一下字段顺序是免费的内存优化。

## 六、常量与 iota

常量是 Go 中**在源码编译期间被创建**的语法元素：它的值可以像变量那样被初始化，但初始化表达式必须是在编译期间就能求出值的表达式。〔TB14 p2〕常量一旦声明并完成初始化，值在整个程序生命周期内保持不变，声明之后不可再改。由"值全程不变"能直接推出两个好处：并发设计时不用考虑常量访问的同步问题；被创建并初始化后的常量还可以作为其他常量初始化表达式的一部分:编译期就能求出值的元素，天然可以被后续常量定义复用。〔TB14 p2〕

声明常量用 `const` 关键字，与声明变量的 `var` 相对应。声明形式也和 `var` 完全对齐：`var` 支持单行声明多个变量、支持以代码块形式聚合变量声明，`const` 同样支持单行声明多个常量、支持以 `const` 代码块形式聚合常量声明：

```go
const Pi float64 = 3.14159265358979323846 // 单行常量声明

// 以 const 代码块形式声明常量
const (
	size    int64 = 4096
	i, j, s       = 13, 14, "bar" // 单行声明多个常量
)
```

上面的写法出自原课示例〔TB14 p2〕。同时有一条规范边界要记住：Go 语言规范规定，常量的类型只局限于基本数据类型:数值类型、字符串类型，以及只有 `true` 和 `false` 两个取值的布尔类型。数组、切片、map、结构体这些复合类型没有常量形态。

接下来看常量与类型怎么相处。本章开头对比表里有一行"无隐式转换（无类型常量除外）"，先把括号外的前半句看清楚。Go 对类型安全有严格要求：即便两个类型拥有相同的底层类型，它们仍然是不同的数据类型，不可以相互比较，也不能混在同一个表达式中运算。这条要求不仅适用于变量，也同样适用于**有类型常量**（Typed Constant，声明时显式赋予了类型的常量）。〔TB14 p4〕

定义 `type myInt int`，声明有类型常量 `const n myInt = 13`，再拿一个 `int` 变量与它相加：

```go
package main

import "fmt"

type myInt int

const n myInt = 13

func main() {
	var a int = 5
	fmt.Println(a + n) // 编译错误：invalid operation: a + n (mismatched types int and myInt)
}
```

`myInt` 的底层类型明明就是 `int`，运算仍被拒绝（go1.26.4 实测报 `mismatched types int and myInt`）：底层类型相同不等于类型相同。把 `n` 用进另一个 `int` 常量的初始化表达式同样通不过，原课示例 `const m int = n + 5` 报 cannot use n + 5 (type myInt) as type int（原课记录的报错文案，现行工具链措辞可能略异），是同一条规则。〔TB14 p4〕出路只有显式转型:把参与运算的值变成同一类型。

```go
package main

import "fmt"

type myInt int

const n myInt = 13
const m int = int(n) + 5 // OK：先显式转型为 int 再参与运算

func main() {
	var a int = 5
	fmt.Println(a + int(n)) // 输出：18
}
```

〔TB14 p4〕每次都写 `int(n)` 太啰嗦。Go 为此做了第一个创新：**无类型常量**（Untyped Constant），即声明时不显式赋予类型的常量，例如 `const n = 13`。〔TB14 p4-5〕

注意，"无类型"不等于"没有类型"：无类型常量有自己的**默认类型**，默认类型由初值的形式决定，初值是整数形式，默认类型就是 `int`。〔TB14 p5〕关键是这个默认类型并不把常量锁死在 `int` 上,它可以和别的类型的变量直接放进同一个表达式：

```go
package main

import "fmt"

type myInt int

const n = 13 // 无类型常量，初值为整数形式

func main() {
	var a myInt = 5
	fmt.Println(a + n) // 输出：18
}
```

`n` 的默认类型 `int` 与 `myInt` 并不是同一个类型，`a + n` 却编译通过并输出 18。〔TB14 p5〕为什么这次严格类型规则没有拦住它？答案是常量的第二个创新"隐式转型"：编译器根据上下文中的类型信息，把无类型常量自动转换后再参与求值；转换的对象是编译期常量，不会引发类型安全问题，转不了的场景（如把超出 `int8` 表示范围的值转进去）编译器同样立刻报错。〔TB14 p4-6〕这就是 `const n = 13` 能和 `int8`、`int64` 等混用而不用写显式转型的原因，换成会溢出的常量值，编译器立刻拦下；也是本章开头对比表"无隐式转换（无类型常量除外）"的完整含义:隐式转型只对无类型常量开放，变量之间不适用。在 Go 中，用无类型常量参与表达式运算是惯用法，混合类型的求值不需要写任何显式转型。〔TB14 p5-6〕

最后是用常量实现枚举。Go 没有 `enum` 关键字，枚举用 `const` 块加 `iota`：

```go
package main

import "fmt"

type Weekday int

const (
	Sunday Weekday = iota
	Monday
	Tuesday
	Wednesday
	Thursday
	Friday
	Saturday
)

func main() {
	fmt.Println(Sunday, Monday, Tuesday, Saturday)
}
```

```text
0 1 2 6
```

`iota` 在每个 `const` 块里从 0 开始，每行加 1，后续行隐式重复前一行的表达式，所以 `Monday`、`Tuesday`、`Saturday` 依次是 1、2、6；每个 `const` 块独立计数。〔TB14 p8-12〕

## 七、作用域与遮蔽

作用域是针对**标识符**的概念，不局限于变量：每个标识符（变量、常量、类型、函数、导入的包名）都有自己的作用域，即声明之后可以被有效使用的源码区域。作用域是**编译期**概念：编译器在编译过程中检查每个标识符，对超出作用域的使用直接报编译错误（go1.26.4 实测报 `undefined`）。〔TB11 p4〕〔TB11 p11〕划定原则只有一条：声明于外层代码块中的标识符，其作用域包括**所有内层代码块**，显式块和隐式块都适用，所以包级变量在 `func`→`if`→`for` 层层嵌套的隐式块里可以直接使用（实测编译通过）。〔TB11 p4〕这条规则同时也是遮蔽问题的土壤，真正咬人的是 `:=`：它在内层块里会**新建**变量，遮蔽外层同名变量，这是最阴险的低级 bug。〔TB11 p1-2〕〔TB11 p4〕

```go
package main

import "fmt"

func main() {
	x := 1
	var err error
	if _, err := fmt.Sscan("12", &x); err != nil {
		// 这里的 err 是 if 语句里的新变量
	}
	fmt.Println(x, err)
}
```

```text
12 <nil>
```

`x` 被改成了 12（`Sscan` 真的写进了 `&x`），但外层 `err` 还是 nil，因为 `if` 里的 `:=` 声明了一个**新的** `err`，遮蔽了外层的，错误被静默丢弃。这类 bug 难查就在于代码看起来"确实处理了 err"，其实处理的是另一个变量。

原课用更小的例子开场（节选）：包级 `var a = 11`，`foo` 里执行 `a := 1` 和 `a += n`。〔TB11 p1-2〕

```go
var a = 11

func foo(n int) {
	a := 1
	a += n
}

func main() {
	fmt.Println("a =", a)                    // 11
	foo(5)
	fmt.Println("after calling foo, a =", a) // 11
}
```

`foo` 里明明写了 `a := 1` 和 `a += n`，但 `foo` 调用前后包级 `a` 都是 11：`a := 1` 是在 `foo` 函数体这个内层块里**新建**的变量，`a += n` 改的只是这个内层变量，赋值从头到尾没有落到包级 `a` 上。〔TB11 p1-2〕原文对这类错误的定性值得记住：变量遮蔽是 Go 开发者日常最容易犯的编码错误之一，它低级又不容易查找，常常让人陷入漫长的调试过程；这个例子还能肉眼定位，更复杂的遮蔽可能把人折腾很久，最后只能靠工具捕捉。〔TB11 p2〕

**函数边界上的标识符**。函数签名里的接收器、参数、命名返回值写在函数体大括号外面，看起来"不在任何代码块里"，但它们属于函数定义的一部分，作用域就是函数体这个显式代码块：`func (t T) M1(x int) (err error)` 里，`t`、`x`、`err` 在函数体的任意内层块中都可以直接使用，直到函数体的收尾大括号处才终止。〔TB11 p6〕函数体**内部**声明的常量、变量和类型走另一条规则：作用域**始于声明语句的末尾**，终止于**最内层包含块的末尾**:声明那一行之前的代码不能用这个名字，出了所在块也不能再用。〔TB11 p6-7〕把原文的作用域标注翻译成注释（讲解用片段，不能独立编译）：

```go
func (t T) M1(x int) (err error) { // 代码块 1：t、x、err 的作用域从这里开始
	m := 13 // m 的作用域始于本行末尾

	{ // 代码块 2
		type bar struct{} // bar 的作用域始于本行末尾
		{ // 代码块 3
			a := 5 // a 的作用域始于本行末尾
			{ // 代码块 4
				// ... ...
			}
			// a 的作用域终止于此
		}
		// bar 的作用域终止于此
	}
	// m、t、x、err 的作用域终止于此
}
```

**隐式代码块：规范定义、没有大括号的五层嵌套**。前面看到的代码块都有肉眼可见的配对大括号，但 Go 的代码块不止这一种。隐式代码块（Implicit Block）没有显式代码块那样的肉眼可见的配对大括号包裹，无法靠大括号识别，它由 Go 语言规范明确定义。〔TB11 p3〕原文为此配了一张五层嵌套示意图（图片未随正文文本保留），随后正文按"范围从大到小"逐层文字描述，嵌套关系可以完整复原。按范围从大到小，五层依次是：

1. **宇宙代码块（Universe Block）**：囊括的范围最大，所有 Go 源码都在这个隐式代码块中，可以把它想象为在所有 Go 代码的最外层加一对大括号。
2. **包代码块（Package Block）**：嵌套在宇宙代码块内部，每个 Go 包对应一个，包含该包中的所有 Go 源码，不管这些代码分布在多少个源文件里。
3. **文件代码块（File Block）**：嵌套在包代码块内部，每个 Go 源文件对应一个；一个包有多个源文件，就有多个对应的文件块。
4. **控制语句隐式块**：包括 if、for 与 switch，每个控制语句都被视为处于它自己的隐式代码块里。注意：控制语句的隐式代码块与它用大括号包裹的显式代码块**不是同一个块**:以 switch 为例，其隐式代码块的位置在它显式代码块的外面，包住整个语句。正因如此，switch 头部短声明引入的变量对各个 case 子句来说是"更外层"的名字（这一结构正是后面三连遮蔽案例里遮蔽二、三的载体）。〔TB11 p3-4〕
5. **case/default 子句隐式块**：最内层。switch 或 select 语句的每个 case/default 子句虽然没有大括号包裹，但实质上每个子句各自自成一个代码块。〔TB11 p3-4〕

原课小结把这五类复述为：宇宙代码块、包代码块、文件代码块、分支控制语句隐式代码块，以及 switch/select 的子句隐式代码块。〔TB11 p11〕这些规则是语言规范内容，现行有效：go1.26.4 下本文各示例的行为都与规则一致（下文 else-if 链的实测即是一例）。

**宇宙块：预定义标识符的"自留地"**。从最外层看起。宇宙块这一层的标识符无法由开发者声明,原文称这一区域是 Go 语言预定义标识符的"自留地"，这是第一层规则；第二层是位置带来的结果：这些预定义标识符位于包代码块的外层，作用域范围最大，对开发者而言，源代码中的任何位置都可以使用它们。〔TB11 p4-5〕原文以表格整理了"Go 语言当前版本定义里的所有预定义标识符"，但该表以图片形式贴出、未随正文文本保留，这里不转抄清单；true、false、iota、len、cap、new、make、append 是其中几个常用例子。

预定义标识符**不是关键字**。不是关键字，内层代码块中就可以声明同名标识符把它们遮蔽掉:`type new int` 之后再写 `new(int)` 就编译不过（详见下文三连遮蔽案例的遮蔽一）。〔TB11 p4-5〕这正是三连遮蔽案例里 `type new int` 能通过编译的规则前提：在包级把 new 声明成新类型后，宇宙块里的预定义 new 在本包内被顶掉，后续想用它分配内存的代码就会受影响。实践上两条：不要用预定义名当变量或类型名；函数保持短小，缩短遮蔽的查找范围。

**包块：顶层声明与导出标识符**。下一层是包代码块。哪些标识符具有包代码块级作用域？答案是：包顶层声明中的常量、类型、变量或函数,方法（method）不在其列。〔TB11 p5〕这里有一个特殊情况：当一个包 A 导入另一个包 B 后，包 A 仅可以使用被导入包 B 中的导出标识符（Exported Identifier）。按照 Go 语言定义，一个标识符要成为导出标识符需同时具备两个条件、缺一不可：一是这个标识符声明在包代码块中，或者它是一个字段名或方法名；二是它名字的第一个字符是一个大写的 Unicode 字符。〔TB11 p5〕用这两个条件回答一个自然的问题：小写开头的包级函数能被导入方使用吗？它满足条件一（声明在包代码块中），但名字首字符小写不满足条件二，因此不是导出标识符，导入方无法使用（教学推导：原文给出的是判定条件与"仅可使用导出标识符"的规则，这一句由两者直接推出）。原文由"包 A 为什么只能用 B 的导出标识符"之问引出这套定义，只给判定条件，未解释设计动机。

**文件块：导入的包名**。再往里，具有文件代码块级作用域的标识符，原文说"确实不多了"，但还有一个:导入的包名。〔TB11 p6〕这条作用域规则直接回答一个常见疑问：如果包 A 有两个源文件，二者代码都依赖包 B 中的标识符，那么这两个源文件**各自**都需要导入包 B。不存在"包级导入"：导入的包名只在本源文件的文件块内可见，只在一个文件里 import 了 B，另一个源文件并不能直接使用 B 的标识符。

**控制语句隐式块：if/else if 链的等价转换**。if、for、switch 各自的隐式块如何决定可见性？原文用一条三层的 if-else if-else 链示范（讲解用片段）：

```go
func bar() {
	if a := 1; false {
	} else if b := 2; false {
	} else if c := 3; false {
	} else {
		println(a, b, c)
	}
}
```

等价转换规则：每个 if 语句的隐式代码块包住其后的所有 else if/else 分支。把链中的隐式块全部转成显式块后，第一个 if 的隐式块变成最外层转换块（内含 `a := 1` 与 `if false {} else {...}`），每个 else if 同样各自转成一个显式块（分别内含 `b := 2`、`c := 3`），层层嵌套。下面是原文给出的转换结果：

```go
func bar() {
	{ // 等价于第一个if的隐式代码块
		a := 1 // 变量a作用域始于此
		if false {

		} else {
			{ // 等价于第一个else if的隐式代码块
				b := 2 // 变量b的作用域始于此
				if false {

				} else {
					{ // 等价于第二个else if的隐式代码块
						c := 3 // 变量c作用域始于此
						if false {

						} else {
							println(a, b, c)
						}
						// 变量c的作用域终止于此
					}
				}
				// 变量b的作用域终止于此
			}
		}
		// 变量a作用域终止于此
	}
}
```

转换代码把各变量的作用域边界标了出来：c 的作用域终止于它的转换块末尾，b 终止于其外一层，a 终止于最外层转换块末尾,三者的作用域都延伸覆盖到最内层 else。原文由此给出结论：声明于不同层次隐式代码块中的变量 a、b、c，其实际作用域都位于最内层的 else 显式代码块之外，于是在 println 所在的那个显式代码块中，a、b、c 都是合法的，而且还保持了初始值（1、2、3）。〔TB11 p7-8〕这条规则现行有效：把两个变量的版本 `if a := 1; false {} else if b := 2; false {} else { println(a, b) }` 在 go1.26.4 下运行，最内层 else 打出 `1 2`，即条件中声明的变量在最内层分支可见（主控实测）。原文只给出转换与可见性结论，未解释该设计的动机，这里不替原文补。

**三连遮蔽：一次用全所有规则**。原课收尾给了一个真实案例（节选，`errors`、`fmt` 的导入从略；它与 `type new int` 的组合在 Go 1.17.1 下已实测编译报错（留言区反馈），版本差异与两种修复方向见下文）：〔TB11 p8-10〕〔TB11 p13〕

```go
var a int = 2020

func checkYear() error {
	err := errors.New("wrong year")

	switch a, err := getYear(); a {
	case 2020:
		fmt.Println("it is", a, err)
	case 2021:
		fmt.Println("it is", a)
		err = nil
	}
	fmt.Println("after check, it is", a)

	return err
}

type new int

func getYear() (new, error) {
	var b int16 = 2021
	return new(b), nil
}

func main() {
	err := checkYear()
	if err != nil {
		fmt.Println("call checkYear error:", err)
		return
	}
	fmt.Println("call checkYear ok")
}
```

原文（2021 年语境）的运行输出：

```text
it is 2021
after check, it is 2020
call checkYear error: wrong year
```

`getYear` 返回了正确的年份 2021，`checkYear` 结尾却打印 2020、还向 main 返回了非 nil 的错误。原文把这归为变量遮蔽的"锅"。逐处"找找茬"，一共三处遮蔽：〔TB11 p8-10〕

**遮蔽一：标识符遮蔽预定义标识符。** `type new int` 用 `new` 这个名字定义了新类型，遮蔽了预定义标识符 `new`。此时若在 main 下方补上 `p := new(int)`，2021 年的编译器会报 "type int is not an expression"。意识不到 `new` 被遮蔽，这个提示会让人不知所措。但要注意：遮蔽 `new` **并不是本例输出反常的原因**，它只影响后续想用 `new` 分配内存的代码。〔TB11 p9-10〕

版本差异：这个示例对 Go 版本敏感。精选留言（程旭阳，2021-11-06）在 go1.17.1 下实测，`type new int` 会报错，错误信息有两条：`cannot assign new to a (type int) in multiple assignment` 与 `cannot use new value as type int in assignment`；修改为类型别名 `type new = int` 之后不再报错（留言原文在"不再报错"之后即被省略号截断，其后的内容不可见）。〔TB11 p13〕另一位留言者（Rayjun，2021-11-06）给出另一个修复方向，"修改两个地方"：把 a 的类型改成 new（留言展示 `var a new = 2020`），并"去掉 switch 那的一个引号"。引号的具体位置原文未展示，留言代码在 `func checkYear() error { …` 处截断，无法核实，这里如实存疑。〔TB11 p14〕两条留言合并的含义：这个示例里 `type new int` 与该赋值的组合从 Go 1.17.1 起已不能照原样编译，在更新版本的 Go 下需要按上面两个方向之一调整（本章末「想深入」TB11 笔记也记了这条）。现行 go1.26.4 实测口径：单独声明 `type new int` 可以编译；同包内再写 `new(int)` 报 `int (type) is not an expression`；没有 `type new int` 时 `new(int)` 正常编译。

**遮蔽二：switch 隐式块遮蔽包级变量。** switch 语句在它自身的隐式代码块里，通过短变量声明 `a, err := getYear()` 重新声明了变量 `a`，遮蔽了包级 `a`。2021 被赋给了 switch 隐式块里新声明的 `a`，包级 `a` 从未被赋成正确年份，这就是打印 "after check, it is 2020" 的原因。〔TB11 p10〕

**遮蔽三：同一句短声明遮蔽外层显式块的 err。** 还是 `a, err := getYear()` 这一句，除新声明 `a` 之外还声明了名为 `err` 的变量，遮蔽了 `checkYear` 函数显式代码块里声明的 `err`。case 2021 里的 `err = nil` 落到了 switch 隐式块的 `err` 上，外层 `err` 仍是非 nil 的 "wrong year"，于是 `checkYear` 虽然从 `getYear` 拿到了正确年份，却把错误返回给了 main，main 打印 "call checkYear error: wrong year"。〔TB11 p10〕

这个案例的共性结论，原文的说法是：短变量声明与控制语句的结合十分容易导致变量遮蔽问题，并且很不容易识别，因此在日常 go 代码开发中要尤其注意两者结合使用的地方。〔TB11 p10〕checkYear 第 7 行 switch 的一句短声明 `a, err := getYear()` 正是"高发且难辨认"的具体依据：这一句同时新声明了 a（遮蔽包代码块中的包级变量 a）和 err（遮蔽 checkYear 函数显式代码块中的 err）,一句声明制造两处遮蔽，上面找出的三处问题有两处都出自它。原文接着说，依靠肉眼识别变量遮蔽问题终归不是长久之计，并由此过渡到可以辅助检测的工具（go vet 加 shadow 插件，下一小节展开）；原文未给出更深层的机理解释，这里不替原文补。

**工具检测：shadow 插件的能力与边界**。go vet 是 Go 官方提供的静态检查工具，可用于对 Go 源码做一系列静态检查；在 Go 1.14 版以前它默认支持变量遮蔽检查，Go 1.14 版之后，变量遮蔽检查的插件需要单独安装。〔TB11 p10〕现在要检测一个文件的遮蔽问题，完整命令分安装与执行两步（均照抄原文）：

```text
$go install golang.org/x/tools/go/analysis/passes/shadow/cmd/shadow@latest
$go vet -vettool=$(which shadow) -strict complex.go
```

原文安装时输出了所下载的模块版本：golang.org/x/tools v0.1.5 与 golang.org/x/mod v0.4.2（2021 年的工具版本记录）。对三连遮蔽那个 complex.go 执行 -strict 检查，原文仅得到一条提示：

```text
./complex.go:13:12: declaration of "err" shadows declaration at line 11
```

变量 a 以及预定义标识符 new 被遮蔽的情况都没有提示。原文由此给出的结论是：工具确实可以辅助检测，但不是万能的，不能穷尽找出代码中的所有问题，所以还是要深入理解代码块与作用域的概念，尽可能在日常编码时就主动规避遮蔽问题。〔TB11 p11〕

不过"只报 err 一处"是 2021 年工具版本的口径，不能照搬到今天。按 go1.26.4 + shadow@latest 主控实测，当前版本的行为是：err 遮蔽在默认模式（不加 -strict）下即报；包级变量 a 的遮蔽只在加 -strict 时才报；`type new int` 这类类型标识符的遮蔽在两种模式下都报不出来。换句话说，-strict 现在能补报出包级变量的遮蔽，但类型标识符遮蔽至今仍检测不到,原文"工具辅助但非万能"的结论在现行版本依然成立，且边界从"漏报哪些"具体到了"哪一类遮蔽报不出来"。

Go 1.22 起，`for` 用 `:=` 声明的循环变量**每次迭代新建一份**（前提是该文件采用 Go 1.22 或更高语言版本）；用 `=` 赋值给已有变量仍会复用该变量：

```go
package main

import "fmt"

func main() {
	var fs []func()
	for i := range 3 {
		fs = append(fs, func() { fmt.Print(i, " ") })
	}
	for _, f := range fs {
		f()
	}
	fmt.Println()
}
```

```text
0 1 2
```

老教程里闭包共享循环变量的坑，在采用新语义且由循环声明变量时已不存在；如果循环使用 `=` 更新外部变量，闭包仍共享那个变量。

## 小结

1. Go 赋值传参都复制值；复合值里也可能包含指针或其他引用，复制外层不等于复制所引用的数据。
2. 数组是值（整块拷贝），切片是三元组（指针、len、cap），拷贝描述符不拷贝数据。
3. append 可能换数组，永远接住返回值；切片是否共享取决于容量。
4. map：key 要可比较，读不到返零值要用 `v, ok` 区分，遍历无序，不是并发安全。
5. 字符串不可变，保存任意字节；`len` 数字节，`range` 按 UTF-8 解码 rune。
6. `type T S` 是新类型，`type T = S` 是别名；结构体字段顺序影响内存占用。
7. 无类型常量按上下文隐式转型，枚举用 const + iota。
8. `:=` 在内层块可能新建变量遮蔽外层；1.22 起循环声明的变量每次迭代独立。

## 常见坑

1. 以为两个切片独立，其实共享底层数组；append 后是否脱钩取决于容量。
2. 用 `len(s)` 当字符个数，对中文得到的是字节数。〔TB13 p5-6〕
3. `if x, err := f(); ...` 里的 `err` 遮蔽外层 `err`，错误被静默丢弃。〔TB11 p1-2〕
4. 整型溢出悄悄回绕，不报错也不 panic，窄整型做计数时要小心。〔TB12 p5〕
5. nil map 写入 panic、把遍历顺序当成稳定的：见第三节。

## 判断题与答案

先自己答，再看后面。

1. 函数 `func f(s []int) { s = append(s, 1) }`，调用方的切片变了吗？如果 `s` 的容量还有富余呢？
2. `var m map[string][]int; m["a"] = append(m["a"], 1)` 哪一步出问题？
3. 为什么 `x := 1; if true { x := 2 }` 之后外层 `x` 还是 1？
4. 结构体 `struct{ a bool; b int64; c bool }` 为什么不是 10 字节？

答案：

1. 调用方的切片值没变，因为 `append` 的返回值只赋给了 `f` 里的局部变量 `s`。容量有富余时，新元素确实写进了共享的底层数组，但调用方的 `len` 没变，看不到；容量不足时换新数组，调用方完全无感。
2. 读 `m["a"]` 和 `append` 都没问题（nil map 可读，nil 切片可 append），出问题的是最后的赋值 `m["a"] = ...`：它要向 nil map 写入，nil map 不可写，直接 panic `assignment to entry in nil map`。
3. 内层 `x := 2` 用 `:=` 在内层块里新建了一个同名变量，遮蔽了外层 `x`；赋值只发生在内层变量上，外层不受影响。
4. 编译器为对齐插入填充：`int64` 要对齐到 8 的倍数，`bool` 后面补 7 字节，末尾 `bool` 后再补 7 字节凑成 8 的倍数，实际是 24 字节，不是 1+8+1=10。

### TB10 变量声明的选择规则

**为什么静态语言需要"变量声明"**。变量是编程语言用特定名字绑定特定位置内存块的产物，但通过变量不能随意引用或修改内存：这个名字究竟操作 4 字节、8 字节还是 256 字节内存，必须有明确边界。动态语言（如 Python、Ruby）的解释器在运行时通过对赋值的分析自动确定边界，同一个变量在运行时还能被赋予大小不同的边界；静态语言的编译器必须在使用变量前就明确知道边界，自己却没有能力提供，这个边界信息只能由语言使用者给出。变量声明由此而来，这就是它存在于静态语言的根本原因。实现层面，边界信息由变量的类型属性赋予。Go 身处静态语言阵营，沿袭这一要求：使用变量之前必须先声明。〔TB10 p1-2〕

**通用声明：四段式与零值**。Go 的通用变量声明分四个部分：var 关键字、变量名（如 a）、类型（如 int）、初值（如 10），即 `var a int = 10`，任何类型的变量都可以用这种形式声明；与其他主流静态语言相比有个显著差异：Go 把变量名放在类型前面，原文把这题留给了读者，官方的解释见本节末尾。声明时若没有显式赋予初值，编译器会赋予该类型的零值：`var a int` 的初值就是 int 的零值 0。零值是每种原生类型的默认值；复合类型的零值是组成式的：数组、结构体这类复合类型变量的零值，就是它们组成元素全为零值时的结果（规范注明这种初始化递归进行，所以结构体数组每个元素的字段也会清零，$GOROOT/doc/go_spec.html:8138-8139）。〔TB10 p3-4〕

**声明块与一行多声明**。除了逐个声明每个变量，Go 还提供了变量声明块（block）的语法形式：用一个 var 关键字加括号，把多条变量声明聚合在一起。块内各条声明的类型各不相同也完全可以，原文的示例块一个 var 关键字就声明了 int、int8、string、rune、bool 五种类型的变量，可见 var 块在语法上不限制块内各条声明的类型：

```go
var (
	a int    = 128
	b int8   = 6
	s string = "hello"
	c rune   = 'A'
	t bool   = true
)
```

Go 还支持在一行里同时声明多个变量，如 `var a, b, c int = 5, 6, 7`，类型只写一次；这种一行多声明同样可以放进 var 块（原书示例把 `a, b, c int = 5, 6, 7` 与 `c, d, e rune = 'C', 'D', 'E'` 写进了同一个 var 块，两行重复使用变量名 c，而同一个块里不能声明同名变量，原样照抄编译不过，写示例时应把名字错开）。〔TB10 p4〕类型只写一次意味着它作用于整行全部名字，所以带显式类型的一行多声明只能声明同类型的变量；要在一行里声明 int、rune、string 三种不同类型的变量，须改用省略类型的糖 `var a, b, c = 12, 'A', "hello"`，各变量分别取初值对应的默认类型 int、rune、string，推导规则就是下文"语法糖一"讲的按初值取默认类型。〔TB10 p5-6〕三种写法合在一个程序里（本机 go1.26.4 实测）：

```go
package main

import "fmt"

func main() {
	// 一行多声明：类型只写一次，三个变量同类型
	var x, y, z int = 5, 6, 7
	// 混类型的一行多声明：省略类型，各变量取初值对应的默认类型
	var i, j = 1, "s"
	// 一行多声明同样可以写进 var 块
	var (
		a, b, c int = 5, 6, 7
	)
	fmt.Println(x, y, z)
	fmt.Println(a, b, c)
	fmt.Println(i, j)
}
```

```text
5 6 7
5 6 7
1 s
```

**语法糖一：省略类型**。在通用形式的基础上可以省略类型信息，标准范式 `var varName = initExpression`，例如 `var b = 13`。编译器遇到这类声明，按右侧初值推导类型并赋予初值对应的默认类型：整型值默认 int，浮点值默认 float64，复数值默认 complex128；其他类型值的默认类型更好分辨，布尔、字符、字符串在 Go 里各自只有唯一对应类型，分别是 bool、rune、string。本机 go1.26.4 实测（用 `%T` 打印类型）：

```go
package main

import "fmt"

func main() {
	var b = 13                     // int
	var f = 1.5                    // float64
	var c = 1 + 2i                 // complex128
	var a, r, s = 12, 'A', "hello" // 一行三个变量：int、rune、string
	fmt.Printf("%T %T %T\n", b, f, c)
	fmt.Printf("%T %T %T\n", a, r, s)
}
```

```text
int float64 complex128
int int32 string
```

第三行里字符常量 `'A'` 的默认类型是 rune，`%T` 打出的是它的底层类型名 int32(rune 只是 int32 的别名,语义上表示一个 Unicode 码点)。

不接受默认类型时，除了通用四段式（`var b int32 = 13`），还可以写转型形式 `var b = int32(13)`，要 float32 就写 `var f = float32(1.5)`。这颗糖的前提是声明的同时必须显式赋初值，有两种写法过不了编译（均为 go1.26.4 实测报错）：

```go fail
func main() {
	var b
}
```

```text
syntax error: unexpected newline, expected type
```

`var b` 既无类型也无初值，编译器没有可推导的信息。`var n = nil` 是另一类失败：nil 没有默认类型，类型检查阶段直接拦下（报 use of untyped nil in variable declaration）：

```go fail
var n = nil
```

规范层面完全同源：VarSpec 文法（$GOROOT/doc/go_spec.html:2810）规定类型与初值表达式二选一必现；省略类型时初值若为无类型常量，隐式转换为它的默认类型（699-706 行）；且预先声明的 nil 不能用于初始化无显式类型的变量（2847 行的规范示例就是 `var n = nil // illegal`）。〔TB10 p5-6〕

**语法糖二：短变量声明**。最简化的形式连 var 关键字也省去，标准范式 `varName := initExpression`，如 `a := 12`、`b := 'A'`、`c := "hello"`。注意它没有用赋值操作符 `=`，而是短变量声明专用的 `:=`，一个符号同时完成"声明新变量"与"赋初值"两件事。类型确定原理与糖一相同：由编译器根据右侧初值自动推导。短声明同样支持一次声明多个变量，形式更简洁：`a, b, c := 12, 'A', "hello"`。规范把它定义为带初值表达式、省略类型的常规变量声明的简写（$GOROOT/doc/go_spec.html:2867，文法在 2863 行）。两颗糖逐级省掉的都只是显式类型信息，声明向编译器提供内存边界的本质没有变。但短声明并非处处可用，哪些变量能用、哪些不能用，取决于它属于下面哪一类。〔TB10 p6-7〕

**两类变量：选择声明形式的坐标系**。Go 的变量分两类：包级变量（package variable）在包级别可见，声明在函数体外，若是导出变量（大写字母开头）还可视为全局变量；局部变量（local variable）在函数或方法体内声明，仅在函数或方法体内可见。所有变量都逃不开这两类，前面学过的几种声明形式该用哪一种，正是围绕这两类分别展开的。〔TB10 p7〕

**包级变量：只能 var，不能用 `:=`**。结论：包级变量只能使用带 var 关键字的变量声明形式，不能使用短变量声明。在函数体外写 `b := 12` 编译报 non-declaration statement outside function body（go1.26.4 实测）；规范也写明短变量声明只能出现在函数内（$GOROOT/doc/go_spec.html:2901）。`:=` 本质上是语句，而包级位置只放声明。形式细节上仍有灵活度，分类的角度是"声明时是否延迟初始化"。第一类，声明并同时显式初始化：标准库惯用省略类型信息的糖，如 $GOROOT/src/io/io.go 第 29 行 `var ErrShortWrite = errors.New("short write")`、第 35 行 `var ErrShortBuffer = errors.New("short buffer")`、第 44 行 `var EOF = errors.New("EOF")`，编译器按右侧结果值的类型（及其默认类型）确定左侧变量类型。第二类，声明但延迟初始化：只能用通用形式，如 `var a int32`、`var f float64`，未显式初始化时变量拥有零值（自定义类型建议保证零值可用）。〔TB10 p7-9〕

**显式指定类型时：推荐转型写法，统一 var 块形态**。要声明的包级变量不接受默认类型时有两种等价写法：`var b int32 = 17`（通用形式）与 `var b = int32(17)`（糖加转型，同类的还有 `var f = float32(3.14)`）。Go 更推荐后者，理由是声明一致性：它把"接受默认类型"（`var a = 13`）和"显式指定类型"（`var b = int32(17)`）统一为同一种形态，放进同一个 var 块时最明显，推荐：

```go
var (
	a = 13
	b = int32(17)
	f = float32(3.14)
)
```

而不是每行形态不一的：

```go
var (
	a = 13
	b int32 = 17
	f float32 = 3.14
)
```

设计取舍是牺牲一点点显式性，换取声明块内声明形式的统一。〔TB10 p8-9〕

**声明聚类：同类声明放进同一个 var 块**。既然语法允许把多条声明聚合进一个 var 块，接下来的问题就是按什么原则分块。原文的做法叫"声明聚类"：通常把同一类的声明放在一个 var 块，不同类的放不同的 var 块；具体到初始化方式，把延迟初始化的声明放一个块，把声明且显式初始化的变量放另一个块，声明聚类可以提升代码可读性。原书举的是 2021 年 $GOROOT/src/net/net.go 里的两段包级声明，一段是延迟初始化的聚类，一段是显式初始化的聚类：

```go
// 2021 年版 $GOROOT/src/net/net.go
var (
	netGo  bool
	netCgo bool
)

var (
	aLongTimeAgo = time.Unix(1, 0)
	noDeadline   = time.Time{}
	noCancel     = (chan struct{})(nil)
)
```

到了现行源码（go1.27），这两组的下落不同。netGo/netCgo 已不再是包级 var 块，而是 net/conf.go 第 52-53 行 type conf 结构体里相邻的两个 bool 字段。aLongTimeAgo 一组仍是 net.go 第 524-533 行的包级 var 块，块内注释写明 aLongTimeAgo 用于立即取消拨号。noDeadline/noCancel 只是给参数太多的函数提供的零值，为可读性服务。

现行 net 包里同用途聚类的例子仍然好找：conf.go 第 72-75 行的 confOnce/confVal 一块（前者用 sync.Once 守护后者的初始化），dnsclient_unix.go 第 42 行开始的 var 块里聚了一串 err 前缀的 DNS 错误变量。〔TB10 p9-10〕

**局部变量：约束正好反过来**。和包级变量相比，局部变量多出一种短变量声明形式，它也是局部变量采用最多的声明形式。分类的角度不变，仍是"声明时是否延迟初始化"。延迟初始化的局部变量只能用通用形式 `var err error`：省略类型的声明与短变量声明这两种糖都要求声明的同时赋初值，都不支持延迟初始化，这类局部变量和包级变量一样只剩通用形式可用。声明且显式初始化的，建议用短变量声明：接受默认类型就直接 `a := 17`、`f := 3.14`、`s := "hello, gopher!"`；不接受默认类型时，仍在 `:=` 右侧做一次显式转型，保持声明形式的一致性：`a := int32(17)`、`f := float32(3.14)`、`s := []byte("hello, gopher!")`。〔TB10 p10-11〕

**分支控制融合：把声明写进 if/for 头部**。分支控制是短变量声明应用得最广泛的场景。写 Go 代码时，很少单独声明用于分支控制的变量，而是把声明与 if、for 融合在一起，即在控制语句头部直接声明只在控制块内使用的变量。范本是 strings 包的 LastIndexAny（摘自本机基线 go1.26.4 源码 src/strings/strings.go 第 250-252 行；2021 年原书同段一致，go1.27.0 中外层守卫换成 `shouldUseASCIISet(len(s))`、代码漂移到 233-242 行，if 头部短声明的惯用法不变）：

```go
if len(s) > 8 {
	if as, isASCII := makeASCIISet(chars); isASCII {
		for i := len(s) - 1; i >= 0; i-- {
			if as.contains(s[i]) {
				return i
			}
		}
		return -1
	}
}
```

`as` 和 `isASCII` 是在 if 条件位置用短变量声明引出来的，原书作者注就标在这一行：它们是 if 代码块里要用的变量，出了这个块便不可见。块内的 `for i := len(s) - 1; i >= 0; i--` 同样把循环变量写进了 for 头部；2021 年版本的回退路径里还有两处循环内短声明，`r, size := utf8.DecodeLastRuneInString(s[:i])` 和作者注指向的 `for _, c := range chars`。这种融合写法体现的正是就近原则，让变量的作用域最小化。〔TB10 p11-12〕

**局部 var 块：遇到适合聚类的场景不要犹豫**。良好的函数设计讲究单一职责，函数/方法规模都不大，很少需要用 var 块来聚类声明局部变量；但遇到适合聚类的场景，应该毫不犹豫地用 var 声明块声明多于一个的局部变量。范本是 net 包的 resolveAddrList（2021 年原书为 $GOROOT/src/net/dial.go，go1.27 源码中方法在第 338 行起，局部 var 块在 361-366 行）：

```go
var (
	tcp      *TCPAddr
	udp      *UDPAddr
	ip       *IPAddr
	wildcard bool
)
```

四个变量同属"地址过滤"这一件事，聚在一块一目了然。它们都是延迟初始化的：声明时只是各自类型的零值，块后的 type switch 才按 hint 参数的动态类型给其中一个赋值并计算 wildcard（hint 是 `*TCPAddr` 就赋 tcp，是 `*UDPAddr` 就赋 udp，是 `*IPAddr` 就赋 ip；switch 在 dial.go 第 367-377 行），随后在 dial.go 第 378-395 行的过滤循环里，这些值用于剔除网络类型或地址族不匹配的地址（教学推导：hint 是接口类型，哪个变量被赋值要等运行期类型分派才知道，声明处给不出初值，var 块先声明零值正合适）。〔TB10 p12-13〕

**就近原则：声明靠近首次使用处**。尽可能在靠近第一次使用变量的位置声明这个变量，这就是就近原则，它实际上是对变量作用域最小化的一种实现手段。因此"包级变量是否应全部集中放在源文件头部"不能一概而论，按使用模式选：一个包级变量若在整个包中仅被某个方法使用，就声明在紧邻该方法的地方，标准库实例是 net/http/request.go 第 442 行的 `var ErrNoCookie = errors.New("http: named cookie not present")`，它紧邻第 448 行起的 Cookie 方法，方法内 450、455 两处返回它（现行代码比 2021 年原文多了 `name == ""` 的前置分支，但"错误变量贴着唯一使用它的方法"的布局没变）；若包级变量在包内部被多处使用，放在源文件头部声明更合适。〔TB10 p10〕

**类型为什么写在变量名后面**。这不是标新立异，官方博客 Declaration Syntax 给出的解释是：相比 C，复杂声明（函数指针等）从左往右就能读顺，不用由里向外拆；官方中文版见 blog.go-zh.org/gos-declaration-syntax，英文原版见 go.dev/blog/declaration-syntax。留言区里作者还用自己的经历佐证了这个解释：他以前是 C 程序员，读懂那些复杂函数原型颇为费力，换 Go 之后，再未被这类问题困扰过。〔TB10 p15-17〕

**类型声明与效率无关**。有读者问，"静态语言明确声明类型"会在编译阶段或运行阶段提高效率吗？作者的回答分两层：其一，类型声明与效率无关，它是静态语言的机制所要求的；其二，静态语言运行效率原本就比动态语言高，因为它已经编译为机器码，无需开销较大的解释过程就可以运行，效率差异来自"编译为机器码"这一执行方式，而不是"声明类型"这个动作。〔TB10 p17〕

### TB11 五层隐式代码块

- 代码块分显式和隐式,隐式共五层,按范围从大到小:宇宙块、包块、文件块、if/for/switch 自身的隐式块、switch/select 每个 case 子句各成一块。控制语句的隐式块在它显式大括号之外,所以 switch 头部短声明的变量比 case 里看到的更外层。〔TB11 p3-4〕
- 宇宙块住着预定义标识符(true、len、new、iota 等),它们不是关键字,内层同名声明就能遮蔽;文件块里最常见的标识符是导入的包名,同包两个源文件都要用包 B,就各自 import 一遍。〔TB11 p4-6〕
- 接收器、参数、命名返回值没被大括号包裹,但作用域是整个函数体块,不是更小。〔TB11 p6-7〕
- if/else if 链的隐式块层层嵌套，条件里声明的变量在后续分支中可见：`if a := 1; false {} else if b := 2; false {} else { println(a, b) }`。〔TB11 p7-8〕〔TB11 p10〕
- 检测只能兜底:go vet 从 1.14 起默认不含遮蔽检查,要单独装 shadow 插件(`go install golang.org/x/tools/go/analysis/passes/shadow/cmd/shadow@latest`)再 `go vet -vettool=$(which shadow) -strict`;课件里的三连遮蔽案例它只报出 err 一处,不能全信。〔TB11 p10-11〕
- 包块里的标识符是包顶层声明的常量、类型、变量、函数(不含方法);跨包只能用导出标识符,条件有二:声明于包块(或字段名/方法名)且首字母大写,缺一不可。〔TB11 p5〕
- 短变量声明撞上控制语句是遮蔽高发区,肉眼不易识别,这正是 shadow 工具存在的理由。〔TB11 p10〕
- 同代码块里重名是"重声明",语法直接禁止;不同代码块里同名是"重名",各自独立,内层的新变量遮住外层的。两个词不是一回事,读报错信息时别混。〔TB11 p13〕
- 老课件里 `type new int` 加赋值的写法在 Go 1.17 起已经编译报错(cannot use new value as type int),要遮蔽预定义 new 得写成别名 `type new = int`;翻老教程遇到这段代码要知道它过时了。〔TB11 p13〕

### TB12 数值类型的底层细节

先建立最底层的认知：Go 的类型分三类，基本数据类型（数值、字符串、布尔）、复合数据类型（数组、切片、map、结构体等）、接口类型。〔TB12 p1-2〕其中数值类型又分平台无关的和平台相关的：平台无关的整型是 `int8`/`int16`/`int32`/`int64` 与对应的 `uint8`/`uint16`/`uint32`/`uint64`，它们在任何 CPU 和操作系统上长度都一样〔TB12 p2〕；平台相关的是 `int`、`uint`、`uintptr` 三个，它们的长度会根据运行平台的改变而改变。〔TB12 p4〕

平台相关对写代码意味着什么？原文特别叮嘱：因为这三个类型的长度是平台相关的，**编写有移植性要求的代码时，千万不要强依赖这些类型的长度**。〔TB12 p4〕若想当然认为 `int` 在哪都是 8 字节，按这个假设去算内存布局或设计文件格式，代码挪到别的平台就可能出错（教学推导：原文只给告诫，没有展开具体事故场景）。真需要知道它们在目标平台上的长度时不要猜，通过 `unsafe` 包提供的 `Sizeof` 函数获取（原文散文把它写作 “SizeOf”，示例代码和标准库里的真名都是 `unsafe.Sizeof`）。原文以 x86-64 平台为例，测得三者长度均为 8：〔TB12 p4-5〕

```go
var a, b = int(5), uint(6)
var p uintptr = 0x12345678
fmt.Println("signed integer a's length is", unsafe.Sizeof(a))   // 8
fmt.Println("unsigned integer b's length is", unsafe.Sizeof(b)) // 8
fmt.Println("uintptr's length is", unsafe.Sizeof(p))            // 8
```

本机 go1.26.4 实测三行都打出 8，与原文的 x86-64 结论一致；长度随平台变，换到别的平台就未必是这个数。反过来，如果确实需要固定宽度，直接选平台无关的 `int32`、`int64` 这类类型，长度就不会随平台漂移。

类型之间要求“一模一样”，没有隐式转换，这是 01 节“显式”那条的延伸。更隐蔽的问题是**整型溢出**。无论哪种整型都有取值范围，也就是它可以表示的值边界；整型因为参与运算导致结果超出值边界，就发生了溢出。溢出不报编译错误、也不 panic：整型表示不了“溢出后的那个结果”，变量的值依然会落到它的取值范围内，只是结果与预期不符，程序逻辑就此悄悄出错。〔TB12 p5〕有符号、无符号各来一例：

```go
var s int8 = 127
s += 1 // 预期 128，实际 -128
fmt.Println(s)

var u uint8 = 1
u -= 2 // 预期 -1，实际 255
fmt.Println(u)
```

`s` 是 `int8`，取值范围 -128 到 127：加 1 的数学结果 128 越过了上边界，落回范围内最小的 -128。为什么恰好是 -128？用本章末 TB12 小节讲的补码编码看一眼就清楚：127 的 8 个比特是 0111 1111，加 1 后变成 1000 0000，按补码解释就是 -128。`u` 是 `uint8`，范围 0 到 255：1 减 2 的数学结果 -1 越过了下边界，回绕到最大值 255（0000 0001 减 0000 0010 得 1111 1111，按无符号解释就是 255）。本机 go1.26.4 实测，两句的输出正是 -128 和 255。

溢出最容易发生在循环语句的结束条件判断中，因为这是整型变量最常出场的地方；无符号、有符号整型都有这个问题。所以原文的叮嘱有两点：要十分小心地选择参与循环结束判断的整型变量类型，以及与之比较的边界值。〔TB12 p5〕最经典的事故现场，是拿无符号类型向下数到 0（教学示例，按 p5 的结论构造，能编译但永远停不下来）：

```go
for i := uint8(3); i >= 0; i-- {
	fmt.Println(i) // i 数到 0 后回绕成 255，循环永不结束
}
```

`i` 从 3 数到 0 都正常；再减 1 时 0 回绕成 255，而 `i >= 0` 对无符号数永远成立，循环永不结束。把循环变量改成有符号的 `int`，或把条件写成 `i > 0` 再单独处理 0 的那一轮，循环才能正常退出。所以选整型要看清取值范围，别随手用 `int8`、`uint8` 这类窄类型做计数或循环条件。

数值类型还有一族：复数。数学上，形如 z=a+bi（a、b 均为实数，a 称为实部，b 称为虚部）的数称为复数。对比一下出身：C 语言直到采用 C99 标准，才在 complex.h 中引入对复数类型的支持，Go 则原生支持复数类型。不过和整型、浮点型相比，复数类型在 Go 中的应用更为局限和小众，主要用于矢量计算这类专业领域的计算，原文的态度是“简单了解一下就可以”。〔TB12 p13〕Go 提供两种复数类型：`complex64` 的实部与虚部都是 `float32` 类型，`complex128` 的实部与虚部都是 `float64` 类型；没有显式赋予类型的复数，默认类型为 `complex128`〔TB12 p13〕。本章末“TB10 变量声明的选择规则”小节里 `var c = 1 + 2i` 用 `%T` 打出 complex128，正是这条默认类型规则的实测。

操作复数有三种方法〔TB12 p13-14〕。第一种，用复数字面值直接初始化变量：

```go
var c = 5 + 6i
var d = 0o123 + .12345E+5i // 83+12345i
```

第二种，用 Go 提供的 `complex` 函数构造，原文注明这种方式方便创建 complex128 类型的值：

```go
var c = complex(5, 6)              // 5 + 6i
var d = complex(0o123, .12345E+5) // 83+12345i
```

第三种，用预定义函数 `real` 和 `imag` 获取复数的实部与虚部，返回值为浮点类型：

```go
var c = complex(5, 6) // 5 + 6i
r := real(c)          // 5.000000
i := imag(c)          // 6.000000
```

（第三段代码的注释沿用原文写法，是按 %f 风格写出的值；`real(c)`、`imag(c)` 的返回类型是 float64，本机实测 5+6i 的实部、虚部就是 5 和 6。）也正因为复数的实部与虚部都是浮点类型，复数的格式化输出可以直接套用浮点型的方法〔TB12 p14〕：直接 `Println` 会得到 `(1+2i)` 这样的形式（本机实测 `complex(1.0, 2.0)` 输出 `(1+2i)`），要控制小数位数，就对 `real`/`imag` 的结果用 `%f`、`%g` 这些浮点动词（教学推导：原文只说“直接参考前面浮点的讲解”，具体动词组合自行试）。

- 有符号与无符号的本质差别是最高位是否解释为符号位;Go 整型用补码编码,负数是"原码逐位取反加 1",不能把最高位简单当负号读。同一比特序列按 uint8 读是 129,按 int8 读是 -127。〔TB12 p2-3〕
- Go 1.13 起字面值支持二进制 `0b10000001`、新八进制 `0o700` 和数字分隔符 `5_3_7`(要求 go.mod 的 go 行不低于 1.13);按进制输出用 %b、%o、%O、%x、%X。〔TB12 p6-7〕
- 浮点只有 float32 和 float64,没有 float,全是平台无关的。内存表示按 IEEE 754 分符号位、阶码、尾数,float32 是 1+8+23 位,float64 是 1+11+52 位,阶码 = 指数 + 偏移值(float32 偏移 127)。〔TB12 p7-10〕
- float32 尾数只有 23 位,2^24=16777216 能精确表示,下一个可表示的数是 2^24+2,16777217.0 会被舍回去,所以 `f1 == f2` 是 true。日常用 float64;金钱计算用最小货币单位(分)的整数,0.1+0.2 不等于 0.3 同源。〔TB12 p11〕〔TB12 p18-20〕
- 浮点字面值有十进制直白形式(.15、82.,前导 0 和末尾 0 都可省)和科学计数法两种,科学计数法还分十进制底数(1.5e-3)与十六进制底数(0x2p4);写出来有时都猜不到真实值。〔TB12 p11-13〕
- 数值类型小结:`type MyInt = int32` 别名与原类型完全等价可直接互赋,主要场景是重构;`type MyInt int32` 是新类型,数值性质相同但不能直接混算。〔TB12 p14-15〕〔TB12 p15〕
- 自定义数值类型的两个动机:一是给原生类型建立更高级的抽象,二是原生类型(int、float64 这些)不能附加方法,想要方法只能先定义新类型。〔TB12 p19〕
- 十进制浮点手工转二进制是四步:整数小数分别转、小数点归一到 1.xxx、指数加偏移值算阶码、拼符号阶码尾数;日常只读不写,知道流程即可。〔TB12 p9-10〕

### TB13 字符串操作的隐性开销

- 不可变换来的好处:字符串可以随便跨 goroutine 共享,不用加锁;相同的字符串值编译器只分配一块存储。〔TB13 p3-4〕
- 代价是所有"修改"类操作都要分配新内存:string 与 []byte、[]rune 的每次双向转型都拷贝,热路径上反复转是隐性开销。〔TB13 p15-16〕
- 拼接用 +/+= 体验最好但不是性能最优,大量拼接用 strings.Builder 或 strings.Join;留言区共识是 fmt.Sprintf 通常最差,以自己的 benchmark 为准。〔TB13 p14-17〕
- 比较是逐字节字典序:长度不同直接判不同,长度相同先比数据指针是否同一块底层存储,再比内容。Go 的 == 比内容,Java 的 == 比对象同一性,拿 Java 语义套 Go 会踩坑。〔TB13 p14-15〕〔TB13 p18-20〕
- 想窥视底层结构,老材料用 reflect.StringHeader{Data, Len} 加 unsafe.Pointer;该结构体自 Go 1.20 起弃用,现行写法是 unsafe.StringData(切片配 unsafe.SliceData)。〔TB13 p10-12〕
- string 的价值就在"统一抽象":字符串常量、变量、字面值的类型都归一为 string,编译器替你做类型校验、防缓冲区溢出、求长 O(1),C 手搓字符数组的五类缺陷一次清掉。〔TB13 p1-2〕
- 字符串有两种迭代结果:常规 `for i := 0; i < len(s); i++` 是字节视角,逐个吐 UTF-8 字节;`for range` 是字符视角,每轮给码点值和该字符起始字节偏移(0/3/6);数字符个数用 utf8.RuneCountInString。〔TB13 p12-14〕
- `rune` 在 builtin 里就是 `type rune = int32` 的别名定义,一个 rune 实例即一个 Unicode 字符;字符字面值还能写成 '\u4e2d'、'\x27'、'\047' 多种形式,彼此等价。〔TB13 p6-7〕

### TB14 iota 的技巧与边界

- 对比 C 就懂 Go 常量:宏常量类型不安全、调试时无法按名查看;C 的 const 本质还是变量,连数组声明长度都当不了。Go 常量编译期求值还有个收益:常量表达式里的整数除零、字符串索引越界,编译期就报错。〔TB14 p3〕〔TB14 p12〕
- C 枚举"首常量 0、后续加 1"被拆成两个可独立组合的特性:隐式重复上一行表达式,加 iota 行偏移指示器。位标志 `1 << iota`、任意起始值、跳值都靠这两个组合出来。〔TB14 p7-9〕
- 略值技巧:首行写 `_ = iota` 让枚举从 1 开始(syscall 包的 IPV6_V6ONLY 就是这么写的);中段用 `_` 占位跳过某个值。〔TB14 p9-10〕
- iota 有边界:syscall 编号、错误码、颜色 rgba 值这类"值即标准"的常量用显式字面值,方便对照文档;API 发布后不能往枚举中部插入,插入会改掉已发布的值,只能追加。〔TB14 p12-15〕

### TB15 数组与切片的补充

- 数组类型的两个属性是元素类型和长度,声明 `var arr [N]T` 里 N 必须是整型字面值或常量表达式,编译期就要定死。〔TB15 p2〕
- 数组变量在 C 里会退化成指向首元素的指针,Go 里变量代表整个数组,迭代与传参都是纯值拷贝,开销随长度增长;这是切片被引入的直接原因。〔TB15 p6-7〕
- 数组占一整块连续内存,总大小等于各元素大小之和;下标越界或负数,编译器直接报错。〔TB15 p3-5〕
- make([]byte, 6, 10) 建切片时第二参是 len、第三参是 cap,省略 cap 时 cap 等于 len。〔TB15 p9〕
- 数组初始化有两个省事写法:`[...]int{21, 22, 23}` 让编译器数长度;稀疏数组用下标赋值 `[...]int{99: 39}`,得到 [100]int,其余元素是零值。〔TB15 p4〕
- 完整的切片化语法是三索引 `arr[low:high:max]`:len 是 high-low,cap 是 max-low,省略 max 时默认取到数组末尾。正文里 `base[1:3]` 的 cap 是 3,就是 max 省略后的结果。〔TB15 p9-10〕
- nil 切片和空切片不是一回事:`var s1 []int` 是 nil(s1 == nil 为 true),`s2 := []int{}` 已初始化(== nil 为 false),JSON 序列化等场景两者行为有差异。〔TB15 p15-17〕
- 大多数场合用切片替代数组:传递开销恒定,还带下标访问、边界校验、动态扩容;Go 指针不支持算术运算,数组指针给不了这些。〔TB15 p14-15〕
- 一个底层数组可以被多个切片同时"开窗",任一切片改元素,其他切片立刻可见(`sl2[2] = 14` 后 `sl1[0]` 也是 14,两处指向同一个 arr[3]);基于切片再切片同理。所谓"独立切片"只在各自扩容换数组之后才成立。〔TB15 p11〕
- 扩容的具体动作:len 追平 cap 时 append 在运行时重新分配底层数组并拷贝旧元素,从 nil 切片逐个 append 的容量轨迹是 1、2、4、4、8(本例 int 元素新容量翻倍),旧数组随后被 GC。翻倍只适用小容量,别把它当语言承诺。〔TB15 p11-13〕
- 解绑是双向的:切片触到容量上限触发扩容后才和原数组脱钩,脱钩前 append 会写回原数组,脱钩后改切片元素原数组也不再跟着变。正文 base/sub 那段代码就是这两步的完整演示。〔TB15 p13-14〕

### TB16 map 的几条硬约束

- delete(m, key) 是唯一删键方法,键不存在也不报错;map 不能调用 cap,这是与切片的一个不同。〔TB16 p7〕〔TB16 p9〕
- 语法层的 map 操作都会被编译器重写成运行时调用:make 到 runtime.makemap、m[k]=v 到 mapassign、v := m[k] 到 mapaccess1、v, ok := m[k] 到 mapaccess2、delete 到 mapdelete。〔TB16 p13〕
- `&m[key]` 编译期就报 cannot take the address of m[key]:扩容会搬动 value,持有地址不安全,这条禁令由编译器强制。〔TB16 p20〕
- 扩容的代价被摊平:元素数超过负载因子上限或溢出桶过多时触发扩容,搬迁不是一次做完,而是挂在后续每次 assign/delete 上渐进进行,扩容期间新旧数组并存,查找要双查。〔TB16 p18〕

### TB17 结构体的初始化与填充

- 结构体类型字面值 `type T struct { Field1 T1; ... FieldN Tn }`,字段名在一个结构体内必须唯一。〔TB17 p5-6〕
- 按字段顺序写复合字面值有三个问题:字段增删要同步改初始化代码、字段多时容易错位、含非导出字段直接编译错;go vet 的 composites 规则专门警告这种写法,官方不推荐。〔TB17 p12-13〕
- 非导出字段零值不可用(如 time.Timer 内部的 runtimeTimer)或初始化逻辑复杂时,给类型配专用构造函数 `func NewT(...) *T`,把复杂逻辑和未导出字段都收进函数内部,标准库大量用这个模式。〔TB17 p14-15〕
- 对齐分两个阶段:先逐字段对齐(int64 必须落在 8 的倍数地址),再把总大小圆整到对齐系数的倍数。尾部也要补是为了数组:数组元素连续存放,T[1] 的地址等于 T[0] 地址加 sizeof(T),不圆整则后续元素全错位。早期 Sparc 遇到未对齐地址直接段错误,x86-64 不崩但存取变慢。〔TB17 p17-20〕
- 嵌入字段只写类型不写名:Book 里写一个 Person,既能 book.Person.Phone 也能用语法糖 book.Phone,转发机制在 04 节展开。〔TB17 p7-8〕
- 想进一步控制布局可以主动填充:用空标识符 `_` 当字段名占位,runtime 的 mstats 里就有 `_ [1 - _NumSizeClasses%2]uint32`,为的是 32 位平台上把后面的字段对齐到 64bit,好做原子操作。〔TB17 p20-21〕
