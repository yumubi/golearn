# 17 数据迁移与双写：不停机换库的套路

> 详细程度：深入 · 约 35 分钟
> 材料：W11-1、W11-2、W18-2 · 旧长版：无整章对应（`notes/p11-sqlc-goose.md` 讲的是 schema 迁移，不是本节的数据迁移）
> 前置：04 接口与组合、12 数据库

## 这一节要建立的认知

数据迁移最容易误解的地方：它不是"复制得足够快"的问题，而是**数据一直在变**的问题。t1 时刻把两边校平，应用一写，目标库又落后了，永远追不上，像蜗牛悖论。〔W11-1 p9〕

解法分两半：

1. **双写**：让每一次变化同时落到两边，不再依赖"追"。
2. **校验加修复**：双写不可能完美（总有一边偶尔失败），所以要有一个独立程序不断比对、修复，让两边**收敛**到一致。

整个方案的哲学可以一句话概括：**失败了就失败，靠校验修复兜底；用监控保证双写失败只是偶发**。〔W11-2 p13〕

## 和停机迁移比

| | 停机迁移 | 不停机迁移 |
|---|---|---|
| 做法 | 停应用、导出、导入 | 双写加校验，分阶段切流量 |
| 适用 | 中小型或不重要的业务，数据量不大 | 在线业务、数据量大 |
| 代价 | 停机时间随数据量增长 | 方案复杂，要写校验与修复程序 |
| 回滚（推论，资料未写） | 基本没有 | 每一步都能退一步 |

〔W11-1 p6〕〔W11-1 p8〕不停机的两个约束：迁移期间新数据不断产生、老数据不断更新；迁移本身不能给库带来太大压力。再加一类**异构迁移**（表结构不同，或跨库如 MySQL 到 MongoDB），难点在数据转换和完整性校验，主键对不上时只能用唯一索引或外键定位，字段丢弃或有计算字段时只能定制校验逻辑。〔W11-1 p5〕〔W11-1 p32〕

## 一、四个阶段、八个步骤

四个阶段用双写模式命名最清楚：

| 阶段 | 模式 | 读 | 写 | 以谁为准 |
|---|---|---|---|---|
| 一 | `SrcOnly` | 源 | 只写源 | 源 |
| 二 | `SrcFirst` | 源 | 先写源，成功再写目标 | 源 |
| 三 | `DstFirst` | 目标 | 先写目标，成功再写源 | 目标 |
| 四 | `DstOnly` | 目标 | 只写目标 | 目标 |

〔W11-1 p10〕〔W11-2 p5〕展开成八步：建目标表、初始化数据、（可选）全量校验修复、开双写（读源）、增量校验修复一段时间、切换双写顺序（读目标）、继续增量校验、切成只写目标表。〔W11-1 p11〕

**回滚怎么设计**（推论，资料未写）：每个阶段切换前两边的数据都是完整的，所以任何一步都可以退回上一步。但切到 `DstOnly` 之后源库不再更新，就没有退路了，因此这一步之前要在 `DstFirst` 停留足够久，让增量校验持续无差异。以上是我对流程的推导，资料没有单独列回滚策略。

注意**读流量要和写模式一起调度**，资料强调双写方案要一并考虑读流量。〔W11-2 p5〕举个反例（推论）：双写阶段以源为准，读流量却先切到目标表，会读到还没追上的旧数据。

## 二、双写怎么实现

三种思路：

1. **DAO 层双写**：每个方法里 `switch` 模式。直观，缺陷是侵入式改动多、容易遗漏。〔W11-2 p6-7〕
2. **ORM 的 Callback**：不可行。Hook 要一个个定义，且回调拿到的 DB 是固定的，没法动态切换模式。〔W11-2 p8〕
3. **连接池层双写**：GORM 底层有一个与数据库打交道的接口（`Prepare`/`Exec`/`Query`/`QueryRow`），实现一个双写版本，按模式分发。事务也能覆盖：开事务时按模式开一个或两个。〔W11-2 p9-12〕提交时先提交权威侧，是推论，资料未写。

第三种对业务零侵入，是通用方案。下面用内存版演示模式切换和失败语义，`Table` 是内存里的"表"，可以注入写失败：

```go
func (d *DoubleWrite[T]) Put(r T) error {
	first, second := d.Src, d.Dst
	switch Pattern(d.pattern.Load()) {
	case SrcOnly:
		return d.Src.Put(r)
	case DstOnly:
		return d.Dst.Put(r)
	case DstFirst:
		first, second = d.Dst, d.Src
	}
	if err := first.Put(r); err != nil {
		return err // 权威侧失败：整体失败
	}
	if err := second.Put(r); err != nil {
		d.SecondaryFails.Add(1) // 非权威侧失败：记下来，靠校验修复
	}
	return nil
}
```

失败语义有三种情况：源写成功目标失败，等校验修复；源事务开成功、目标事务开失败，回滚源；源提交成功、目标提交失败，因为没有记录语句，无法直接修复，也只能等校验。〔W11-2 p13〕

## 三、校验：正向、反向、泛型 Validator

校验程序要回答"两边一致吗"。不要给每张表写一套 DAO 加比较，表多了要命。资料的方案是泛型：查询通用，**比较逻辑交给实体自己实现**。〔W11-1 p24〕

```go
type Entity[T any] interface {
	ID() int64
	Utime() int64
	CompareTo(T) bool
}

type Validator[T Entity[T]] struct{ Base, Target *Table[T] }
```

`ID` 是校验体系的围绕点，`CompareTo` 决定字段怎么比、忽略哪些列、有没有业务比较；资料里实体还需要提供 `TableName` 和 `Columns` 用于修复。〔W11-1 p25-26〕`Base` 与 `Target` 加方向，就能同时支持"以源为准"和"以目标为准"两个阶段。

**正向校验**：以 `Base` 按 id 排序分批查，逐条去 `Target` 找，查不到是 `target_missing`，字段不等是 `neq`。〔W11-1 p27-28〕

**反向校验**：以源为准的阶段理论上不会出现"源没有而目标有"，除非硬删除（软删除是 UPDATE，没问题）。要发现硬删除就得反向：取一批目标表的 id，去源表找，差集就是已经被删的，事件类型 `base_missing`。〔W11-1 p29-31〕

**修复**：三种事件三种动作（插入、用源覆盖、删目标多出来的）。更简单的做法是**一版逻辑覆盖三种**：不看事件类型，直接查 `Base` 最新值，找到就 upsert 到目标，没找到就删目标。〔W11-1 p37〕〔W11-1 p39〕

```go
func (v *Validator[T]) Fix(e Event) {
	if b, ok := v.Base.Get(e.ID); ok {
		_ = v.Target.Put(b)
		return
	}
	v.Target.Delete(e.ID)
}
```

为什么必须是 upsert：从校验到修复之间数据会被改，特别是双写阶段目标表也在被业务写，校验时目标没有这条，修复时可能已经有了。upsert 幂等，吸收了这种并发。〔W11-1 p40〕

把三步串起来跑一遍（5 行源数据，目标表为空）：

```text
1 全量校验: [1:target_missing 2:target_missing 3:target_missing 4:target_missing 5:target_missing]
  修复后: []
2 双写失败次数: 1
  增量校验: [3:neq]
  修复后: []
3 反向校验: [5:base_missing]
  修复后: []
  DstFirst 写 4 号, src/dst: u4-dst u4-dst
```

第 2 步里给目标库注入了"写 3 号失败"，`SrcFirst` 模式下业务仍然成功，`SecondaryFails` 记了一次，增量校验只扫 `utime >= 150` 的行，精准发现 `3:neq` 并修复。第 3 步在源表硬删了 5 号，只有反向校验能看到。

## 四、增量怎么知道"改了什么"

全量校验只在开双写前跑一次（可选），双写期间要持续做**增量校验**，只看新改的数据，防止双写出问题。〔W11-2 p15〕怎么知道哪些行变了：

1. **在连接池层拦截**：很难。`UPDATE ... WHERE` 影响了哪些行未知，理论上要把 SQL 语法树转成 `SELECT`。〔W11-2 p16-18〕
2. **`utime` 轮询**：简单，校验时加 `WHERE utime >= ?`。要求表规范有更新时间列，且 `utime` 要有独立索引，否则查询特别慢。〔W11-2 p18〕
3. **binlog / CDC**：实时。Canal 伪装成 MySQL 从库消费 binlog，转成消息发到 Kafka。〔W18-2 p8〕〔W18-2 p12〕binlog 三种格式里推荐 Row（最详细，量大）。〔W18-2 p9〕

用 Canal 做增量校验时，消费者拿到消息不管是增删改，只取 id 就去双查再比较。几个必须知道的细节：

- 同一个 id 的消息要进同一分区才保序，配置按 id 哈希。〔W18-2 p21〕
- 删除消息里，被删的数据在 `data` 字段，`old` 为 null，和直觉相反。〔W18-2 p17〕
- **切换窗口漏检**：以源为准期间产生的 binlog，到达 Canal 时可能已经切到以目标为准，消费者此时忽略源库的 binlog，这批不一致就没人发现，切换后要手动补校验窗口期的数据。〔W18-2 p26〕

## 五、并发与一致性窗口

修复覆盖了业务的并发写怎么办：修复读到旧值，把双写刚写入的新值盖掉。资料的态度是**不用办**，等下一次更新，或者再跑一轮校验就收敛了。〔W11-2 p21〕全量和增量校验可以并行；并发问题同样靠"反复校验"收敛，这是最终一致，不是强一致。〔W11-2 p22〕

主从库带来的差别：校验最新数据要读主库（从库有延迟）；主库负载高时，可以先读从库，不一致再读主库复核；修复只能走主库。〔W11-2 p32〕

## 六、别把线上库打垮

- **程序侧**：按表一个 goroutine；大表再按 id 尾号分片（10 个 goroutine 各负责 0 到 9 尾号）。瓶颈通常在数据库，不在程序。〔W11-2 p30〕
- **量化**：数十亿条的逻辑表一天校完，意味着 QPS 过万，答案是尽量高并发、同时保护源和目标库。〔W11-1 p20〕
- **数据库侧**：低峰期多开、高峰期停；专用从库代价太高，一般不用。〔W11-2 p31〕
- **修复走 Kafka**：解耦削峰，控制消费速率就等于控制目标表写入速率。〔W11-1 p21-22〕
- 初始化目标表时的并发手段：按表拆分或按 ID 取模拆分，并发度要控制，别影响线上。〔W11-1 p16〕

## 常见坑

1. **只做全量复制不做双写**：复制期间的变化永远追不上。
2. **双写失败就让业务失败**：非权威侧失败应记录并告警，权威侧失败才失败。否则迁移本身变成线上故障源。
3. **校验用 offset 分页**：数据变动时漏检或重复；改成 id 游标更稳。（资料作业的思考方向，待核）
4. **`utime` 没建索引**：增量扫描拖垮数据库。
5. **只写正向校验**：硬删除永远发现不了。
6. **切换窗口没补校验**：Canal 方案里窗口期的差异会永远留着。
7. **没有演练失败注入**：双写提交失败那条路径，不测就等于没写。
