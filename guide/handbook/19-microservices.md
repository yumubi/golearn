# 19 微服务拆分与治理：怎么拆、怎么切流量、拆完多了什么

> 详细程度：深入 · 约 35 分钟
> 材料：W10-1、W10-2、W10-3、W14-1、W13-2 · 旧长版：`notes/p10-grpc.md`（gRPC 基础与拦截器）
> 前置：04 接口与组合、16 稳定性

## 这一节要建立的认知

微服务是**分而治之**的一种实现，目的是降复杂度：把系统拆到一个人能完整理解一个模块，模块之间只通过 API 耦合，不必知道彼此的内部细节。资料给了一个直观的推导：两个系统合并后的复杂度大于两者之和，多出来的是它们之间的交互成本。〔W10-1 p5-6〕

同时要清楚它只是架构之一，不是目标。拆分换来的是：独立开发测试部署扩容、API 向后兼容后可以独立演进、运维的基本单位变成实例（单体 16G 对拆出的 4G）、结构贴近组织架构以减少沟通损耗。〔W10-1 p7〕代价是：RPC、注册发现、负载均衡、路由、故障处理（检测、处理、恢复，加熔断限流降级）、超时控制、优雅退出，这一整套都要自己面对。〔W10-1 p8〕

所以判断"该不该拆"的标准不是技术，是**一个人能不能掌握一个服务的全部细节**。作者自己的标准就是拆到这个程度；粒度也要考虑团队组织，两个披萨能喂饱的团队大约 9 人。〔W10-2 p4〕

## 和你已知的选择相比

| 问题 | 选项一 | 选项二 |
|---|---|---|
| 服务间协议 | HTTP：运维简单、组件少、门槛低、兼容好，适合异构 | RPC：运维复杂、组件多、要求高，协议不合适就无法异构通信 |
| REST 的位置 | REST 是风格，微服务是架构，两者没特别大关系 | 可以直接当通信机制，也可以二次封装成 RPC |

〔W10-1 p11-12〕资料的建议是遇事不决选 gRPC：高性能（HTTP/2 双向流、流控、压缩）、跨语言、社区强。〔W10-1 p26〕Go 框架对比：gRPC 生态最好；go-zero 集成 Web 加微服务，底层也是 gRPC；Dubbo-go 能和 Java 的 Dubbo 互通；go-micro 简单易用。选型三个维度：功能性、成熟度、非功能性（性能，中小公司基本不用管）。〔W10-3 p4-5〕

## 一、边界怎么划：DDD 只取够用的几个词

DDD 有八个概念，拆服务时真正有用的是：**限界上下文**，同一个业务模型在不同场景特征不同（销售眼中的产品和售后眼中的产品），它直接描述微服务边界，与组织架构可能重合，黑白地带是难点；〔W10-1 p16〕**聚合体**，聚合根加若干值对象，聚合体之间只能通过 ID 引用，聚合根是修改的唯一入口；〔W10-1 p19〕**领域事件**，多是聚合体数据变化，发到消息队列的消息就是它；〔W10-1 p22〕**仓库**，数据存储的抽象，屏蔽缓存与数据库，业务逻辑尽量放进聚合体，CRUD 项目里 Domain Service 几乎没代码。〔W10-1 p21〕〔W10-1 p23〕

## 二、拆分路线：先模块化，再进程化

不要一上来就拆进程。资料给的路线是四个阶段：混沌（补单测、抽公共工具、用聚合层解循环依赖）、模块化（模块挪到独立仓库、加 CI）、模块依赖化（逐个服务化，加自动部署回滚、MQ、分布式事务、可观测性）、服务化（治理、网关、分库）。〔W10-2 p5〕路线选型上，只先拆一个模块，可以提前验证流程但"开弓没有回头箭"；全部模块按序推进则处处可停但流程问题最后集中爆发。资料选的是先拆一部分。〔W10-2 p6〕

具体到单个模块是**八步**：选定模块、补测试到 80%（业务加异常场景）、代码拆出到新仓库、技术选型、模块改成微服务对外提供、主应用**本地与微服务双调**（开关控制流量，可回滚）、流量逐步调到 100%、删除本地调用。〔W10-2 p7〕

### 选哪个模块先拆

先易后难，三个条件：业务影响力小（崩了无所谓）、最独立（依赖最少）、QPS 低。资料里选了点赞收藏，而用户和帖子不能选（核心依赖），短信是核心依赖，热榜 QPS 高。〔W10-2 p12〕

### 重构的心态与保障

- 重构必然引入 bug，要问"出 bug 了怎么办"而不是"怎么不出 bug"。〔W10-2 p12〕
- 回滚设计：出问题大概率在"拆代码"与"转微服务调用"两步；拆代码仍是本地调用，风险小；转调用引入中间态，微服务调用出问题立刻切回本地。〔W10-2 p8〕
- **补测试是第一步**：不知道全部业务场景时就追求覆盖所有代码，80% 以上才稳妥，集成测试（真实打 DB 和 Redis）的覆盖率比单元测试更重要；但代码全覆盖不等于业务全覆盖，还要人工检查核心路径、梳理业务场景。〔W10-2 p13-14〕
- **重构点先行**：动手前把受影响的文件列全（Web、Service、Domain、Repository、Cache、DAO、`wire.go`、初始化表、事件消费），忌边拆边发现漏了。〔W10-2 p19〕
- 模块化之后不允许依赖原主应用的内部包，所以消费者代码要复制一份而不是共享事件定义。〔W10-2 p22〕

## 三、契约：Protobuf 与 API 管理

gRPC 规定用 IDL 描述接口，落地选 Protobuf：跨语言平台无关，编译生成各语言的客户端和服务端代码。〔W10-1 p27-28〕对契约兼容性最重要的几条规则：

- `message` 字段编号不能冲突〔W10-1 p35〕，而且**删除后不复用**（后一条是 Protobuf 的通行规则，资料没讲，字段下线时用 `reserved` 占住编号）。
- 生成的服务端接口强制组合一个空实现（`mustEmbedUnimplemented...Server`），目的是向后兼容：接口以后加方法不会让老实现编译失败。〔W10-1 p49〕
- `enum` 的 0 值留给 Unknown。〔W10-1 p36-39〕

API 定义放在哪：三种方案：公司级统一 API 仓库（30 人以内推荐，课程采用）、服务内 API 目录、实现仓库和 API 仓库分离（巨型应用）。〔W10-3 p7〕`protoc` 插件难管理、命令行参数长，用 `buf` 配 `buf.gen.yaml` 统一生成。〔W10-3 p10-11〕

服务端实现里有一个值得记住的结构原则：**gRPC、定时任务、HTTP 是同一层，都是"服务对外的表现形式"**。本地服务抽象得好，gRPC 服务端只是组合 `Unimplemented...Server` 加持有原来的 Service，Service 本身零修改。〔W10-3 p12-13〕

## 四、拆分的关键一步：灰度切流量

八步里最危险的是第六步。做法是用适配器和流量调度装饰器，让调用方依赖同一个接口，用阈值加随机数决定走新路径还是老路径：

1. **适配器**：把本地 Service 适配成 gRPC 客户端的形态，让两种实现类型一致（临时代码，拆完就删）。〔W10-3 p23〕
2. **调度装饰器**：持有 `remote`、`local` 两个实现和一个阈值，随机数小于阈值走远程。〔W10-3 p24〕
3. **配置热更**：阈值放在原子变量里，配置变化时更新；解析失败只记日志，不中断。〔W10-3 p25〕

```go
type Switch struct {
	remote, local Interactive
	threshold     atomic.Int32
	rnd           func(n int) int
}

func (s *Switch) Like(ctx context.Context, biz string, id int64) (string, error) {
	if int32(s.rnd(100)) < s.threshold.Load() {
		return s.remote.Like(ctx, biz, id)
	}
	return s.local.Like(ctx, biz, id)
}
```

依次把阈值设为 0、10、50、100、0，各打一万次请求（随机数，数字略有浮动）：

```text
threshold=  0  remote=  0.0%
threshold= 10  remote=  9.8%
threshold= 50  remote= 50.1%
threshold=100  remote=100.0%
threshold=  0  remote=  0.0%
```

通用的灰度思路：**阈值加随机数，或者用业务 ID 的哈希代替随机数**（这样同一用户总是走同一路径）；默认全走老路径，逐步放大，出问题立刻把阈值归零；动态修改要通过配置中心同步到所有节点。〔W10-3 p28〕被问到"怎么保证没引入 bug"，诚实的答案是保证不了，只能说完善的测试显著降低概率，线上再用灰度兜底。〔W10-3 p30〕

## 五、治理三件事怎么协同

拆开之后，调用方面对的是这几件事，它们是联动的，不是孤立的：

- **发现**：知道有哪些实例（注册中心，见 20）。
- **负载**：在实例里选一个（见 20）。
- **容错**：选的实例坏了怎么办（见 16）。

联动的典型例子：客户端从响应里发现服务端触发了熔断或限流，在一段时间内不再选它，等于把 failover 做进负载均衡；资料作业里就是收到这类响应直接把权重调到极低。〔W13-2 p35〕故障处理的通用顺序是预防、检测、处理、恢复，这些都要在拆分后重新落地。〔W14-1 p5〕

链路超时也变成新问题：A 调 B 调 C，整条链路共用一个总预算，下游拿到的是剩余时间。gRPC 自动传播 deadline，服务端 ctx 里已是剩余值。〔W14-2 p19-20〕

## 六、拆完之后，日常工作多了什么

每个服务有自己的 `main`、依赖注入和配置文件，注意工作目录与配置路径要对；〔W10-3 p16-18〕集成测试要从统一目录挪进模块，测试目标从本地实现改为 gRPC 服务端，断言改成 gRPC 返回的错误和 protobuf 响应；〔W10-3 p14-15〕开发环境要求每人起全部依赖不现实，常见形态是单一测试环境、测试加开发、测试加多个开发环境；〔W10-3 p6〕可观测靠拦截器统一接日志、链路追踪和 Prometheus 指标。〔W14-2 p24-26〕`ArticleHandler` 这类直接持有另一个服务客户端的聚合层，不完全符合 DDD 但好用。〔W10-3 p21〕

## 常见坑

1. **一上来就拆进程**：没有模块化、没有测试覆盖，拆完无法回滚。
2. **先拆最核心的模块**：用户、短信、热榜这类被依赖最多或 QPS 最高的模块，应该最后拆。
3. **只想"不出 bug"，没有设计回滚**：双调开关、可归零的阈值是底线。
4. **模块化后仍共享内部包**：导致名义上拆了、实际上互相编译依赖。
5. **protobuf 字段编号复用**：新老版本混跑时数据错位。
6. **用 `enum` 的 0 当成有意义的值**：默认值会被误当成真实选择。
7. **所有治理都靠框架默认值**：默认负载均衡策略可能是 `pick_first`，只用第一个节点，见 20。

## 判断题（先答再看）

1. 双调阶段的写操作（如 `Like`）如果同时落到本地和远程两边会怎样？灰度切流量时怎样保证写路径只有一个权威？
2. 灰度阈值用业务 ID 哈希代替随机数，对缓存命中率和问题排查各有什么影响？
3. 拆分后调用链上每一跳都有重试，一次失败最多会放大成多少次实际调用？（对照 16 节）
4. 服务端实现里，gRPC、HTTP、定时任务为什么是"同一层"？

## 在项目里

`dnsproxi-go` 把传输层和业务分开，是一个小号的"同层多形态"例子：UDP 路径和 TCP 路径（`tcp/server.go` 里的 `Serve`）共用同一个 `handleQuery`，TCP 侧靠 `streamConn` 把连接适配成 `net.PacketConn`。换传输协议不用改业务，就是这一节"本地抽象好，对外形式只是外壳"的缩影。真正的服务拆分演练放在 minifeed 里。
