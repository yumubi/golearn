# 13 缓存、消息队列与幂等：读写放大之后的三件套

> 详细程度：深入 · 约 40 分钟

> 前置：10 分层与依赖注入，12 数据库

## 这一节要建立的认知

数据库扛不住读，就加缓存；扛不住写和耦合，就加队列；缓存和队列一加，**重复和乱序就成了常态**，所以所有写路径最终都要问一句：做两遍会怎样？这三件事是一个整体：

1. **缓存**：用一致性换读性能。关键不在"怎么存"，而在"什么时候失效、失效时谁去回源"。
2. **队列**：用延迟换解耦和削峰。关键在"至少投递一次"带来的重复，和"分区内有序"的边界。
3. **幂等**：前两者的兜底。重复执行必须无害。

## 一、缓存放在 repository 层，业务无感知

引入业务专属的缓存类，而不是让调用方直接碰 Redis：它屏蔽三件事，过期时间、key 结构、序列化协议。缓存集成位置是 repository 层，因为它属于"如何存数据"，service 对它无感知，构造函数多一个依赖就行。〔W04-1 p13〕〔W04-1 p16〕

写入路径要**清缓存**：创建、更新、同步三个写路径都要删第一页缓存，失败只打日志。缓存逻辑全部内聚在 repository，业务看不见。〔W06-3 p10〕

## 二、缓存什么，由业务访问模式决定

没有通用规则，课程里有几个对照鲜明的决策：

| 场景 | 决策 | 理由 |
|---|---|---|
| 个人资料（高频读） | 缓存 | 读多写少，登录态后几乎每个请求都要 |
| 登录的"邮箱到用户"映射 | 不缓存 | 登录低频，收益小〔W04-1 p19〕 |
| 分页列表 | 只缓存第一页 | 筛选、排序、偏移任一变化缓存就失效，用户大多只看第一页〔W06-3 p7〕 |
| 列表缓存的内容 | 只存摘要，不存全文 | 列表页只展示摘要〔W06-3 p9〕 |
| 大文档 | 超过 1MB 不预加载 | 缓存内存也要权衡〔W06-3 p15〕 |
| 个人是否点赞、收藏 | 不缓存，只缓存总数 | 重复访问同一篇是小概率，命中率低〔W07-1 p23〕 |

规律是：**先看命中率，再看一致性成本，最后看内存**。

两个提前写缓存的套路也值得记：

- **预加载**：认为创作者拿到列表后大概率点开第一条，返回列表后把第一篇放进缓存。预测性质，所以过期时间设得很短（1 分钟）。预加载要不要异步，让**调用者决定**，别自己偷偷开 goroutine。〔W06-3 p12-13〕〔W06-3 p14〕
- **发布时提前写**：新帖发布后预期立刻被访问，发布成功就直接写缓存。凡是有"制作库、线上库"区分的场景都适用，TTL 可按创作者是否大 V 区别对待。〔W06-3 p17-18〕

过期时间的本质是让"接下来对资源的访问都命中"：长 TTL 高命中低一致性，短 TTL 反之。〔W06-3 p20〕

## 三、穿透、击穿、雪崩：三种失效事故

| 事故 | 现象 | 常用对策 |
|---|---|---|
| 穿透 | 查不存在的数据，每次都落库 | 缓存空值（短 TTL），或布隆过滤器 |
| 击穿 | 热点 key 过期，大量并发同时回源 | 合并回源（singleflight）或加互斥锁 |
| 雪崩 | 大批 key 同时过期，或缓存整体不可用 | TTL 加随机抖动，缓存失效降级 |

```go
if useSF {
	sf.Do("hot", load) // singleflight：同一个 key 的并发回源合并成一次
} else {
	load()
}
```

〔实测〕热点 key 刚过期，100 个并发读：不合并时回源 100 次（并发时序下可能略有出入），`singleflight` 合并后回源 1 次。缓存空值后，对不存在的 key 连查 5 次只回源 1 次。TTL 的抖动是在写入时加 `rand` 出来的一小段，让同一批 key 不会在同一时刻过期。

还有一条和 Redis 崩溃有关的取舍：读缓存时出错就回落数据库，Redis 一崩所有读都落到数据库。课程的建议是**只有确认是"未命中"才回源，别的错误直接返回**，业务不可用但数据库保住，别的业务不受连累。〔W04-1 p17〕

## 四、计数：不要"读出加一再写回"

阅读、点赞、收藏是三个典型计数。关键纪律：数据库里更新计数必须是 `read_cnt = read_cnt + 1` 这种原子自增，而不是先读出来加一再写回，后者并发下会丢更新，行级锁保证前者安全。〔W07-1 p7〕新帖没有记录时用 Upsert：不存在则插入，存在则自增，表上 `biz` 加 `biz_id` 的联合唯一索引是关键。〔W07-1 p8〕

缓存侧：Redis 的 hash 一个 key 存三个计数。要处理两种缺数据的情形，key 不存在，或者 key 存在而 field 不存在。〔W07-1 p9〕〔W07-1 p10〕自增前要"先检查 key 是否存在"，检查加自增是典型的"检查再做某事"，用 Lua 脚本保证原子，key 不存在就不动，等后续查询回写。〔W07-1 p11〕

点赞要拆成两件事：记录"谁赞过"（可取消，一张表），和总数统计。取消再点赞用软删除，只更新一列，保留数据。〔W07-1 p12〕〔W07-1 p15-16〕

一致性怎么分析：缓存有数据时，Lua 自增是对的；缓存没数据时，读请求回写缓存和写请求更新数据库并发交错，可能把旧值回写覆盖新值。〔W07-1 p24-25〕课程的立场是：**阅读数不准没关系**，部分失败引发的不一致不去解决。〔W07-1 p6〕这就是"基于业务理解的取舍"：金额不能这样，计数可以。

## 五、榜单：异步定时算，别实时扫

热榜是首页高频接口，要求性能和可用性都极高。直接实时算要全表扫描再全局排序，千万级数据磁盘、内存、带宽都扛不住。方案是**异步定时计算**，间隔可控，再叠缓存和可用性设计。〔W09-1 p12〕〔W09-1 p13〕

课程选了 HackerNews 模型：`Score = (P-1) / (T+2)^G`，P 是点赞数，T 是小时数，G 取 1.5。〔W09-1 p8〕计算流程是分批拉取、算分、用**小顶堆**保留 TopN：堆满之后，新分数比堆顶（当前第 N 名）大才替换；全部批次结束，堆里就是 TopN。〔W09-1 p18-19〕

```go
for _, b := range batches {
	for _, p := range b {
		it := item{p.ID, score(p)}
		if h.Len() < n {
			heap.Push(h, it)
		} else if it.score > (*h)[0].score {
			heap.Pop(h)
			heap.Push(h, it)
		}
	}
}
```

〔实测〕3 批数据取前 3：分数 `20.0`（30 分钟前的 80 赞）、`19.1`（1 小时前的 100 赞）、`6.1`，老帖即使点赞多（7 天前的 1000 赞）也排不进去，这就是时间衰减。

三个工程细节：

1. **七天优化**：批次的最后一条早于截止时间（七天前）就中断循环，七天前的数据不可能进前 100。〔W09-1 p23〕
2. **写 Redis，TTL 要比计算间隔长**，留够重试时间；缓存字段要满足查询接口，一个不少，但用摘要不存全文。〔W09-1 p24〕
3. 定时调度用 `time.Ticker` 或 cron；`select` 里的 `break` 退不出 `for`，要用标签。〔W09-1 p14〕

## 六、分布式锁：谁抢到谁执行，且要有续约

多实例会同时跑榜单任务。结果相同问题不大，但仍要解决：任一时刻只有一个节点运行。方案是节点先抢锁，抢到才执行。〔W09-2 p6〕

`Lock` 的错误要分三种：整体超时（加没加上未知）、超过重试次数没抢到、Redis 通信问题。〔W09-2 p7〕锁放在 **Job 层** 而不是 Service 层：Service 保持业务纯净，Job 保证调度唯一。〔W09-2 p8〕

课程的两个版本：

- **执行期间持锁**，锁的过期时间等于任务超时。缺陷是只管"同一时刻"，实例 0 释放后实例 1 立刻抢到再算一遍。〔W09-2 p9〕〔W09-2 p10〕
- **启动就拿锁、不释放**，加自动续约（每隔超时的一半续一次）。续约失败说明失联，要放弃身份。〔W09-2 p11〕〔W09-2 p12-14〕

锁的语义里最容易漏的是**释放必须验 token**：A 的业务超过 TTL，锁已过期并被 B 拿走，A 迟到的释放不能把 B 的锁删掉。用"检查 token 再删除"，在 Redis 里是 Lua 脚本，保证原子。

```go
// UnlockSafe 相当于 Lua 里的 "if get(key)==tok then del(key)"，必须原子
func (s *Store) UnlockSafe(key, tok string) bool {
	s.mu.Lock()
	defer s.mu.Unlock()
	if e, ok := s.m[key]; ok && e.tok == tok {
		delete(s.m, key)
		return true
	}
	return false
}
```

〔实测〕用内存版演示：A 抢到锁、B 抢不到；A 超时后 B 抢到；A 迟到的释放返回 `false`，B 的释放返回 `true`。另一条思路是用 MySQL 做抢占式调度：任务表加状态和版本号，乐观锁抢占，抢到的实例不断更新时间戳证明活着，崩溃后无人续约，别人才能接手。〔W09-2 p17〕〔W09-2 p18〕

## 七、消息队列：解耦、削峰和它带来的重复

Kafka 的五个概念：producer、consumer、broker、topic 加分区、消费者组。一个业务一个 topic，一个 topic 多个分区。〔W07-2 p4〕〔W07-2 p5-6〕

要背的语义：

1. **分区内有序，全局无序**。要全局有序就单分区；要"同一业务有序"就让同一业务的消息进同一分区，即按 key 哈希。〔W07-2 p9〕〔W07-2 p8〕
2. **消费者组内，一个分区最多一个消费者**。N 个分区最多 N 个消费者有效，多出来的闲着，消息积压时加消费者提不了速。〔W07-2 p10-11〕
3. **`acks`**：0 是发了不管，1 是写入主分区，-1 是同步所有 ISR；性能递减、可靠性递增。〔W07-2 p22-23〕
4. **主从分区要分散在不同 broker**，目标是单 broker 崩溃影响最小。〔W07-2 p6-7〕

RabbitMQ 的对应概念有三条：

- 消息持久化需要**队列 durable 加消息 persistent 两个条件同时满足**，即使如此也不保证立即落盘。〔C:go_frame/mq/rabbitmq/producer/direct.go:33-36〕
- `autoAck=false` 时消费后必须显式 `Ack`。漏 Ack 的消息在 channel 关闭后会重新投递，所以**消费者要能容忍重复**。〔C:go_frame/mq/rabbitmq/consumer/direct.go:28-31〕
- `Qos(prefetch)` 限制单个消费者未确认的消息数，值越小越均衡，吞吐越低。〔C:go_frame/mq/rabbitmq/consumer/direct.go:66-72〕

Kafka 的 Go 客户端有三个选择：Sarama 用户最多，segmentio/kafka-go 没有大缺点，confluent 版需要 cgo，跨平台差。〔W07-2 p17〕

## 八、幂等：重复无害

队列的"至少投递一次"、网络重试、前端重复点击，都会让同一个操作执行多次。通用做法是给每个操作一个**业务幂等键**（事件 ID，不是 offset），处理前先查"是否处理过"，处理和记录放在**同一个事务**里。

```go
func (c *Consumer) Handle(m Msg) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.seen[m.ID] {
		fmt.Println("  跳过重复", m.ID)
		return
	}
	c.seen[m.ID] = true
	c.cnt[m.Key]++
}
```

〔实测〕3 条属于同一实体的消息按 key 哈希进同一分区，保持发送顺序；模拟位点未提交导致 `e3` 重新投递，被跳过，实体的处理次数仍是 3。真实系统里 `seen` 是带唯一索引的表。

幂等的几种实现，按成本排序：

1. **天然幂等**：设置为某值（`SET status = 1`）比累加安全。
2. **唯一索引去重**：处理记录表加唯一约束，重复插入失败就是重复消息。
3. **状态机**：只允许合法的状态迁移，重复的迁移被拒绝。
4. **乐观锁加版本号**：更新时带版本条件。

验证码是一个小例子：同号一分钟只发一次、10 分钟有效、验证通过立即作废、三次失败作废，失败只说"不对"不提示次数。〔W04-2 p26〕

## 同步改异步，值不值

把同步写改成发消息，换来解耦和削峰，也带来：延迟变大、需要处理重复和乱序、需要监控积压、失败要有补偿。阅读数、点赞数这类可以接受不准的写，适合异步（先 Kafka，消费者批量落库）；金额、库存这类强一致的写，别轻易异步。抽奖的例子给了另一种答案：用 Redis 单线程的原子 `DECR` 保证并发扣库存正确，只有减库存成功才把结果返回前端，和秒杀是一个道理。〔C:go_frame/lottery/readme.md:45-49〕〔C:go_frame/lottery/handler/gift.go:31-78〕

## 常见坑

1. 缓存空值不设短 TTL，数据后来有了却一直读到空。
2. 缓存和数据库双写，写缓存失败后不清理，读到旧值。优先"写库后删缓存"。
3. 分布式锁释放不验 token，误删别人的锁。
4. 锁没有续约，任务超时后两个节点同时执行。
5. 消费者没有幂等，重复投递导致重复入账。
6. 分区数小于消费者数，多出来的消费者闲着；以为加消费者能解决积压。
7. `time.Ticker` 没有 `Stop`，泄漏 goroutine。〔W09-1 p14〕
8. 抢锁失败当作错误上报：抢不到说明别的节点在做，是正常情况。〔W09-2 p9〕

## 在项目里

- `dnsproxi-go/cache/` 是一个真正的缓存实现：`Cache.Get` 与 `Cache.Put` 的读写、`ExpireRound` 与 `RunExpirer` 的主动过期（抽样回收，和 Redis 的主动过期同思路）、`sketch.go` 里 `FreqSketch` 做 TinyLFU 准入。它和业务缓存的区别是容量有限，所以要关心"淘汰谁"和"准入谁"。
- `dnsproxi-go/cache/reply.go` 的 `BufPool` 是 `sync.Pool` 复用应答缓冲，命中路径少分配，属于进程内的对象缓存。
- 消息队列和分布式锁在 dnsproxi 里没有对应物，这里没有现成例子。
