# 20 注册发现与负载均衡

> 详细程度：标准 · 约 30 分钟
> 材料：W12-1、W12-2、W13-1、W13-2、C:dachang/etcd · 旧长版：`notes/p10-grpc.md`（gRPC 基础）
> 前置：16 稳定性、19 微服务拆分与治理

## 这一节要建立的认知

拆成多个服务之后，调用方首先要回答两个问题：**这个服务现在有哪些实例**（发现），**这一次调哪一个**（负载均衡）。两个问题的答案都会随时间变，所以不能写死在配置里。

发现机制的演进正好是一条"缓存与新鲜度"的线索：

| 方式 | 优点 | 缺点 |
|---|---|---|
| IP 直连 | 没有 | IP 会变、难维护；只适合联调或定向 debug 某个实例 |
| 域名加 DNS | 简单，没有额外组件 | 客户端不缓存就每次多一跳；缓存了就无法及时更新节点列表 |
| 注册中心 | 注册、查询缓存、变动主动通知三件事一起解决 | 大规模下注册中心容易成瓶颈 |

〔W12-1 p5-7〕注册中心的做法是：服务端启动时注册，客户端首次调用前查询并缓存，节点变动时主动通知。它之所以能打破 DNS 的两难，是用"主动通知"替代了"过期重拉"。

注册中心数据膨胀之后还有一步：**服务自省**（Dubbo 提出）。注册中心只存最小化的定位数据，其余元数据一般不变，查一次就够，通过独立的元数据服务暴露。〔W12-1 p8〕

## 一、注册中心要处理的几件事

- **注册什么**：定位信息（IP 加端口）是关键，其他是治理信息（分组、权重）。〔W12-1 p13〕
- **启动阶段**：连不上注册中心直接失败退出，因为这时服务还没对外提供，失败代价最小。〔W12-1 p12〕
- **心跳就是租约续租**：注册机制本质是租约，心跳是续租。两个参数都是业务权衡：间隔越短压力越大；失败判定次数越少发现越快但越怕偶发失败，越多则越稳但发现越慢。〔W12-1 p15〕
- **优雅下线五步**：通知注册中心、不再接受新请求（读到一半的请求读完即拒，不进业务代码）、等在处理的请求和定时任务结束、结束运行、整个退出有超时控制，超时强退。〔W12-1 p18-19〕
- **客户端发现的两个时机**：启动时发现（拿全部列表，失败不启动）或首次调用时发现（惰性）；客户端与注册中心也要保持连接以接收变更。〔W12-1 p20〕

## 二、etcd 实现注册发现

etcd 是 Go 写的、基于 Raft 的强一致键值库，部署简单。用它做注册中心的思路是**把实例信息写成带租约的 key**：

1. 服务端启动：`Grant` 申请租约（TTL 例如 5 秒），`Put` 时带上租约；开 `KeepAlive` 自动续约。
2. 服务端退出：取消续约，删除 key。
3. 服务端宕机：没有人续约，租约到期，key 自动消失。

第 3 点解释了为什么必须用租约：进程被强杀时没机会删除 key，不用租约的话 etcd 上的节点会一直残留。〔W12-2 p10-11〕etcd 默认约 TTL 的三分之一续一次，SDK 不暴露重试与判定的定制，大多数框架直接用它。〔W12-2 p12〕

key 的设计可以很简单：`/service/grpc/<service_name>/<endpoint>`，只存 key 不存 value；服务端心跳用 `KeepAliveOnce`，遇到 `ErrLeaseNotFound` 就重新注册。〔C:dachang/etcd/service_registration_center/common.go:12-21〕〔C:dachang/etcd/service_registration_center/server/service_hub.go:54-84〕

三个实现细节：

- **注册自己的 IP**：不能写 `127.0.0.1`。资料的取法是对一个外部地址做 UDP "拨号"（不真正发包），再读本地地址。〔W12-2 p16〕
- **先监听，再注册**：确保端口已经打开才对外宣告，否则别人拿到地址连不上。〔W12-2 p14-15〕
- **K8s 环境**：注册 IP 必须是外部能通信的，Pod 重启 IP 会漂移，更推荐直接用 Service 的 DNS，不用注册中心。〔W12-2 p18〕

gRPC 这一侧的关键认知：**gRPC 的核心抽象是 Resolver（解析定位信息），它不知道也不关心你用不用注册中心**。默认走域名解析，资料说它会定时刷新缓存。〔W12-2 p4-6〕**资料说法与实现有出入**：我读 `grpc v1.84.0` 的 `internal/resolver/dns/dns_resolver.go`，DNS resolver 只在被调用 `ResolveNow`（例如连接失败）时重新解析，两次解析之间至少隔 `MinResolutionInterval`（30 秒），并不是严格定时。客户端接入 etcd 只需要注册一个 Resolver，用类似 `etcd:///service/user` 的目标地址拨号，数据同步由 SDK 处理。〔W12-2 p13〕

## 三、CAP 与注册中心选型

CAP：一致性（任意节点读到相同数据）、可用性（每个请求有限时间内返回）、分区容错（网络分区时仍工作）。分布式系统里分区容错几乎必选，分区发生时只能在一致性和可用性之间舍一个。〔W12-2 p29-30〕

注册中心的面试标准答案是 **AP**：对服务发现来说，"返回稍旧的节点列表"好过"拿不到列表"，客户端有失败重试兜底。〔W12-2 p31〕主流产品的取向：

- ZooKeeper：树形结构，Watch 后主动拉取，CP，大集群里 TCP 连接数和主从写入会成瓶颈；Eureka：对等集群，AP，扩展性好，缺点是发现慢、多语言客户端差；Nacos：同时支持 CP 和 AP，中文社区好，部署运维较难。〔W12-2 p32-33〕〔W12-2 p34〕〔W12-2 p35〕
- etcd：Raft 强一致，Go 生态友好，大规模下表现好；网络不稳定时不合适。网络分区时少数派一侧不可用，按 CAP 属 CP 取向（资料 p30 把它称为"AC 模型"，说法不严谨，以 CP 为准）。〔W12-2 p30〕〔W12-2 p36〕

资料的务实结论：小规模熟悉哪个用哪个，大规模优先 etcd（或 AP 方案），现实里常常是写文档罗列优缺点，再看团队偏好。〔W12-2 p37〕

## 四、注册中心自己崩了怎么办

用三条边看最清楚：服务端到注册中心、客户端到注册中心、客户端到服务端。客户端崩不用处理。〔W12-2 p39〕

- **服务端崩了**：注册中心发现并通知有秒级延迟，这段时间客户端会连不上，要自己 failover 换节点重试。〔W12-2 p40〕
- **注册中心崩了**：客户端继续用本地缓存的节点列表（可能不准），连不通就移出列表；没有缓存的新服务就返回错误由调用方决定。服务端这边，新节点注册失败直接退出，老节点继续服务。〔W12-2 p42-43〕
- **注册中心误判服务端崩了**：双方都不需要特别处理，客户端在收到错误判定前仍可调用，但服务端失联一段时间要告警。〔W12-2 p44〕
- **提升注册中心可用性**：单点升级集群、核心业务独立注册中心、线上线下拆分，并在测试环境模拟注册中心崩溃，验证客户端容错。〔W12-2 p41〕〔W12-2 p46〕

## 五、负载均衡：先把问题简化

负载均衡的目的是选最快返回响应的节点。资料把它简化成"负载"一个维度：挑负载最轻的，整体就均衡。〔W13-1 p4-5〕

| 类别 | 算法 | 要点 |
|---|---|---|
| 静态（不看实际负载） | 轮询 | 最简单、应用最广；假设机器能力和请求资源一样，不成立时偶发不均 |
| | 加权轮询 | 按权重分配；缺陷：高权重节点会连续收到多个请求 |
| | 平滑加权轮询 | 解决上面的连续问题，见下 |
| | 随机、加权随机 | 靠大数统计，倒霉时不均 |
| | 哈希、一致性哈希 | 业务特征（业务 ID）算哈希，同一 key 到同一节点；一致性哈希在增减节点时只迁移一部分请求 |
| 动态（看实时负载） | 最少连接 | 连接多约等于负载高；连接多路复用时会失真 |
| | 最少活跃数 | 活跃数是正在处理的请求数，客户端为每个节点维持计数，更准 |
| | 最快响应时间 | 指标可选平均或 99 线 |

〔W13-1 p6-10〕〔W13-1 p18-21〕〔W13-1 p22-23〕〔W13-1 p24-27〕

### 平滑加权轮询：四步

1. 算总权重。
2. 每个节点的"当前权重"加上自己的初始权重。
3. 选当前权重最大的。
4. 选中者的当前权重减去总权重。

〔W13-1 p11〕

```go
func (s *SWRR) Pick() string {
	s.mu.Lock()
	defer s.mu.Unlock()
	total := 0
	var best *node
	for _, n := range s.nodes {
		total += n.weight // 1. 累加总权重
		n.current += n.weight // 2. 每个节点当前权重加上自己的权重
		if best == nil || n.current > best.current {
			best = n // 3. 选当前权重最大的
		}
	}
	best.current -= total // 4. 选中者减去总权重
	return best.name
}
```

权重 A=10、B=20、C=30，连续取 60 次：

```text
前 6 个: [C B A C B C]
60 次分布: map[A:10 B:20 C:30]
```

分布严格等于权重比，而且前 6 个里 C 没有连续出现。如果按权重展开后顺序取（朴素加权轮询），C 会连续命中 30 次，这正是"平滑"要解决的。

### 选型与权重的几条经验

遇事不决用轮询，出问题再说；选指标前先想四个问题：是否考虑服务器能力、用什么指标表达负载、请求资源是否不同（大商家大买家会偶发打爆实例）、能否自组合设计。〔W13-1 p28〕动态调整权重必须设上下限，否则权重可能变成 0 永不被选，或变到最大一直被选；结合调用结果调整（错误降权、成功加权）是常见做法。〔W13-1 p29〕客户端负载均衡只知道自己的连接数和响应时间，看不到其他客户端的情况；〔W13-1 p30〕哈希均衡加本地缓存可以让同一个业务 key 总是命中同一节点，缓存命中率高，也避免每个节点都缓存一份造成内存翻倍。〔W13-2 p34〕

## 六、在 gRPC 里怎么接入

- **默认没有负载均衡**：永远选解析结果里的第一个节点（`pick_first`）。〔W13-2 p4〕要换成轮询，在 `Dial` 时传 service config：

```go
grpc.WithDefaultServiceConfig(`{"loadBalancingConfig":[{"round_robin":{}}]}`)
```

JSON 是手写字符串，写错只有运行时才发现，要仔细（这一行用仓库已有的 `grpc v1.84.0` 编译检查过）。〔W13-2 p5〕

- **自定义只需两个接口**：`PickerBuilder`（`Build` 返回 `Picker`）和 `Picker`（`Pick` 返回选中的连接）。顶层的 `Balancer` 要管连接池状态，逼不得已才用。〔W13-2 p11-12〕
- **内置算法**：`roundrobin`、`weightedroundrobin`（不是服务端配权重，而是客户端根据 QPS 和错误率自己算权重）。其余除非有特殊需求，没必要用。〔W13-2 p9-10〕补充一点资料省略的实现细节：`grpc-go` 里的 `weightedroundrobin` 依赖服务端通过 ORCA 上报的负载数据来算权重（`balancer/weightedroundrobin` 引用 `orca` 包），服务端不上报就用不上。Kratos 把算法封装成 Selector，支持 P2C（随机挑两个，取负载低的）、随机、加权轮询。〔W13-2 p21-24〕
- **failover = 重试加负载均衡**：调用不通就重试，重试再过一遍负载均衡，负载均衡避免再选到坏节点。最简单的做法是 `round_robin` 加 `retryPolicy`（最大尝试次数、初始与最大退避、退避倍数、可重试状态码）。〔W13-2 p29-30〕
- **注册模式**：自定义 Picker 通过 `balancer.Register` 注册到包级变量，作者不太喜欢这种全局注册；Go 里常见的"匿名导入触发 `init` 注册"就是这种。〔W13-2 p7-8〕〔W13-2 p16〕

## 常见坑

1. **以为 gRPC 自带负载均衡**：默认只打第一个节点，双节点实验里只有一个在被使用。
2. **注册 `127.0.0.1` 或容器内部 IP**：别的机器连不上。
3. **不用租约**：进程被强杀后，注册中心里一直残留死节点。
4. **心跳参数拍脑袋**：间隔太长发现慢，太短压垮注册中心，失败次数太少会因偶发抖动误踢。
5. **动态权重没有上下限**：权重滚雪球或归零。
6. **负载指标滞后**：响应头带 CPU 之类的指标，如果指标过期，所有客户端会一起涌向"最空闲"的节点。（资料作业的推论，待核）
