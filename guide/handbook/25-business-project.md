## 先看一个问题：这个系统该从哪一行代码开始写起

资料里的 21 周课程是同一个业务项目（内容社区，仓库名 webook）的完整成长史：从单体的注册登录起步，加缓存，加消息队列，上可观测，拆微服务，做数据迁移，再接搜索、Feed、IM。21 周听完，最值钱的不是任何一周的具体代码，而是**一个系统长大的顺序**：什么时候加缓存、什么时候拆服务、什么时候动数据库，每一步都对应着一个真实的痛点，不痛不加。

还原一下当时的场景。你入职一个新团队，老板给你一个空仓库："做个内容社区，先能注册登录发帖，后面会火。"你面对的不是技术选型清单，是一串顺序问题：第一刀切在哪（先写哪一层）？什么时候才值得引入 Redis？帖子从 10 万涨到 1000 万，数据库要动什么？用户量过百万，要不要拆微服务？每一步都有人催你"早点上"，也都有人警告你"别过度设计"。这一节按这条主线走一遍，每一步给出"痛点是什么、为什么这时候引入"，然后你自己在 `minifeed/` 上把最小的一刀做出来。

先把全景铺开。技术栈按课程出现顺序：Gin、GORM 与 MySQL、Redis（含 Lua 脚本）、Kafka、Prometheus 与 Grafana、OpenTelemetry 与 Zipkin、etcd、gRPC 与 Protobuf、Elasticsearch、Canal、K8s；装配用 wire，配置用 viper，日志用 zap。主线分层是 `Handler → Service → Repository → (DAO + Cache)`。〔W02-2 p14-17〕〔W21-1 p25〕
这条分层里最实在的一条设计结论：Repository 负责"一切与存储有关的事"，包括缓存一致性、预加载、存储层降级；缓存与否、怎么缓存是技术问题，不是业务逻辑，所以放 Repository 不放 Service。〔W21-1 p25〕这与 10 节的分层原则是同一句话的两种说法。

## 第一刀的底稿：W02 的 Gin 接请求与三层落位

这条分层在第 2 周还只是几行注册代码和一个空壳调用链。把它按原课事实铺开，后面每一周的"痛点"才有落点：Gin 怎么接住第一个请求，数据库代码为什么不进 Handler，三层怎么立起来。路由、绑定、校验、CORS 与 middleware 的完整展开在 11 节正文和它的 W02-1 干货块；本小节只收支撑主线顺序必需的部分。

**gin.Context 的双职责。** 最简 Gin 应用三步：引入 gin 依赖，`server := gin.Default()` 初始化 Engine，`server.Run(":8080")` 监听启动。Engine 是逻辑上的 Web 服务器，一个 Go 进程可以创建多个 Engine〔W02-1 p6〕。注册只是把"`GET /hello` 该由谁处理"登记进路由表，真正的读写都发生在处理函数拿到的 `*gin.Context` 上，它是贯穿请求处理的统一入口类型〔W02-1 p6〕：

```go
server := gin.Default()
server.GET("/hello", func(ctx *gin.Context) {
    ctx.String(http.StatusOK, "hello, world")
})
```

`gin.Context` 是 Gin 里的核心类型，日常开发最常和它打交道，两个核心职责：处理请求、返回响应。这两个职责在结构体上就对应两个字段：`Request *http.Request` 承载请求侧（请求方法、路径、头部、body 都从它读），`Writer ResponseWriter` 承载响应侧（状态码、响应头、响应体都往它写）〔W02-1 p10〕。上面例子里 `ctx.String(http.StatusOK, "hello, world")` 走 Writer 侧，把状态码和响应体一起写出；读的例子是下文的 `Param` 与 `Query`，它们从 Request 侧取值。

**三类路由，一种取值。** Gin 支持三类路由〔W02-1 p13〕：静态路由完全匹配（如 `/hello`）；参数路由在路径中带参数；通配符路由任意匹配。取值统一用 `Param`，它是 `c.Params.ByName(key)` 的快捷方式〔W02-1 p14〕：

- 注册 `/users/:name` 后请求 `localhost:8080/users/daming`，`Param("name")` 得到 `daming`，响应"这是你传过来的名字 daming"。
- 参数值连斜杠一起截取：请求 `/user/john` 时 id 是 `john`；请求 `/user/john/`（带尾斜杠）时 id 是 `john/`〔W02-1 p14〕。
- 通配符匹配上了什么也用 `Param` 取：注册 `/views/*.html` 后请求 `localhost:8080/views/home.html`，`Param(".html")` 得到 `/home.html`，匹配值自带斜杠，因为通配符匹配的是带斜杠的那一段〔W02-1 p16〕。
- 硬边界：`*` 不能单独出现，`/users/*`、`/users/*/a` 这类路由不能注册〔W02-1 p16〕。

查询参数是另一回事：`/order?id=123` 的 `id` 附着在 URL 后面，用 `Query("id")` 取，与参数路由是两套机制〔W02-1 p15〕。

**从快捷方法到 handle：注册的三层。** Gin 为每一个 HTTP 方法都提供了一个注册路由的方法（GET/POST/DELETE/PATCH/PUT/OPTIONS/HEAD），这些方法基本上都收两个参数：路由规则（如 `/hello` 这种静态路由）加处理函数〔W02-1 p12〕。提示列表里还有 `Any`（任意方法都注册）、`Match`（收 `methods []string`，自选方法组合）和 `StaticFile`〔W02-1 p12〕；`Any` 的实际用例见 11 节微信扫码的回调路由（回调请求的方法不确定，Any 比只注册 GET 稳，那里引 W05-1 p15）。所以 `server.POST("/users/signup", handler)` 背后是三层：快捷方法按 HTTP 方法转调 `Handle`，`Handle` 再落到底层的 `handle`。OCR 里的源码形态：`GET is a shortcut for router.Handle("GET", path, handlers)`，内部 `return group.handle(http.MethodGet, relativePath, handlers)`，DELETE 同型〔W02-1 p11〕。课件顺带给的方法论：灵活运用 IDE 的代码提示功能和源码查看功能，通过查阅 API 定义来快速掌握 API 用法〔W02-1 p11〕。

**UserHandler：集中还是分散。** 用户模块最先设计的接口是注册和登录，而后才考虑编辑和查看用户信息。作者的研发偏好是"从前端往后端"：先定义 Web 接口，再考虑数据库设计，早期先定数据库时经常遇到前端要加字段的问题〔W02-1 p21〕。组织方式：定义 UserHandler，把所有和用户有关的路由都定义在这个 Handler 上，给它一个 `RegisterRoutes(server *gin.Engine)` 方法注册路由，处理逻辑就是定义在 UserHandler 上的方法〔W02-1 p22〕：

```go
func (c *UserHandler) RegisterRoutes(server *gin.Engine) {
    server.POST("/users/signup", c.SignUp)
    server.POST("/users/login", c.Login)
    server.POST("/users/edit", c.Edit)
    server.GET("/users/profile", c.Profile)
}
```

这是分散注册；另一种是集中注册，在 main 函数里 `c := &web.UserHandler{}` 后逐条 `server.POST("/users/signup", c.SignUp)`。取舍是原文的两列对照：集中注册打开就能看到全部路由，但路由太多的时候找起来很费劲；分散注册比较有条理，但找路由的时候不好找〔W02-1 p23〕。作者对这种 Handler 组织方式的评价带前提：**在简单的应用里面**这是不错的 Web 代码组织方式，比如后续可以有 ArticleController 之类的并列 Handler〔W02-1 p22〕。分散注册跑一阵还会遇到具体痛点：四条路由全带 `/users` 前缀，手一抖就有可能写错，这时用分组路由，前缀只写一次：

```go
ug := server.Group("/users")
ug.POST("/signup", c.SignUp)
ug.POST("/login", c.Login)
ug.POST("/edit", c.Edit)
ug.GET("/profile", c.Profile)
```

作者给分组功能的定位是一种便利手段，为了方便组织代码而引入，没有引入新的语义〔W02-1 p24〕。

**Handler 为什么不直接碰 GORM。** 数据库准备好了，课程问：增删改查代码放在哪里？能不能直接在 UserHandler 里面操作数据库（GORM）？答案是否定的，不能：因为 Handler 只负责和 HTTP 有关的东西，需要一个代表数据库抽象的东西〔W02-2 p14〕。解法是直接引入 Service-Repository-DAO 三层结构，其中 service、repository 的提法参考的是 DDD 设计；同时还需要一个 domain，代表领域对象〔W02-2 p15〕。三层各自代表：service 代表领域服务（domain service），代表一个业务的完整处理过程；repository 按 DDD 的说法代表领域对象的存储，可以直观理解为存储数据的抽象；dao 代表数据库操作〔W02-2 p15〕。作者对 DDD 的态度是边界说明：DDD 看起来很简单但实际上很难理解，这时先不要去探究什么是 DDD，先记住每层放什么、调用链怎么走。

**repository 和 dao 为什么不合并。** 原文自设一问：为什么有 repository 之后还要有 dao？repository 是一个整体抽象，里面既可以考虑用 ElasticSearch，也可以考虑使用 MySQL，还可以考虑用 MongoDB，它只代表数据存储，但是不代表数据库；dao 只对应"数据库操作"这一种实现。service 拿来干嘛：组合各种 repository、domain，偶尔也会组合别的 service，来共同完成一个业务功能（"偶尔组合别的 service"是原文给出的边界）。domain 被认为是业务在系统中的直接反应，可以直接理解为一个业务对象，或者一个现实对象在程序中的反应〔W02-2 p16〕。按这套分工做一个教学推论（原文逻辑的自然延伸）：哪天把存储从 MySQL 换成 MongoDB 或 ElasticSearch，动的是 repository 底下接的那个实现，repository 往 service 暴露的形态不变，存储后端可替换性由 repository 层承担，这也是两层不合并的理由。

**一次注册穿过四层。** 课程总结的预期调用链：web 和 HTTP 打交道，service 放主要业务逻辑，repository 是数据存储抽象，dao 是数据库操作，链路 web→service→repository→dao〔W02-2 p17〕。落到注册接口，p18 的改造代码分三段（OCR 可见字段与调用）：

```go
type UserService struct {
    repo *repository.UserRepository
}

func (svc *UserService) Signup(ctx context.Context, u domain.User) error {
    return svc.repo.Create(ctx, u)
}

type UserRepository struct {
    dao *dao.UserDAO
}

func (ur *UserRepository) Create(ctx context.Context, u domain.User) error {
    return ur.dao.Insert(ctx, dao.User{Email: u.Email, Password: u.Password})
}

type UserDAO struct {
    db *gorm.DB
}

func (ud *UserDAO) Insert(ctx context.Context, u User) error {
    return ud.db.WithContext(ctx).Create(&u).Error
}
```

划清原页与补足的边界：p18 OCR 能证实的是三个结构体的字段（`repo *repository.UserRepository`、`dao *dao.UserDAO`、`db *gorm.DB`）和三行调用，Signup 里 `return svc.repo.Create(ctx, u)`，Create 里 `return ur.dao.Insert(ctx, dao.User{Email: u.Email, Password: u.Password})`，Insert 里 `return ud.db.WithContext(ctx).Create(&u).Error`。方法签名在 OCR 截断处，入参类型按调用形态补足；三个依赖字段怎么被赋值（构造注入）原页未展示，按本节"想深入"的 DI 两条铁律（B 是字段就从构造函数传入〔W21-1 p5〕）补足。能从原页直接读出的结论有三条：service 基本上不做什么事情（原话），repository 也没做啥、最关键的都在 dao 里面（原话），domain 用户的字段转成 dao.User 字段（OCR 可见 Email、Password）的类型转换只发生在 repository 这一层，GORM 调用只出现在 dao 层。web 层原课未给代码：按课程分层推演，web 层的 SignUp 校验完请求字段后把字段装进 domain.User 交给 service（这一步是示意，不当作原页事实。

这页的三层全是透传骨架，是"先立分层骨架"，不是最终实现形态，业务逻辑要后续章节再往里填〔W02-2 p18〕；透传的另一面是让"业务逻辑、存储抽象、SQL 细节"各自只有一个变化理由，哪层开始写业务，分层的钱就花在哪层（见本节"想深入"的 W02-2 干货条）。dao.User 与 domain.User 为什么要分成两个类型：domain.User 是业务概念，不一定和表或列完全对得上（比如数据库以 JSON 存的字段，在 domain 里会转成结构体），dao.User 则直接映射到表里面〔W02-2 p20〕；10 节的最小骨架就是这个形状（那里把 dao 层类型命名为 UserRow，课程原页叫 dao.User）。注册业务的异常后果课程也有固定去向：邮箱撞唯一索引时 dao 判 MySQL 1062 错误码转成 `ErrUserDuplicateEmail`，沿层往上传导，Handler 据此返回冲突响应，链条展开在 12 节。minifeed 阶段 1 是这条主线的自建练习骨架（非原课实现）：路由装配在 `minifeed/server.go:113-117` 的 `newMux`（`POST /users` 对应原课的 `POST /users/signup`），`handleSignup`（`minifeed/server.go:155-156`）校验字段后调 `auth.Hash` 再交 Store，按 400/409/201 返回；它把 service 与 repository 压掉、handler 直依赖 Store 接口，对照课程四层正好看清每层各自承担了什么。

## 二、五条演进规则，每条讲清为什么

**规则一：重构先补测试。** 课程建议覆盖率达到 80% 以上再动手，并强调集成测试，因为它真的打到数据库和 Redis。覆盖率只是发现测试缺口的线索，不证明关键行为已被覆盖；应先识别要保持的业务行为、失败路径和回滚条件。课程的做法是单元测试保逻辑分支，集成测试保 SQL 与缓存等边界；两者互补，不能只凭任何一种测试证明系统没有问题。〔W10-2 p12-13〕14 节的测试金字塔可以帮助安排它们的比例。

**规则二：拆微服务，先挑最不重要的模块。** 直觉是拆"用户"这种核心，反了。资料的标准是三个条件按序筛：业务影响力小（崩了无所谓）、依赖最少（拆它不牵动别人）、QPS 低（拆的过程压测好做）。按这套筛子，用户和帖子不能选（核心依赖），短信不能选（登录要用），热榜不能选（QPS 高），最后选了点赞收藏。〔W10-2 p12〕拆分本身有八步固定动作：选模块、补测试、拆代码、技术选型、改为微服务对外、本地与微服务双调、流量逐步切到 100%、删除本地调用。其中第六步是整套流程的安全阀：两套调用都在，开关控流，微服务出问题立刻把流量切回本地调用，随时可回滚。〔W10-2 p7〕19 节有这八步的逐步展开，包括第六步为什么要留一个中间态。

**规则三：不停机迁移数据，靠双写加反复校验。** 四个阶段：读源、双写以源为准、双写以目标为准、只读写目标。难点不是搬运，是"迁移期间数据一直在变"：存量搬完了，增量还在来；等增量追平，之前的存量又被改了。所以方案里没有"校验一次"这个动作，只有"增量校验持续跑、不一致就修复"这个循环，监控保证双写失败只是偶发，靠校验修复兜底。〔W11-1 p9-10〕增量从哪来？定时任务全量比对、binlog 的 CDC（Canal 伪装成 MySQL 从库收 binlog 再转发）各有适用场景，一个准实时一个实时，17 节展开。18 节的最终一致性是它的理论底座：双写方案默认"最终一致，靠校验收敛"，先接受这一点，方案才立得住。


**规则四：一切不在你控制范围内的调用都要容错。** 第三方短信、支付、别的团队的接口，都是失败域：你不知道它什么时候挂，也不知道挂了会拖你多久。做法有固定顺序：先限流（防自己被打死），再用装饰器无侵入地叠加超时与重试（不改原有实现，调用方无感知），最后 failover（换一个备用通道）。〔W04-6 p3-5〕〔W04-6 p10〕〔W04-6 p21〕16 节把这三种阀门的位置讲全了：服务端放限流熔断保护自己，客户端放超时重试 failover 保护自己不被下游拖死。顺序不是随意的：不先限流，重试会放大流量；不先有超时，failover 永远轮不到执行。

**规则五：允许延迟时考虑异步。** 例如 Feed 可以根据产品要求接受秒级甚至十秒级延迟；消息队列可以解耦、削峰，但也引入投递失败、延迟和最终一致性。〔W19-1 p35〕先问业务能否接受延迟、丢失风险和乱序，再决定是否异步：点赞计数、Feed 刷新、榜单更新可能适合，登录密码校验通常需要同步结果。还要考虑操作是否可重试、队列和消费者如何恢复，以及多次消费是否安全；这是 13 节的主题。

### 前四个阶段抄什么：从骨架代码反推设计

阶段 1 到 4 的实现已经在 `minifeed/` 里，做它们的意义是"读懂一版正确答案"。每个阶段有一个值得停下来想一分钟的决策：

阶段 1（用户与登录）。密码为什么存盐哈希而不是加密？因为验证只需要比对，不需要还原，哈希把"拖库后直接得到明文"变成"拖库后还要暴力破解"。token 为什么是自签 HMAC 而不是 Session？因为 API 服务多实例部署时 Session 需要共享存储，token 只需要每个实例持有同一个密钥。对应课文：`auth.Hash()` 与 `auth.SignToken()` 的实现加注释里的 W02-1。

阶段 2（发帖）。为什么 `PostStore` 要内存和 SQLite 两个实现？因为"帖子怎么存"是可替换的存储细节，Handler 和 Service 都不该知道用的是哪个；双实现同测还白送一个好处：逻辑错误在内存实现上更容易暴露。对应课文：12 节的存储层抽象，`post/post_test.go` 里 `TestMemoryList` 与 `TestSQLiteList` 跑同一组断言。

阶段 3（计数）。为什么点赞先进内存、定时批量落库？1000 QPS 的点赞如果每次都 `UPDATE`，数据库光写这一件事就要扛 1000 QPS；批量合并后可能只要每秒 10 次。代价是崩溃丢最近一个窗口的计数，这是可接受的取舍：点赞数不需要精确。对应课文：13 节计数部分，`counter` 包的 flush 回调。

阶段 4（热榜）。为什么榜单是定时算而不是实时算？实时算意味着每次读都全表扫描加全局排序，千万级数据下磁盘和带宽都扛不住；定时算把计算成本摊平成"每 N 秒一次"，读的时候只碰缓存。两个配套件：单飞（并发触发只算一次）和降级（刷新失败沿用旧榜，首页不能白屏）。对应课文：13 节热榜部分，`rank.Refresh()` 的实现。

读这四个阶段时带着一个问题走：每个决策把什么换成了什么？性能换一致性（阶段 3）、实时性换可用性（阶段 4）、开发速度换可测试性（阶段 2）。说不出换出去的是什么，说明还没读懂这个决策。

### 阶段 5 的设计走一遍：Feed 的决策点

阶段 5 是唯一没有现成实现的，值得把决策链完整走一遍。问题：帖子创建成功（`handleCreatePost`）之后，粉丝怎么看到这条帖子？

方案 A 全推（写扩散）：发帖时给每个粉丝的收件箱写一条。读快（收件箱就是结果），写随粉丝数线性涨：2000 粉丝的作者发一次帖写 2000 次。方案 B 全拉（读扩散）：只写自己的发件箱，粉丝读时合并所有关注对象的发件箱再排序。写恒定 1 次，读随关注数涨。21 节给过这两个缺陷的数值版：2000 粉推，写 2000 次；300 万粉拉，读时合并两路。

一种常见方案是推拉结合：普通作者走推，大 V 走拉，阈值按压测数据定，再叠加活跃用户过滤（不活跃粉丝连收件箱都不用推）。判断时查询至多阈值加一条粉丝记录：多出的记录表明超过阈值，不必读取全部粉丝；查询成本仍取决于阈值、索引与数据库执行计划，不是 O(1)。读路径的合并顺序与分页稳定性见 21 节。

两个附带的决策。一是索引列顺序：`follow` 表既要查我关注了谁，也要查谁关注了我。唯一索引 `(follower, followee)` 可约束关系不重复并支持按 follower 查询；反方向通常还需要以 followee 为首列的索引。〔W16-2 p11〕二是幂等：唯一索引只能拒绝重复行，还要在 `FollowRepo.Follow` 中将对应的重复冲突处理为成功，重复调用才不会报错。

### 你要写的两个接口

关注关系与 Feed 的接口骨架（进程内事件总线先用 channel，换 Kafka 只动这一处）：

```go
type FollowRepo interface {
	Follow(ctx context.Context, follower, followee int64) error   // 幂等：重复调用不报错
	Unfollow(ctx context.Context, follower, followee int64) error
	Followers(ctx context.Context, followee int64, limit int, afterID int64) ([]int64, error)
	Followees(ctx context.Context, follower int64) ([]int64, error)
}

type FeedStore interface {
	PushInbox(ctx context.Context, uid int64, p Post) error     // 写扩散：粉丝收件箱
	PushOutbox(ctx context.Context, author int64, p Post) error // 读扩散：大 V 发件箱
	Inbox(ctx context.Context, uid int64, limit int) ([]Post, error)
	Outbox(ctx context.Context, author int64, limit int) ([]Post, error)
}

type Bus interface {
	Publish(ctx context.Context, topic string, v any) error
	Subscribe(topic string, h func(ctx context.Context, v any) error)
}
```

`OnPostCreated` 可以先调用 `Followers` 查询阈值加一条：多出的一条说明粉丝数超过阈值，只 `PushOutbox` 一次；否则逐个 `PushInbox`。这避免读取全部粉丝，但查询最多仍需处理阈值加一条记录，并非常数成本。

### 做的时候要守的纪律

- 先写接口再写实现，包之间只依赖接口，`server.go` 是唯一知道具体类型的地方（10 节的手写 DI）。
- 阶段 8 之前不要拆进程；拆的时候先补集成测试（规则一）。
- 每个阶段结束项目都可运行、测试全绿；上一阶段不绿就不开下一阶段。

### 阶段 8 的双写演练怎么设计

阶段 8 的迁移部分最容易做成"背课文"。给它一个可验证的最小形态：现有 `user` 表的存储从 SQLite 换成另一个 SQLite 文件（模拟换库），用 17 节的四阶段走一遍。写一个 `DualStore`，实现和 `PostStore` 一样的接口：内部持有源和目标两个存储，写路径按阶段开关决定写哪边、以哪边为准；读路径按阶段开关决定读哪边。再写一个校验循环：每 N 秒比对两边同一批 ID 的字段值，不一致就打日志并修复。四个阶段切换靠一个枚举字段，测试里显式推进阶段并断言每个阶段的读写行为。这个练习做完，17 节的"双写、校验、修复、切换"就不再是名词，你还会遇到真实的坑：双写失败一边怎么办（记录后继续，靠校验修复）、自增 ID 怎么对齐（显式指定主键）、校验本身打满数据库怎么办（限速分批）。

## 小结

1. 21 周课程的价值是"系统长大的顺序"：分层、缓存、消息队列、可观测、拆服务、迁移、搜索、Feed、IM，每一步都由前一步的痛点逼出来；对照表比周次表好用。
2. 分层主线 Handler、Service、Repository、DAO 加 Cache；缓存属于存储范畴，放 Repository 不放 Service。〔W21-1 p25〕
3. 五条演进规则：重构先补测试；拆服务先挑风险较低的模块并保留回滚开关；迁移靠双写与持续校验；外部调用设计容错；业务允许延迟时再权衡异步。
4. minifeed 是主线的练习场：已有五个包的起步骨架，你要补的是关注与 Feed，按八个阶段推进，每个阶段用 `go test -race` 验收。
5. 推拉结合的判定技巧：列表多取一个，判断是否超过阈值而不必读取全部粉丝；阈值应结合压测数据与业务约束确定。

| 阶段 | 最容易迷路的地方 | 拉回来的办法 |
|---|---|---|

| 2 发帖 | 状态机散落成 if-else | 状态迁移集中一个函数，非法迁移返回错误 |
| 3 计数 | 落库失败把点赞主路径堵死 | flush 回调只记日志，计数在内存继续 |
| 4 热榜 | 刷新失败返回错误拖垮首页 | 沿用旧榜，记一条 WARN |

## 常见坑

1. 一开始就拆微服务，没有测试保护，回滚没有开关。
2. 把缓存逻辑写进 Service：业务代码被存储细节污染，换缓存要改业务。
3. 关注关系的唯一索引列顺序写反：`WHERE follower = ?` 全表扫。〔W16-2 p11〕
4. 大 V 全部写扩散：一次发文瞬时百万写。〔W19-1 p18〕
5. 迁移只校验一次：迁移期间数据还在变，必须增量校验加修复循环。
6. 异步化没有边界：把"必须同步看到结果"的路径（登录密码校验）也扔进队列。
7. `Followers` 每次全量拉取不分页：粉丝百万时一次查询就是几百 MB，列表接口一律带 `limit` 加游标。
8. 热榜候选集取全表：先按业务缩小范围（最近 N 天、有效状态），再进堆和排序。

## 判断题与答案

先自己答，再看后面。

1. 资料为什么选"点赞收藏"作为第一个拆出去的模块，而不是"用户"？
2. 双写迁移的第二阶段和第三阶段，区别是什么？为什么不直接从双写跳到只写目标？
3. minifeed 的 `FeedStore` 为什么要同时有 Inbox 和 Outbox 两套？

**答案**

1. 三个筛选条件：业务影响力小（崩了无所谓）、最独立（依赖少）、QPS 低。用户是核心依赖，点赞收藏三者全占。〔W10-2 p12〕
2. 第二阶段读源表、先写源表（以源为准），第三阶段读目标表、先写目标表（以目标为准）。直接跳意味着"读哪边"的语义在同一个部署里模糊，出问题无法定位以哪边为准；分两个阶段让读源切换成一个明确的、可回滚的开关。
3. 推拉结合要求两种路径并存：普通作者走 Inbox（写扩散，读时直接拿），大 V 走 Outbox（读扩散，粉丝读时合并拉取）。只留一套，要么写放大要么读放大，见 21 节。

## 在项目里

`dnsproxi-go` 与 minifeed 互补：24 节展示"一个小系统的内部机制"（缓存、逐出、成帧、背压），本节展示"一个业务系统的外部演进"（分层、异步、治理、迁移）。两边的交集是缓存：dnsproxi 的缓存自己管理生命周期，minifeed 的计数器用 flush 回调延迟落库，一个是进程内缓存，一个是"缓存当作主存储、DB 当持久化"的写回模式，两种取舍都值得写进你自己的笔记。

### W21-1 课程总结：把 21 周收进 11 页的判断题

- 面向接口的定义判据不是"现在有几个实现"，是"预期维护期内会不会有新实现"：单实现但预期换（比如短信要接多家服务商）就定义接口；单实现且预期稳定就用具体类型；反过来，要依赖实现细节（比如依赖缓存预加载这个特性）时才用具体实现。接口是为预期中的变化留的口子，不是仪式。〔W21-1 p3-4〕
- 依赖注入两条铁律：A 用到 B，B 就是 A 的字段；B 是字段，就一定在构造 A 时从外部传入。minifeed 的 `server` 结构体和 `openStore()` 就是这两条的直译，`server.go` 是全项目唯一知道具体类型的地方。〔W21-1 p5〕
- 单一职责落到接口上就是"方法寥寥几个且同类"；CQRS 是它的读写特例：读写方法分散到不同接口，最大好处是分别治理，出问题可以只降级写接口、限流时读阈值高写阈值低。搜索服务的 `SearchService` 与 `SyncService` 拆分是课程范例。〔W21-1 p6-7〕
- 开闭原则的落地形态是装饰器：给 sms 加可观测性不改旧代码，包一个新实现。反过来，"加一个 if-else 分支"往往就是违背它的信号。〔W21-1 p8〕
- 超前设计但不超前实现，度量单位是迭代：接下来两三个迭代内的变更，设计时留口子；更远的变更，纳入代价低才考虑、代价高就放弃。全盘考虑的结果是复杂度爆炸，人力扛不住。〔W21-1 p9-10〕
- 课程提出规模扩大后应优先考虑异步：Kafka 等队列可帮助解耦和削峰，但异步也需要处理延迟、重复、乱序和故障恢复，不能仅凭性能或治理便利取代同步调用。先确认业务的结果反馈和一致性要求。〔W21-1 p11〕
- 装饰器不断叠加就是洋葱模式：越靠内核越核心，初始化 sms 时在最基础实现外包可观测、容错、鉴权，大部分中间件设计核心都是一个洋葱。课程在可观测性、容错、failover、ratelimit、metric、otel 等目录里大规模用了这套模式。〔W21-1 p13-14〕
- 构造参数多了怎么选：有点复杂但不特别复杂的用 Option（函数式实现，`WithXXX` 返回函数，`New` 里逐个应用），特别复杂的用 Builder（链式调用返回 Builder 本身）。gRPC 的 `Dialoption` 是接口式 Option 的范例。〔W21-1 p16-17〕
- gRPC 装饰器的向后兼容靠组合：嵌入 `UnimplementedSmsServiceServer`，只装饰必要的方法，protobuf 之后加新方法照样编译通过。〔W21-1 p19〕Gin 的 middleware 是责任链的一环：当前环节处理完调 `ctx.Next()` 执行下一环，`defer` 里统一统计。〔W21-1 p20〕
- 缓存一致性选"先更新 DB 再删缓存"要想清楚它的真实属性：缓解不是解决。极端交叠下（一个读请求拿旧值回写缓存的速度慢于另一个请求写库删 key）缓存里会留下旧值，只是概率小，因为读库回写通常比写库删 key 快。要求强一致就得分布式锁或版本号。〔W21-1 p28〕
- 分页接口很难缓存，可用的一招是只缓存第一页：第一页访问频率远高于后面所有页，收益立现；还能叠加业务预加载，把第一页前几条的详情也提前放进缓存。〔W21-1 p29-30〕
- 更常用的是应用启动预加载：toB 场景标签服务在启动时把缓存灌满。预加载本地缓存是每个节点各自加载一遍；预加载 Redis 只需一个节点做一次。〔W21-1 p31〕
- 性能苛刻的场景上三级结构，本地缓存、Redis、DB，读序本地到 Redis 到 DB，写序 DB 到本地到 Redis。先写本地后写 Redis 不是教条：本地操作几乎不可能失败，本地写成功 Redis 失败只是短暂不一致，读侧有本地兜底。〔W21-1 p32〕
- 本地缓存的默认答案是别用：命中率低、占内存。只有两个场景值得：三级结构，或者当 Redis 的故障备份（平时走 Redis 到 DB，Redis 崩溃临时走本地到 DB，恢复后切回）。〔W21-1 p33〕
- 注册发现面试必强调容错：客户端尽可能用本地缓存的节点数据，发现节点不可用先挪走，之后还要考虑挪回来。负载均衡的本质是找到预期最快返回的节点，静态算法是基础，关键在动态调权重（步长、上下限），再和熔断限流降级整合成复杂策略。〔W21-1 p36-37〕
- 熔断和降级一句话分清：熔断是触发后直接拒绝所有请求，保护自己；降级是尽可能给个响应，预配默认值或走快慢路径里的快路径，保住体验。〔W21-1 p38-39〕
- 限流算法固定窗口、滑动窗口、令牌桶、漏桶四选；"拒绝"有三种去向：转异步后续处理、返回特定错误、转发别的节点。限流熔断降级还能和缓存结合：触发时只查缓存，Redis 命中就返回，没数据才查库或直接降级。〔W21-1 p40-41〕
- 治理是组合拳：触发后客户端直接换节点，还能把该节点权重降到极低让后续请求不再选它；客户端治理的核心是识别第三方有没有问题（超时、响应时间、错误响应、错误码四个判据，服务端自己看硬件资源和性能数据，还能通过响应元数据或定期上报把指标传出去）。判定出问题后的三板斧：同步转异步、换节点、返回默认值。〔W21-1 p42-44〕
- 要不要微服务的原话值得记住：不是为了 KPI，只有走投无路才考虑。微服务对团队和运维要求都高，准备不充分贸然推行容易翻车。这条是规则二的元规则。〔W21-1 p46〕
- 最佳实践七分客观三分主观，遇到先问三句：客观的还是主观的（缩进风格是主观的）、适不适配公司现状（大厂高并发实践未必适合你）、什么时候提出的（十年前的实践受制于当年性能）。归结为不盲从。〔W21-1 p47〕
- 课程建议工具库和基础中间件以单元测试为主，业务开发重视集成测试。具体比例仍取决于风险：单元测试检查业务分支，集成测试检查真实依赖和边界，两者不能互相替代。〔W21-1 p53〕

### WX-sms 短信服务：把容错凑成一个完整业务

- 短信平台两头对外：对内收业务方请求（同步调用，或业务方直接发 MQ 异步），对外直连第三方服务商（腾讯、阿里）；配套管理后台做查询、补发、单发群发定时发、营销短信和鉴权限额（比如某业务一个月 10 万条）。〔WX-sms p1-2〕
- 可靠投递的根是入库先行：请求先落库，立刻尝试发送，失败交给定时扫描未成功记录的补偿任务补发。反过来直接调第三方，失败即丢，崩溃后无从追讨。代价是可能重复发送加部分非实时，都可接受。〔WX-sms p2-3〕
- 重复请求靠去重加幂等回放：请求带 `biz_type+biz_id` 建唯一索引，重复请求来了查同键之前是否发送成功，成功返成功、失败返失败。去重键必须用业务语义，不能用手机号：同一个人两条不同业务的短信都要发。〔WX-sms p3〕
- 灵活重试是按业务方配的：是否跨进程重试、间隔、次数各自不同；最终失败的消息丢进 MQ 让业务方订阅，再配告警（邮件、聊天机器人）告知终态。〔WX-sms p3-4〕
- 平台自保护两件套：降级是高负载时同步转异步，给业务方"已受理"响应，业务方查接口或听消息拿结果；限流保护平台自己的入口，被限流的请求也转异步而不是直接报错。直接报错等于把压力变事故。〔WX-sms p4〕
- 服务商容错三档递进：客户端限流（防触发服务商限流，触发了自动切换）、轮询 failover（超时或异常响应就切下一个）、健康判定 failover（按超时和异常判定不健康，临时移出，间隔试探，成功恢复、失败延长不健康时间，避免永久拉黑）。单用轮询会把流量反复打到坏节点上。〔WX-sms p4〕
- 回查机制是事务消息的翻版：业务方先发"准备短信"不真发，业务成功提示后才发给用户，失败提示就删除，超时无提示就回查（回查 HTTP/RPC 接口，或丢 MQ 让业务方自查后回执）。它与事务消息、分布式事务联动是分布式架构的亮点，但实现复杂、要业务方配合改造，提一句即可别主动展开。〔WX-sms p4-5〕

#### W02-2 三层落地的最后一环

- 调用链上每一层"薄"得有名堂：UserService.Signup 只透传 repo.Create，UserRepository.Create 只做 domain 到 dao 的类型转换再调 dao.Insert，真正的数据库操作集中在 `db.WithContext(ctx).Create(&u)`。层层薄透传不是浪费，是让"业务逻辑、存储抽象、SQL 细节"各自只有一个变化理由；哪层开始写业务，分层的钱就花在哪层。〔W02-2 p18〕

#### W10-2 方案设计一页纸与执行纪律

- 拆分方案先定边界：课程从 DDD 的“一领域一服务”出发，再用团队能掌握的业务细节范围校正粒度。边界要能被维护它的人理解。〔W10-2 p4〕
- 路线二选一：先拆一个模块，能提前验证完整流程，但拆出去后难以停下；全部模块按模块化、依赖化、服务化推进，各阶段都能停下，问题却会集中到最后暴露。课程选先拆一个模块。〔W10-2 p6〕
- 迁移方案写清八步与回滚中间态：补测试、拆代码、选框架之后，保留本地调用与微服务调用两条路径，用开关逐步切流；出问题就切回本地，稳定后才删旧调用。19 节展开整套步骤。〔W10-2 p7-8〕
- 选模块先易后难：依次看业务影响力、依赖数量和 QPS，课程最终选了点赞收藏模块，具体理由见本节规则二。〔W10-2 p12〕
- 模块化执行的两条纪律：充分利用 IDE 的重构功能挪目录，而不是手工剪切粘贴（挪错引用编译器立刻报）；任何一个关键步骤之后都跑测试验证效果，测试绿了才走下一步。20 页这步只做"代码挪进独立目录、层结构原样保留"，InitTables 挪移、消费者复制、wire 双份重生成是它后面的三颗雷，19 节已展开。〔W10-2 p20〕

#### W19-1 推拉结合的两个补注

- 综合方案的评价页给了两条 25 节设计没写透的边界：写侧的写放大还在，只是"能限制住写扩散的数据不多"（只有大 V 走拉之后的普通作者量）；读侧的聚合排序还在，发件箱一旦分库分表就叠加跨库跨表查询。课程版本只做推拉结合，不做活跃用户判定，优先保障活跃用户体验，非活跃用户读得慢一点是接受的代价。〔W19-1 p20〕

#### W21-1 Builder 与 Option 的分工原话

- Builder 用于构造复杂或预期多变的对象，配合链式调用，每个方法返回 Builder 本身直到构建完成；课程在 middleware 和插件构建里大量用它，MiddlewareBuilder（AllowReqBody、AllowRespBody 默认关闭）是范例。与 Option 的分工口诀：有点复杂用 Option，特别复杂用 Builder。minifeed 阶段不需要，等到配置项超过四五个再想起这条。〔W21-1 p15〕〔W21-1 p16-17〕
