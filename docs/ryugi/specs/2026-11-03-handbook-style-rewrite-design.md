# Go 手册 Ryugi 风格重写设计方案

日期：2026-11-03
状态：澄清完成（全部决定已由所有者确认）
澄清过程：document artifact `document/rewrite-style-clarify`（http://localhost:27319/document/D0Q7FM2dVq26IcWWOgxVa，本地路径 `.ryugi/artifacts/document/rewrite-style-clarify/`，未入库）；风格对比 artboard `artboard/style-reference`（同目录）。

## 1. 背景与问题

仓库 golearn 是 Go 教程项目：读者主路径 `guide/handbook/`（27 节）+ 细节库 `notes/`（35 章，约 1.3 万行）+ `docs/` VitePress 站点。所有者对现状语言的判断（10-27 起）："写的一塌糊涂、东一斧头西一榔头、蜻蜓点水、问题没说到点子上"，点名廖雪峰 js/python/java 教程与 dbwu/eddycjy 的 Go 文章为风格参照。本方案回答：重写成什么风格、什么范围、按什么流程、怎么验收。

## 2. 目标 / 非目标

**目标**
1. 全部读者文档（handbook 优先，notes 排入批次）按定稿风格重写。
2. 每节做到"提纲挈领 + 机制到实现层"：先给地图，再展开，关键机制讲到运行时/编译器行为。
3. 面向 Java/TS/Python 背景读者，从其已有心智模型出发组织对比。

**非目标**
- 不改技术事实：重写是风格与结构工程，事实以 `work/text/` 原文为准。
- 不新增章节、不改章节编号（26 路线 / 27 决策表只随各节时长重算更新）。
- 不为风格放弃批审门禁：只有双审落盘（runId + 回执）算改完。

## 3. 定稿风格规范

**节奏（廖雪峰式，B 档）**
- 从会的代码出发 → 一次引入一个新东西 → 每段代码立刻跑出输出 → 小失败制造"为什么" → 失败后才给术语与原则。
- 修辞尺度（Q8 定案）：禁三类，悬念标题（"先让问题撞墙"式）、卖萌元素（💀/梗图/惊叹号轰炸）、故意隐瞒答案的倒计时写法。保三类，问题先行的引入（"如果要换成短信呢？"）、例子即跑、失败案例直讲并解释。标题用机制命名（"接口调用在运行时怎么发生"），不用悬念。

**提纲挈领（Q9 定案：缺省模板，非硬性范式）**
- 每节默认开头三件套：① 机制对照（本节新概念 × 读者已会概念 × 差异，≤6 行）；② 本节问题清单（读完能答什么）；③ 与前后节的依赖一句话。
- 速查/索引型内容（26 节、27 节）或机制一眼见底的小节可跳过对照表，审稿记录写一句跳过理由。形式服从内容，样张 C 的表格版被所有者判"不适合人类阅读"，对照信息优先用叙事段（样张 C2 形态：先地图后展开），表格只在数据天然成表时用。

**机制深度（Q7 定案）**
- 三档取"机制层"：讲到运行时/编译器实际做什么（itab 结构、vtable 槽位、方法集合判定），配源码级引注；不展开汇编/内存布局，深入需求给 notes/ 链接。
- 硬要求（S5，Round 1 定案）：面向 Java 背景，接口与多态一节必须详细对比 Java 与 Go 的多态实现机制（显式 implements + 单一 vtable vs 隐式方法集合 + itab），从 Java 工程师视角组织，含"运行时成本同量级，差异在关系建立方式"的结论。

**引注（Q11 定案）**
- 保留但降权：行尾小灰字（读者不打扰），不删，双审靠它逐条回对原文防杜撰（审稿 issue 统计中杜撰/归属错误占 15%）。`scripts/check-cite-pages.py` 机器校验全过（当前 2502 个页码标签），每批重写后必须复跑。

**参照语料（Q10 定案）**
- 廖雪峰 js/python/java 教程、dbwu/eddycjy Go 文章、`downloads/` 里已核实的 Tony Bai《Go语言第一课》讲义与 krm 周课文档（Gin/GORM/K8s/可观测性等 21+ 讲）。进 PROMPT 的风格参照列表；事实与引注仍以 `work/text/` 为准。

## 4. 范围（Q1/Q10 定案）

- 对象：仓库内所有面向读者的文档。`guide/handbook/` 27 节优先，`notes/` 35 章按章排入后续批次；`docs/` 镜像与 README 类导航页按仓库 mirror 规则同步（`scripts/mirror.sh` 或单篇 frontmatter 规则）。
- 不在范围：`work/`、`audit/`、构建脚本、练习代码。

## 5. 流程与批审机器（Q5/Q6/Q10 定案）

1. **试产章**：04-interfaces（所有者最有意见、已有 8 条已落盘条目可对照、10-28 有一份即兴重讲素材）。试产 = **整章跑完**（04 章拆成约 13 个连续区块批次串行推进，每批 1-8 条目），全部落盘后 PROMPT 模板才算定稿；不是单批定模板。
2. **批次粒度（builder check #1，本方案拍板）**：沿用现有批审机器粒度，每批 = 一个连续区块 + 1-8 个条目（`batch.workflow` 上限、`apply.js` 唯一替换区块校验），不改机器。章节级主线靠**区块规划**保证：每章开工前先产一份区块规划（按三件套→地图→展开切分，写进批次任务描述），writer 在该区块内成稿，跨批连贯性由规划文档约束。同章**待审条目随风格批次一并送审**，重写正文必然覆盖它们，送审是防"84-91% 引用但从未对过原文"陷阱的唯一路径；落盘后按双审通过处置，台账进度跳变是预期效果。04 章 96 条待审 + 8 条已落盘全部按此进批。
3. **Java 侧事实依据（builder check #2，本方案拍板）**：澄清文档中两张对比表（java-go-polymorphism / vtable-itab）是**所有者已核准的事实底稿**（其内容在澄清过程中由本人看过并认可样张 D 及配套图）。引用方式：正文叙述不挂页码标签（`work/text/` 无 Java 机制原文可对），在节末"深读"里注明"Java 侧行为依据 JVM 公开规范与 HotSpot 公开资料，Go 侧见 TB29"；`check-cite-pages.py` 不受影响（它只校验 W/TB 页码标签）。这是对"事实以 work/text 为准"边界的显式放宽，仅限 Java/TS/Python 类比句，Go 侧事实仍逐条回原文。
4. **notes 通道（builder check #3，本方案拍板）**：notes 排期为独立阶段，开工前置两项工程（属构建脚本改造，已在范围内授权）：① `apply.js`/`handbook_validate.py` 的 `TARGET_RE` 扩展出 notes 路径规则（两处同步改，状态仓对等复刻不破坏）；② 台账补"单元→notes 章节"映射清点批次。notes 章多数无页码引注体系，风格批次只动承载句不新增事实主张，引注补录单列后续任务。开工时点：handbook 25 章全部落盘后。
5. **已落盘条目**：重写触碰的章节，其已落盘条目并入新一轮批次重走双审（处理状态记"风格重写"）；before 取**当前 handbook 文本**（apply 哈希规则要求唯一匹配），after 为新文本。台账进度不回退，旧 runId 保留。
6. **风格回退检查（builder check #4，本方案拍板）**：不改 `batch.workflow`/审稿 schema（动机器会破坏与 omp 18.11.1 的兼容链和状态仓对等复刻）。"百科腔回退"作为审稿**提示词约定**：双审任务描述里加一条"节奏/口吻回退到百科腔或表格拼贴也算 fail"，evidence 里写明位置；台账统计口径按 evidence 文本过滤。零机器改动，约束力靠提示词。
7. **工程章机制判据（builder check #5，本方案拍板）**：10-25 章"机制到位"= **把原文已有的机制讲透**（执行过程、数据流、失败路径讲到读者能预测行为），不要求超出语料的内部实现深度；审稿打回标准 = 语料里有而正文没讲透，而不是"不够深"。这与语言章（样张 D 对照）判据不同，写进 PROMPT 模板的分章说明。
8. **风格资产载体（builder check #6，本方案拍板）**：本设计方案 + 样张 C2/D 文本 + PROMPT 模板落在 `docs/ryugi/specs/2026-11-03-handbook-style-rewrite-design.md` 与 `docs/ryugi/specs/2026-11-03-style-samples.md`（随本方案提交入库），跨机经 git 可达；澄清 artifacts 留在 `.ryugi/` 仅作过程记录，不作为执行依据。样张文本从 artifacts 抄录成 Markdown。
9. **引注灰字实现（builder check #7，本方案拍板）**：渲染层一次性改动列入本方案范围：`docs/.vitepress/theme/` 增加一个 markdown-it 小插件把 `〔Wxx pN〕` 标签包 span 上灰（仿 mermaid-plugin 的挂法），随下一批 docs 镜像同步时验证渲染。硬规则：任何批次不得把标签改写成脚注等其它语法；`check-cite-pages.py` 复跑时命中数不得低于批前值（防"空转通过"）。
10. **纪律不变**：候选稿由 writer agent 产生、双审结论只能由审稿 agent 产生、先查再写台账、台账同步状态仓并互引 commit（CROSS-MACHINE.md）。

## 6. 验收（Q1 定案）

每节双重标准：
1. **体系可读**：目录/索引能一眼看出体系；节首三件套（或合规跳过）在位；叙事连贯无表格拼贴感（对照样张 C2）。
2. **机制到位**：核心机制讲到运行时/编译器行为层；04 章多态节含 Java↔Go 实现机制对比；引注可被机器校验通过。

读者测试按 skill 完整性规则执行：只读新文能答出，为什么需要此机制、例子发生了什么、何时用、边界在哪。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 机制段落写成百科腔，丢掉节奏 | 样张 C2/D 作为 PROMPT 少样本；双审任务加提示词级"节奏回退也算 fail"（§5.6） |
| 引注降权后审稿 agent 找不到 | 引注语法不变，只改视觉呈现（VitePress 插件）；check-cite-pages.py 命中数不得下降（§5.9） |
| notes 章节无批审先例 | TARGET_RE 扩展 + 单元映射补录为前置工程；先试产 p2-lang-core 再放量（§5.4） |
| 263 条已落盘条目重审拉长周期 | 与新批次同卷合并送审，不单开流程 |
| Java 侧事实无原文可回对 | 澄清期两张对比表经所有者核准为事实底稿；节末注明依据，Go 侧仍逐条回原文（§5.3） |
