P19 · 生态与常用库：选型地图 ​

这章学完你能干什么：拿到新需求（配置/日志/HTTP/队列）30 秒说出 社区默认选型和替代品；看懂 go.mod 里每个第三方库在干什么；知道 "标准库优先"铁律的适用边界。读者：读完 P8 和 P2.5。前置：无硬 依赖。后续：P9-P12、P13、P15 是本图四个格子的深潜版。

动手方式：本章命令都短，开终端跟着跑 go list -m all。

体系背景：去中心化的分发模型 ​

Go 生态的气质和 Rust 最大的不同，根源在分发模型：module path 即地址（github.com/jackc/pgx 直接就是导入路径），没有中心注册 表。crates.io 是中心化市场，Go 是"GitHub + proxy.golang.org 兜底 缓存"。

这个模型推出来三件事：

  1. 先看标准库能否解决问题：例如简单 HTTP 服务可以先用 net/http，再根据路由、中间件和团队需求评估框架。这是减少依赖的选型策略，不是分发模型保证的比例。
  2. golang.org/x/... 是 Go 项目的扩展库：例如 errgroup、singleflight 和 crypto 补充包。它们不属于标准库，升级时仍要检查版本、兼容性和维护状态。
  3. 读传递依赖名是免费课程：go mod graph 挑三个查 README， 比读十篇选型文有用。

从标准库开始评估 ​

先看需求能否由标准库满足；遇到缺失功能、维护成本或团队协作问题，再比较第三方方案：

领域标准库答案说明
HTTP 服务net/http1.22+ 路由模式匹配（r.PathValue），不用框架
HTTP 客户端net/httphttp.Client 连接池内置，配 Timeout
JSONencoding/jsonserde 对标（弱些但够用）
日志log/slog（1.21+）P15/P16 深潜
时间time不引 dayjs 类库
并发sync/channel锁、Once、WaitGroup 全在
并发模式golang.org/x/syncerrgroup/singleflight/semaphore
测试testing不用断言库（P2.5 讲过）
CSVencoding/csvExcel 才引 excelize
定时time.Tickercron 语义才引 robfig/cron

encoding/json/v2（实验性）：默认关，GOEXPERIMENT=jsonv2 才启用，默认构建直接编译失败（实测 "build constraints exclude all Go files"）。1.26 实测（本机 M4，100000x bench）：同一 struct Unmarshal v1 296.8ns/6 allocs vs v2 147.1ns/1 alloc（2 倍速、 1/6 分配），Marshal 两者相近（v1 71ns vs v2 136ns，v2 反而慢）。 API 定型前别上生产。

什么时候考虑第三方：标准库没有的领域，如数据库驱动（database/sql 只是接口）、gRPC、指标和分布式追踪；标准库已有基础能力但项目需要更丰富功能时，也可以按成本选库。

新库评估四信号 ​

重要性递减：

  1. 谁维护：看维护责任、发布节奏、问题处理和安全响应，不仅看组织或个人身份。
  2. 生态契合：涉及取消的操作是否支持 context.Context；错误是否按需支持 errors.Is/errors.As；日志能否接入项目现有体系。
  3. 替换成本：检查实际使用的 API、数据模型和数据库方言。pgx 的 database/sql 驱动接口与原生 pgx API 是不同的接入方式，接口相同也不意味着 SQL 可无代价换库。
  4. 衰退信号：README 写 maintenance mode、长期未处理的重要 issue 等都值得调查；稳定的小工具提交少并不自动意味着不可用。

对照：crates.io 的 download 数 ≈ pkg.go.dev 的 import 数 （go.dev/pkg?importers 可查）。

观察题：

  1. go list -m all 找出 prometheus/client_golang 的传递依赖， 对照本章表格认领。
  2. go generate ./exercises/p19eco/ 跑 stringer，看生成的 level_string.go（P1 generate 节 + P2.5 惯例的合流）。

预测题（跑之前写答案）：

  1. TestPingCtx 里用已取消的 ctx 调 Ping，会等一小时超时吗？ 返回什么错误？
  2. TestStringer 的 Warn.String() 返回什么？为什么是小写 （-linecomment）？

改造题（在练习包里）：

  1. TestSlogHandler：给只打 level>=warn 的自定义 Handler 补全 Enabled 方法：体验"生态库全长在标准库接口上"。
  2. TestFunctionalOptions：把 NewServer(addr) 补成 functional options（WithTimeout/WithLogger）。

小结 ​

  1. 标准库是选型起点，不是禁止依赖的铁律；golang.org/x/... 是独立版本的 Go 项目扩展库。
  2. 默认选型：slog（日志）、net/http（服务）、pgx+sqlc+goose （PG 栈）、client_golang（指标）、cobra（CLI）、asynq/river （队列）。
  3. 本仓库 7 个主干依赖每个都能对上地图的格子。
  4. 评估新库：维护者 → 生态契合 → 替换成本 → 衰退信号。
  5. 选型偏离默认要有理由，理由写在 go.mod 旁注释或 README。

章末参考 ​

functional options（对照 Rust builder） ​

go
type Server struct {
    addr    string
    timeout time.Duration
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }

func NewServer(addr string, opts ...Option) *Server {
    s := &Server{addr: addr, timeout: 5 * time.Second}   // 默认值
    for _, o := range opts { o(s) }
    return s
}

srv := NewServer(":8080", WithTimeout(10*time.Second))

进阶形态：Option 改成 interface{ apply(*Server) } 支持错误返回 （grpc-go 的风格）。标准库不用这招（http.Server 直接公开字段）， 内部库才讲究，写业务代码别过度设计。

值得知道的两个库 ​

  • singleflight（golang.org/x/sync/singleflight）：同 key 并发 请求合并成一次调用，缓存击穿的官方解。
  • uber-go/goleak：测试检测 goroutine 泄漏，P14 手写 NumGoroutine 的库化版本（defer goleak.VerifyNone(t)）。
