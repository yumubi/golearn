P21 · testing/synctest + fuzz：时间与输入的测试武器 ​

这章学完你能干什么：给 Retry（指数退避）和 Debounce（防抖）写 毫秒级全绿的测试，不发一条真实 Sleep；给 CLI 解析器挂 fuzz 目标， 60 秒跑两千万个输入。读者：读过 P3、P14、P8。前置：会写表驱动 测试。

动手方式：go test -race ./exercises/p21test/ 起步，fuzz 部分 真跑 60 秒拿自己的 execs 数。

体系背景：计时器是运行时的，不是语言 ​

time.Sleep 不是一个循环加轮询。Go runtime 给每个 P 维护四叉堆 计时器，Sleep/NewTimer/time.After 全是往这个堆里塞事件，由 调度器统一触发。这个事实是 synctest 的可行性来源：runtime 既然 统一管理计时器，就能在测试时把整套计时器换成假时钟。

1.25 转正的 testing/synctest 就是干这个的：把测试扔进"气泡" （bubble），假时钟瞬间走完。这和 Rust 侧 tokio 的 start_paused（tokio::time::pause()）是同一设计：测试时暂停 时间，idle 时自动跳到下一个 timer。差异在挂载点：tokio 挂在它的 异步运行时上（要求 current_thread），synctest 挂在 Go runtime 上， 普通同步代码也能享受。发起输入侧，Rust 有 proptest（结构化策略

  • shrinking）和 cargo-fuzz；Go 的 go test -fuzz 标准库自带。 对照全表在章末。

fuzz 则是另一面：CPU 随机数 + 覆盖率引导，几千万个输入扫不变量。 synctest 不需要注入：time.NewTimer/AfterFunc/Sleep 走的是 同一套 runtime 计时器，bubble 直接把它换成假时钟，函数自己毫不知情：

go
synctest.Test(t, func(t *testing.T) {   // bubble 内
    start := time.Now()
    Retry(ctx, RetryOptions{Max: 3, Base: 100 * time.Millisecond},
        func() error { return errors.New("boom") })
    // 两次退避 100+200ms，虚拟时间恰好走到 300ms
    if time.Since(start) != 300*time.Millisecond { t.Fatal(...) }
})  // 真实耗时：毫秒级

午夜。bubble 开头打印 time.Now() 即可确认：

text
=== RUN   TestVirtualStart
    vt_test.go:11: bubble start: 2000-01-01 00:00:00 +0000 UTC
--- PASS: TestVirtualStart (0.00s)

虚拟时间走 300ms 还是 100 小时，真实 CPU 时间只取决于代码执行量：

sh
$ go test -race -run TestRetryVirtualTime -v ./exercises/p21test/
--- PASS: TestRetryVirtualTime (0.00s)   # 真实 0.00s，虚拟 300ms

不注入的代价：真时钟路径（工具 retryrun 的 main 函数）没法用 bubble 测，只能靠子进程冒烟（跑一次看退出码）。P21 选简单性， 理由是原语足够小。

Sleep 版有多糟，实测说话：等价逻辑用真时钟写（wait=2ms， 每轮 50 次 Call），真机压测：

形态配置结果
真时钟 Sleep 版-count=150 -cpu 13 次 FAIL（timer 触发落在断言窗口外/旧 timer 抢先），150 轮耗时 2 分钟
synctest 版同逻辑 -race -count=1全绿，毫秒级；时间推进是确定性事件

压不出红的注意：这个 flake 是调度相关，负载重的机器更常见。 "偶尔 CI 红、重跑就好"的经典形态，synctest 不是缓解，是消灭。

synctest.Wait 与 durably blocked ​

synctest.Wait 等 bubble 里除当前 goroutine 外的全部 goroutine 进入 durably blocked。这里的“durable”指只能由同一 bubble 内的事件解除的阻塞，不能依赖 bubble 外部的活动；不是说阻塞本身无需事件就能继续：

算 durably blocked不算
bubble 内 channel 的收发 / selectsync.Mutex 的 Lock（等持锁者放行）
sync.Cond.Wait真实 I/O（文件、网络）
WaitGroup.Wait（Add 在 bubble 内）系统调用（cgo、fork）
time.Sleep / 计时器等待

时间推进条件同源：全部 goroutine 都 durably blocked 时，假时钟 直接跳到最近的未来事件。有一个 goroutine 卡在锁或 I/O 上，时间 就不动，Wait 也不返回。

"锁不算"的实测证明：子 goroutine mu.Lock() 卡住（非 durable），主 goroutine time.Sleep(1ms) 后调 Wait()。真机 1.26.4 输出：

text
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [synctest.Run (durable), synctest bubble 1]:
goroutine 21 [sync.Mutex.Lock, synctest bubble 1]:

注意层次：不是 synctest 的 panic（recover 可捕获）、不是挂死， 是 runtime 的 fatal deadlock，退出码 2。官方文档没写清这条，是 实验抓出来的。锁不进 durable 清单，意味着"等锁"永远不能作为 bubble 的时间推进源。

-race：动态分析武器 ​

-race 不扫代码，是 happens-before 动态分析（向量时钟插桩）： 只抓实际发生的竞争路径，所以要多跑（-count）配合不同调度。 两 goroutine 无锁自增 1000 次，detector 把双方栈都点出来（真机 输出节选）：

text
==================
WARNING: DATA RACE
Read at 0x00c0001b81e8 by goroutine 8:
  p21test.TestRaceDemo.func1()  race_test.go:16
Previous write at 0x00c0001b81e8 by goroutine 9:
  p21test.TestRaceDemo.func1()  race_test.go:16

退出码非 0，CI 直接红。-race 可与 fuzz 同跑（实测 execs 从 40 万/s 掉到 6 万/s，慢 6 倍），日常排期先 fuzz 后 race。

bubble 的三种死法 ​

都在 TestBubbleHangs/TestGoroutineLeakDetection 以子进程隔离 演示（源码 retry_test.go 的 deadlockProbe 常量）：

场景形态真机输出退出码
全部 durable 且无人唤醒synctest panicPANIC: deadlock: all goroutines in bubble are blocked7（probe 自定）
卡非 durable（锁）runtime fatalfatal error: all goroutines are asleep2
泄漏：有 goroutine 未退出收尾 panicmain bubble goroutine has exited but blocked goroutines remain7

第三种最有用：泄漏自动指认。bubble 根函数返回时，任何还卡在 bubble 内 channel 上的 goroutine 都触发 panic，输出直接点出泄漏 位置。对比 P14 的 NumGoroutine 计数法（自己写回落断言），这是 零成本内置的。代价：泄漏必须阻塞在 bubble 内通道上，卡真实 I/O 的照旧测不到。

为什么用子进程：两种 panic 一种 fatal，都会带崩测试二进制， 包内跑不得。惯例：t.TempDir() 写 main.go → go build → exec.Command 跑 → 断言 stderr 和退出码。

fuzz：性质测试 ​

fuzz 适合纯函数 + 输入空间大 + 有不变量的目标。P8 的示意 fuzz 函数是极简版，这章给真目标：P20 wcgo 的 ParseArgs （exercises/p21test/fuzz_test.go）。三个性质，全是"任何输入都 必须满足"：

  1. 不 panic：坏输入只该产生错误（fuzz 框架隐式检查）。
  2. 错误必然包装 ErrUsage：出现其他错误类型就是破坏契约。
  3. ExitCode 只落 {0, 1, 2} 且与错误自洽。
go
func FuzzParseArgs(f *testing.F) {
    seeds := []string{"", "-v", "-v -q a.txt", "-x",
        "file1 file2 -v", "-verbose", "-v -v -v f",
        "文件-µ-🎉 -v", strings.Repeat("-a", 100)}
    for _, s := range seeds { f.Add(s) }
    f.Fuzz(func(t *testing.T, cmdline string) {
        args := strings.Fields(cmdline)   // 空格分隔编码 argv
        cfg, err := p20cli.ParseArgs(args)
        if err != nil && !errors.Is(err, p20cli.ErrUsage) { t.Fatal(...) }
        code := p20cli.ExitCode(err)
        if err == nil && code != 0 { t.Fatal(...) }
        if err != nil && code != 2 { t.Fatal(...) }
    })
}

fuzz 的语料是资产：新发现的 interesting 输入保存在 fuzz 缓存，失败输入通常写入 testdata/fuzz/。普通 go test 不带 -fuzz 时重放 f.Add 种子和 testdata/fuzz/ 中的语料，不会把缓存里的全部 interesting 输入当作普通回归用例：

sh
$ go test -run FuzzParseArgs ./exercises/p21test/
ok  	golearn/exercises/p21test	0.209s

要把某个重要输入长期纳入普通 CI 回归，应将它保存到 testdata/fuzz/ 或显式加入种子，而不是依赖机器本地的 fuzz 缓存。

种子质量决定起步：空输入、未知 flag、unicode、超长串，每条覆盖 一个分支。fuzz 参数只支持基本类型（[]string 不行），用空格分隔 串编码 argv 是权宜。

60 秒实测（go1.26.4，M 系列 10 workers）：

text
fuzz: elapsed: 1m0s, execs: 28529755 (0/sec), new interesting: 188 (total: 199)
PASS

这次运行尝试了 2850 万个输入、没有发现 crash；新发现的 interesting 输入保存在 fuzz 缓存中，后续 fuzz 可利用它们，普通测试不会自动重放缓存。

fuzz 能抓到什么，演示一次：把 ExitCode 的 usage 分支 return 2 改成 return 3（植入 bug），种子语料直接命中：

text
--- FAIL: FuzzParseArgs
    --- FAIL: FuzzParseArgs/seed#4
        fuzz_test.go:57: usage error maps to 3, want 2

例子只覆盖 -x 这一路；性质为每个实际运行的输入检查 usage 错误映射，但有限次 fuzz 不能证明所有可能输入都满足性质。

sh

预测题（跑之前写答案；猜错的地方才是认知边界）：

  1. TestRetryVirtualTime 把 Base 改 100ms、Max 改 4，虚拟 elapsed 是多少？封顶 Cap: 300ms 时呢？
  2. TestRetryCancelDuringBackoff 在第 50ms 取消（第一次退避 100ms 中点），返回 context.Canceled 还是 fn 的错误？虚拟 elapsed 是 50ms 还是 100ms？
  3. TestDebounceSynctest 里 3 次 Call 连发后 Wait 返回时 fired 是多少？虚拟时间走满 200ms 后呢？
  4. 把 Retry 的 sleepCtx 换成裸 time.Sleep(wait)，取消响应 会怎样退化？
  5. -race 和 -fuzz 能同跑吗？能的话 throughput 掉多少量级？
  6. fuzz 跑出的 250 个 interesting 输入存在 testdata/fuzz/ 吗？ （提示：什么才落盘。）

改造题：给 Retry 加抖动：wait = Backoff(...) + rand(0, wait/4)。 bubble 里 rand 不确定会让虚拟账本对不上。提示：把 rand 抽象成 func(n int64) int64 注入固定值，或断言区间 100ms ≤ elapsed ≤ 125ms。

Take-away ​

  1. synctest 提供 bubble 内的虚拟时间，无需为这些计时器注入时钟；它能消除依赖真实等待的部分不稳定性，但不能保证所有并发测试没有 flake。
  2. Wait 等的是 durably blocked：bubble 内 channel/Cond/WaitGroup/ Sleep 算；锁、真实 I/O、系统调用不算。一个 goroutine 卡锁， 全场时间静止（真机 fatal 实证）。
  3. bubble 三种死法要认得：synctest panic / runtime fatal / 泄漏 收尾 panic。演示一律子进程隔离。
  4. fuzz 挂性质（不 panic/错误分类/映射域），以种子覆盖重要分支，再用生成的输入寻找反例；有限测试不能证明全称命题。
  5. 真时钟路径（main）不在 bubble 射程内，子进程冒烟 + 退出码 断言兜底。
