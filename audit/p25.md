## 零发现自检

- golang:1.26-alpine 的 351MB 是 docker images 圆整值，inspect .Size 精确字节 68704536 也核过，圆整方向正确，查过无问题
- golearn-httpkv:ms 26.6MB 与 docker system df -v 的 SIZE/UNIQUE SIZE（26.6MB/16.47MB）三口径互证，查过无问题
- alpine:3.22 基础层 10.2MB 与 docker images 显示的 28.2MB 差异是"解包后 vs 传输压缩层"口径差，history 记录的是层内容 10.2MB，笔记用 history 口径无错，查过无问题
- 镜像 RootFS.Layers 恰 2 层（alpine 单层 + COPY 一层）与"两层=基础+二进制"断言一致，JSON 层 ID 逐个对过，查过无问题
- 探针程序输出格式 `GOMAXPROCS= 2 NumCPU= 10` 与笔记 L124 实拍逐字符一致（含空格），查过无问题
- 无限额容器 cpu.max 为 `max 100000`，runtime parseV2Limit 对 "max" 走 no-limit 分支（cgroup.go:78-82），与无限额→10 的实测互证，查过无问题
- 1 核限额→GOMAXPROCS 2 的"反直觉"档位是 ceil 与下限 max(limit,2) 共同作用，源码行号已钉（cgroup_linux.go:97-100），查过无问题
- GODEBUG 默认值跟 go.mod 语言版本走（P22 §GODEBUG）：go.mod 声明 go 1.26 时 containermaxprocs=1 生效，容器内探针实测即证据，查过无问题
- USER nobody 之后镜像内 /usr/local/bin/httpkv 对 uid 65534 可执行（起栈 healthy 证明服务能起），无权限回归，查过无问题
- EXPOSE 8090 是元数据不占层体积，history 0B 已验；healthcheck 若写在 Dockerfile 也是元数据层，速查表口径一致，查过无问题
- 容器内 alpine 自带 /usr/bin/nc（busybox），nc -z 探活无需 apk add，healthcheck 依赖成立，查过无问题
- memory.max=67108864 恰为 64MiB（64×1024×1024），docker 对 `--memory 64m` 的 MiB 换算核实，查过无问题
- 台账证据用到的临时容器（hk-lim/hk-mem 等）与 /tmp/probe 已清理，docker ps -a 无残留，查过无问题
