# Go 教程写作与重写

## 先读状态，再动手

本仓库的改写不是从零开始。动手前必读三份状态，避免重复劳动或推翻已双审的内容：

1. `audit/entry-ledger.jsonl`：原材料条目台账，3713 条，`处置` 字段是唯一进度事实。只有 `已落盘(双审通过)` 的条目经过独立双审；`待审`（约 2777 条）只是"预审认为完整"，从未逐条对过原文。
2. `audit/handbook-scenarios.jsonl`：场景表。`已落盘(双审过)` 的场景可信；`预审认为完整,待独立复核` 是空声明（`runId` 为空、无复核记录），不能当作完成。
3. `CROSS-MACHINE.md`：单批审读流程、纪律（双审结论只能由审稿 agent 产生、先查再写台账）和欠账快照。

历史教训（来自 28 个批审 run 的 51 条审稿 issue 统计）：候选稿缺内容 58%、杜撰或归属错误 15%、before 复制失真 5%、行号引注失配 5%。下方各节规则都针对这些实际失败模式。

## 目标

写给希望建立 Go 知识体系的开发者，尤其是已有 Java、TypeScript、Python 或其他语言经验的读者。教程不只是列出规则和最佳实践：要让读者看到问题，跟着代码理解机制，再知道如何判断和使用。

借鉴廖雪峰教程的教学组织：从已知代码出发，通过一个具体问题逐步修改例子，展示结果，再解释原因；不要照搬原文、示例或口头禅。可参考 [Python：继承和多态](https://liaoxuefeng.com/books/python/oop/extend/index.html)、[JavaScript：闭包](https://liaoxuefeng.com/books/javascript/function/closure/index.html)和 [Java：接口](https://liaoxuefeng.com/books/java/oop/basic/interface/index.html)。`guide/handbook/04-interfaces.md` 的“二、接口”可作为本仓库现有样例，而不是每篇都要套用的模板。

## 工作步骤

1. **确定范围和读者。** 先读目标章节、上下文及相关代码或原材料。确认读者已有的知识、需要解决的问题、章节在全书中的位置。范围不明时从用户指定章节或示例入手，不擅自改写全书。
2. **梳理内容。** 列出必须保留的正确事实、示例、条件、边界、引用和与其他章节的连接；找出跳步、重复、错误、过时内容和只是罗列术语的段落。区分原材料事实与自己的解释，不凭记忆编造源码行为或引用。
3. **设计一条教学主线。** 用读者熟悉的代码或具体任务开场，让问题自然出现。选择一个可逐步演进的例子，安排“当前做法 → 遇到限制 → 一次修改 → 输出或行为 → 原因 → 下一问题”。不为凑结构强行制造问题；一个例子承载不了的主题可以拆为连续小节。
4. **写出推导。** 每段代码前说明为什么要看它；代码后解释关键调用、数据变化和读者应观察的结果。先展示现象，再引入术语和规则；不要把核心机制压成一句结论。必要时展示失败或反例，说明错误原因及适用条件。
5. **建立体系。** 当比较确实能帮助理解时，对照 Java、TypeScript、Python 等读者熟悉的概念，指出共同点、关键差异和类比的边界。解释 Go 的设计取舍：机制解决什么问题、带来什么代价、适合何时使用；不要把某条经验规则说成语言强制或普遍真理。不要为了讲哲学偏离正在解决的问题。
6. **处理细节与删改。** 默认保留已有的正确知识、推理、例子与深度；修改结构和语言不是删减知识的许可。基础行为先讲透，再讲条件、陷阱和高级内容；不要为了主线简短，将正文中的必要解释降级为一句话、参考链接或附录里的术语清单。仅对确实重复、错误、过时或不属于用户要求范围的内容做有依据的处理，遵循下方完整性检查。
7. **验证。** 独立检查每个可运行例子的输出和关键失败示例；明确片段是否依赖前面的代码，标明有意不能编译的例子。核对新旧内容、来源、交叉链接和技术版本。构建或实际查看修改后的页面，依据仓库约定同步源文件与站点镜像；不要重写无关文件。未能验证的内容明确说明。

## 完整性：改写不能变成压缩

适用范围内，原文正确的教学内容是基线，即使它写得零散、冗长或不好懂，也不能因此删掉。更换例子时，必须保留原例所展示的不同机制、条件和结论；新例子只覆盖其中一部分时，补齐其余部分，不以“已举过例子”视为覆盖。适当增加篇幅，优先讲透而不是追求短小。

对每个待改的章节或连续区块，在修改前建立可复核的覆盖清单（可使用任务记录或临时工作记录，不必新增仓库文档）：

1. 逐段记录知识点及其具体内容：定义、工作过程、前提条件、因果、步骤、输入输出、边界、错误处理、取舍、对比、例子、练习、引用及版本条件。大章节分小批读取，截断部分补读；不能只根据标题、摘要或知识点名称判断内容。
2. 对每一条记录改写后的具体落点与处理方式：保留、展开、迁移、合并、纠错或删除。迁移须实际落在可访问的章节，并更新必要链接；不能只写“见别处”而没有完整内容。不要把核心教学内容只移到不解释的附录、速查表或外部链接。
3. 逐项对照改前和改后：读者能否仍然从新文中获得同样的条件、机制、推理链和操作细节？概念名称出现、代码存在或字数相近不等于覆盖；用旧内容中的具体问题检查新文能否回答。
4. 删除或合并必须有具体依据：重复内容要核对剩余位置确实覆盖全部不同细节；错误或过时内容要核实依据并写出适用版本；有疑问时先保留并查证，不以“无教学价值”作为未经核查的删减理由。用户明确要求删改时，仍保留未要求删除的正确知识。
5. 核查既有引用是否支持附近的论断；重新组织或纠错时保留可追溯性。原文和引用不一致、来源不可读或事实无法确认时，不编造解释或页码；保留可确认部分并明确标注未决项。

## 批审机器：什么算"改完"

"自己觉得写清楚了"不算完成。本仓库的完成判定是条目级的：

- **只有 `已落盘(双审通过)` 的条目算改完。** 依据是 `audit/handbook-applied/` 的 apply 回执（runId + before/after + 双审记录），不是正文里有没有引用标记。
- **场景表 `预审认为完整,待独立复核` 等于未审。** 这种声明没有 runId、没有复核记录，条目层往往还是几百条 `待审`（例：SC-auth 声称完整，条目层 358 条待审）。要让它变可信，只能走批次。
- **`notes/` 从未进过批审**（所有 apply 回执的 target 都是 `guide/handbook/`）。notes 的"重写"只有基线改造、批4（P13-P18）和 GLM 措辞轮，没有条目级证据。

走批审的入口（详见 `CROSS-MACHINE.md` 和 `.omp/handbook/README.md`）：

1. 从台账挑同一单元/场景的 5-8 条（场景表"待独立复核"优先；已知欠账：SC-ledger 的 W16-2#K15/K18）。
2. `node .omp/handbook/prepare.js <target> <items> <任务说明>` 生成调用参数，交给 `xd://workflow`（name=handbook-batch）。同一目标章节只有一个在途批次；文件变了旧 revision 作废。
3. `status=reviewed` 才能 `node .omp/handbook/apply.js <runId>`（先 `--check`）。blocked/needs_rework 都未完成，不许落盘。
4. 回填台账（处置/runId/回执），`python3 audit/mirror-scen.py <runId> <sceneId> <注记>` 更新场景表，然后引用守卫 + eslint + 单独 commit（格式：`SC-xxx: N 节主题 Y 条双审落盘(要点)`），push 前先 push 状态仓。

不用批审的改动（措辞修正、术语统一、时长重算）可以直改，但不得在台账里标成任何"已审"状态；这类改动不算消化原材料条目。

## 审稿 issue 的常见失败模式（写作时预防）

以下来自实际返工记录（15/28 批次返工过），写候选稿时逐条自检：

1. **缺内容**（58%）：digest 里有 D1-D3/易错点，候选稿只写了标题口号或"上一节讲过"。规则：每个 requiredId 的 facts 里列出的每个机制、条件、异常分支都要在 after 里找到承载句；"已在别处讲过"必须给出真实可读的落点，读者不用回原文。
2. **杜撰与归属错误**（15%）：把"本节没有的表述"冒充本节已有（如"正好对应本节开头"），给 account 字段挂上只属于 uid 的注释，断言"四个专题"而原文是五个。规则：每个论断的归属（本节/别章/原文注释/教学推导）逐一核对；不确定就进 blockers，不编。
3. **before 复制失真**：before 必须与目标文件逐字节一致（工具行号前缀、OCR 字符差异都会导致 apply 失败）。落盘前用唯一匹配校验。
4. **行号引注失配**：源码引用的行号要覆盖被引论断的实际语句（"37 行是 t.Fail()，35 行才是注释"）。新引文先读原文对应行。
5. **数值与代码细节**：DSN、状态码、EXPECT 参数、逗号全半角，照原文抄；有意省略凭据时显式标注（`root:**`）。

## 写作约束

- 每个小节回答一个清楚的问题；概念和代码一次引入到读者能消化的程度。沿用同一案例时，明确哪些代码沿用、哪些代码发生变化，避免读者反复重建上下文。
- 代码服务于讲解，不用大型项目脚手架掩盖核心机制；示意行为要标明，生产场景的错误处理、并发和安全边界不能被误称为已实现。
- 输出要与可执行代码一致；编译错误要说明错误触发条件。不要编造运行结果。代码片段可用于推导，关键示例应提供可独立运行的完整版本。
- 口语化可以帮助交流，但亲切措辞不能替代解释。避免"显然""正解""必然""越小越好"等掩盖条件的说法，也不要靠大量表格、术语、原则和小结代替推理。
- 对比其他语言时要区分相似的目的与不同的语义；例如 Go 接口可类比静态检查的鸭子类型，但方法集合、指针和值以及类型断言仍需按 Go 规则解释。
- 引用应支持附近的具体论断，保留项目已有的来源格式；新引文先核对原文，不为凑引用推测页码。运行时内部实现及历史行为要注明版本边界。
- 不以缩短篇幅、编译通过或例子能跑作为教学完成的证明。改写前后核对：读者能否解释为什么需要此机制、例子中发生了什么、何时采用以及边界在哪里。
- 引用数量、关键词命中和页码交集不能当语义完整的证据（GLM 轮的教训：handbook 多章 84-91% 的 bullet 带引用标记，但条目层从未逐条对过）。报表必须分列"引用页交集"和"逐条语义处置"，不许混成一个百分比。
- 汇报禁用无证据完成语："已保留全部""预审认为完整""全部章节审读完成"在没有 runId/回执支撑时一律不许出现在状态文件或最终报告里。

## 本仓库落点

- 手册源文件在 `guide/handbook/`，站点镜像在 `docs/handbook/`；`notes/` 与 `docs/` 也有镜像关系。修改前先检查文件及现有生成方式，保持对应内容一致。
- `scripts/mirror.sh` 会镜像整个 `notes/` 和 `guide/handbook/`，调用前确认不会覆盖无关的用户改动；若只改一篇，可按同样 frontmatter 规则同步该篇。
- 站点构建命令见 `package.json` 的 `docs:build`；可运行 Go 示例应实际运行，页面布局变动应检查渲染结果。按修改范围汇报验证和未验证项。

## 两层内容与各自欠账

手册（`guide/handbook/`）与细节库（`notes/`）分工不同，改法也不同：

- **handbook 是读者主路径**，条目级批审只覆盖了它的一部分（16 个批全部指向 handbook；01、03-10、23-25 等章引用 bullet 占比 77-91% 但从未进过批审）。handbook 的改动默认走批审机器。
- **notes 是细节库**（35 章，约 1.3 万行），从未有条目级批审。它的"重写"史 = 10-12 基线改造 + 批4（P13-P18）+ GLM 措辞轮（4da43c8）。把 notes 当"已优化完毕"没有依据；按章节逐一对照 digest 判断哪些章需要真重写，是明确的待办而不是已完成项。
- 原材料入口：`work/digest/<单元>.md`（条目摘要）与 `work/text/<单元>.txt`（原文页面）。二者不入库；状态仓 `~/Dev/golearn-state`（或远端 golearn-state）保存台账与场景表，**台账改完必须同步状态仓并互引 commit**。
- 台账里 `待清点` 591 条（旧台账漏收的 digest 条目）要先补录清点再谈覆盖；`有理由省略` 182 条中 18 条是必读条目（如 my_goframe 分层骨架），省略理由要能回答"为什么不影响主线"。
