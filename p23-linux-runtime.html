P23 · Linux 运行时：进程、信号、fd 与容器 ​

这章学完你能干什么：解释 Ctrl-C 到优雅关停之间 OS 层发生的每一步； 用 lsof 读一个进程的 fd 表；把 httpkv 塞进容器并解释"为什么 SIGTERM 不处理会在宽限期（Linux 容器默认 10 秒）后被 SIGKILL"。 骨架：把 httpkv 从裸跑跑到 docker run。读者：读完 P8（httpkv 就是这章的道具）。前置：无。

实战说明：本机是 macOS（本教程开发机），strace/cgroup 部分 给 Linux 命令与预期输出，其余全部实拍。

体系背景：你的 Go 进程在 OS 眼里是什么 ​

Rust 程序员对这层的直觉是现成的：std::process::Command 起的进程、 libc 的 signal、std::os::fd，和 Go 共用同一个 OS 接口面。语言差异 在“谁替你包装”：Go runtime 提供信号通知；Go 1.25 起，在适用的 Linux 配置下还会参考 cgroup CPU 限额设置默认 GOMAXPROCS。 具体版本及覆盖条件见 P25。

go build 的产物是一个普通的可执行文件。OS 运行它时给三样东西： 一个 PID、一张 fd 表、一组信号处置。进程活着 = 内核任务结构 存在；打开文件或 socket 会占用文件描述符；终端里的 Ctrl-C 通常 向前台进程组发送 SIGINT。进程还使用内存、系统调用等其他 OS 接口； 本章先聚焦 PID、fd、信号与容器限额之间的关系。 这章把包装拆开。

进程：PID 与退出码 ​

sh
$ go build -o /tmp/httpkv ./exercises/p8fast/httpkv/
$ /tmp/httpkv &
$ pgrep -f "^/tmp/httpkv"
91736                     # ← OS 分配的 PID
$ wait $!                   # 等后台 httpkv 退出，再读取它的状态
$ echo $?                   # 0 表示正常退出

每个进程有父进程（PPID）。shell 启动的程序，父就是 shell；容器里 PID 1 是入口进程时尤其要留意信号：Linux 对 PID namespace 中的 init 进程有特殊限制，未安装处理器的信号可能不会按普通进程的默认 方式终止它。容器停止的宽限期可配置；Docker Linux 容器通常默认 10 秒，超时后才发送 SIGKILL。

$? 是 shell 上一条命令的状态；等待子进程后才是该进程的状态。 shell 对信号终止通常编码为 128+信号号，具体表示取决于 shell：

sh
$ sh -c '/tmp/httpkv & P=$!; sleep 1; kill -9 $P; wait $P; echo exit=$?'
sh: line 1: 74043 Killed: 9  /tmp/httpkv
exit=137                     ← 128 + 9（SIGKILL）

进程是从哪个二进制起的、什么版本编译的，现场可查（P22 的 buildinfo 落地）：

sh
$ go version -m /tmp/httpkv | head -2
/tmp/httpkv: go1.26.4
	path	golearn/exercises/p8fast/httpkv

信号：SIGTERM 送达之后 ​

信号是内核发往进程的异步通知。默认处置四种：终止、终止+core、 忽略、停止、继续。未注册通知时 SIGTERM/SIGINT 通常使程序终止， 不会执行应用层的优雅关停流程，因此需要先注册通知：

go
// exercises/p8fast/httpkv/main.go:173
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
// ... srv.ListenAndServe()
<-ctx.Done()          // 收到 SIGTERM：NotifyContext 把 ctx cancel
logger.Info("shutting down")
shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
defer cancel()
srv.Shutdown(shutdownCtx)   // 停止接新连接，等在途请求收尾

（Rust 侧对照：signal-hook 的 flag 位是同样思路，信号只置位， 主循环轮询；tokio::signal 干脆把接收做成 stream。套路相同。）

真机实证（kill -TERM 后进程自己打出日志、端口释放）：

sh
$ /tmp/httpkv > /tmp/httpkv.log 2>&1 &
$ kill -TERM $(lsof -ti :8090)
$ grep shutting /tmp/httpkv.log
{"level":"INFO","msg":"shutting down"}
$ lsof -ti :8090 | wc -l
0                        # ← 端口干净释放

时间线：SIGTERM 由内核投递 → os/signal 通知使 context 取消 → main 从 <-ctx.Done() 醒来 → Shutdown 等待普通 HTTP 请求收尾。 退出状态还取决于程序如何处理错误；Shutdown 不等待被 hijack 的连接。

两条铁律：不捕获 SIGKILL/SIGSTOP（内核保留，容器强杀就是它）； 信号只发通知，清理逻辑写在主流程里（Shutdown），不要塞 handler。

对照组（真跑）：SIGKILL 下没有日志、没有 Shutdown：

sh
$ nohup /tmp/httpkv > /tmp/hk.log 2>&1 &
$ kill -9 $(lsof -ti :8090)
$ grep -c shutting /tmp/hk.log      # ← 0：一行日志都没来得及打
0
$ lsof -ti :8090 | wc -l            # 端口释放，但是内核代劳
0

shut-log=0 说明这次 SIGKILL 没给应用执行清理流程的机会：内核回收进程。 （docker kill）就是这个语义，P25 的优雅关停窗口靠 docker stop 的 TERM 先行才存在。

fd：一切 I/O 的把手 ​

Unix 用 fd 表管理文件、socket、pipe 等 I/O 句柄；惯例上 0=stdin、1=stdout、2=stderr。关闭后的编号可以被后续打开操作复用。

sh
$ lsof -p $(pgrep -f "^/tmp/httpkv") | awk '$4 ~ /^[0-9]+[uwr]$/ {print $4, $5}' | head -6
0u  CHR      # stdin：终端
1w  REG      # stdout：重定向到的日志文件
2w  REG      # stderr：日志文件（stdout 同一文件）
...
sh
$ lsof -p <pid> | grep -c TCP
2                        # :8090 监听 + :6060 pprof 监听（P22 的端点）

和 Go 代码对上：net.Listen → socket fd；os.Open → 文件 fd； log/slog 写 os.Stderr → fd 2。"日志进 stderr"（P20）在 OS 层 就是写 fd 2，docker 的日志驱动收的正是容器的 fd 1/2 字节流。

fd 泄漏是长进程的经典死法：每请求开文件不关，fd 表涨到 ulimit -n（Linux 默认软限常是 1024；macOS 现代版本 1048576， ulimit -Sn 实测），再 open 就是 EMFILE。Go 的 defer f.Close() 和连接池都是防它的。

真机全表（nohup 启动，真输出）：

text
$ lsof -p $(lsof -ti :8090)
COMMAND   PID USER   FD     TYPE  NODE NAME
httpkv  71181 akka    0u     CHR   338  /dev/null      ← nohup 把 stdin 挂到 null
httpkv  71181 akka    1w     REG  78103  /tmp/hk2.log   ← stdout 重定向
httpkv  71181 akka    2w     REG  78103  /tmp/hk2.log   ← stderr（slog 默认目标）
httpkv  71181 akka    3u    PIPE                    ← runtime 内部管道

fd 0/1/2 的去向完全由启动方式决定（nohup、>log、终端）， 进程自己决定 3 号以后开什么。看懂这张表 = 看懂容器日志驱动 （P25）和 docker exec 的 I/O 接线。

容器：隔离的三件套 ​

容器不是轻量虚拟机，是三样内核机制的包装：namespace（看见 什么：PID/网络/挂载点各自独立）、cgroup（能用多少：CPU/内存 限额）、联合文件系统（镜像分层，P25 展开）。

httpkv 容器化全程（真跑）：

sh
# 1. 在构建上下文中生成 Linux ELF（架构需与目标机器匹配）
$ CGO_ENABLED=0 GOOS=linux GOARCH=arm64 \
  go build -trimpath -ldflags="-s -w" -o httpkv ./exercises/p8fast/httpkv/
$ file httpkv
httpkv: ELF 64-bit LSB executable, ARM aarch64

# 2. 镜像：alpine 垫底 + 一个二进制（多阶段构建见 P25）
$ docker build -t golearn-httpkv -f - . <<'EOF'
FROM alpine:3.22
COPY httpkv /usr/local/bin/httpkv
USER nobody
EXPOSE 8090
ENTRYPOINT ["/usr/local/bin/httpkv"]
EOF

# 3. 跑：真机实拍
$ docker run -d --name golearn-httpkv -p 18090:8090 golearn-httpkv
$ curl -s -X PUT -d '{"Value":"in-container","TTL":0}' localhost:18090/kv/k
{"value":"in-container","at":"0001-01-01T00:00:00Z"}   # PUT 回显请求体；At 由 GET 落库时补
$ curl -s localhost:18090/kv/k
{"value":"in-container","at":"2026-10-13T06:44:45Z"}    # GET 读回：At=time.Now
$ docker exec golearn-httpkv id
uid=65534(nobody) gid=65534(nobody)   # ← USER nobody 生效，不跑 root

翻车实录（第一次构建就踩的）：不设 GOOS=linux，产出的还是 macOS 的 Mach-O，容器里跑起来：

text
$ file /tmp/httpkv
/tmp/httpkv: Mach-O 64-bit executable arm64      ← 宿主格式
$ docker run --rm golearn-httpkv
exec /usr/local/bin/httpkv: exec format error    ← 内核拒绝执行

file 命令一眼定性：ELF 是 Linux 的，Mach-O 是 macOS 的。 此例禁用 cgo 并构建纯 Go 程序，避免依赖 cgo 引入的系统动态库； 具体二进制的链接方式仍应按目标平台和构建结果检查。

docker stop 对 PID 1 发 SIGTERM，httpkv 的信号链在容器里照常 工作：

sh
$ docker stop golearn-httpkv
$ docker logs golearn-httpkv 2>&1 | tail -1
{"level":"INFO","msg":"shutting down"}   # ← 优雅关停在容器里原样成立

反例：如果 PID 1 没有为 SIGTERM 安装处理器，该信号可能不会使其 退出；docker stop 在配置的宽限期后发送 SIGKILL，强制中断在途 请求。容器里的服务应处理停止信号，并给关停留出足够时间。

cgroups：限额与 GOMAXPROCS ​

cgroup 是内核的资源记账与限额单元。容器 CPU limit=2 就是把进程 放进 cpu.max=200000/100000 的 cgroup。Go 1.25 起 runtime 自动 读 cgroup 限额设 GOMAXPROCS（containermaxprocs，P22 的 GODEBUG 表里有）；之前的时代要靠 automaxprocs 库手动做，否则 GOMAXPROCS =宿主核数，限了 CPU 的容器里调度器还在开满核数的 P，延迟毛刺。

对照 Linux 机器上验证（本教程 T4 实测过，此处给命令）：

sh
$ cat /sys/fs/cgroup/cpu.max        # 容器内
200000 100000                       # 2 核
$ go run -exec="env GODEBUG=containermaxprocs=1" -r '.*' main.go
$ GOMAXPROCS gomaxprocs=2           # runtime 自动取限额

macOS 无 cgroups，容器里才有；这也是"本机没毛病、进容器毛刺" 这类问题的排查入口：先查限额和 GOMAXPROCS 是否对齐。

Take-away ​

  1. 进程 = PID + fd 表 + 信号处置；退出码是父进程读的 8 位结果， 被信号杀死是 128+信号号。
  2. 默认信号处置直接杀进程，优雅关停 = signal.NotifyContext 把 信号变成 ctx cancel，清理逻辑在主流程。
  3. fd 表是全部 I/O 的把手；日志进 stderr = 写 fd 2 = 容器日志 驱动的数据源；fd 泄漏到 ulimit 是长进程经典死法。
  4. 容器 = namespace（看见什么）+ cgroup（能用多少）+ 联合文件 系统；PID 1 不装 handler 就收不到 SIGTERM，docker stop 宽限期 （Linux 默认 10 秒）后 SIGKILL。
  5. Go 1.25+ 自动按 cgroup CPU 限额设 GOMAXPROCS；"本机好容器差" 先查限额对齐。

  1. kill -9 后 $? 是多少？kill -15 后呢（httpkv 已装 handler）？

进程观察速查（真跑输出） ​

sh
$ ps -o pid,ppid,command -p $(lsof -ti :8090)
  PID PPID COMMAND
71181    1 /tmp/httpkv     ← PPID=1：nohup 孤儿化（原 shell 不等它）

$ pgrep -l httpkv                # 按名找 PID
71181 /tmp/httpkv

PPID=1 的两种来路：docker 的 ENTRYPOINT（设计使然），或父进程 先退（孤儿被 init 收养）。看到"不该是 1 的进程 PPID=1"先查 是不是守护化/孤儿，再查是不是被 supervisor 接管。
