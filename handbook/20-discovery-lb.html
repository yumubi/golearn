20 注册发现与负载均衡 ​

详细程度:标准 · 约 55 分钟 材料:W12-1、W12-2、W13-1、W13-2、C:dachang/etcd · 旧长版:notes/p10-grpc.md(gRPC 基础) 前置:16 稳定性、19 微服务拆分与治理

先看一个让人愣住的现象 ​

把同一个服务部署了两个节点,分别监听 8090 和 8091,客户端连打 4 次 RPC,你预期流量怎么分?大多数人会猜"对半分"。但用 gRPC 默认配置跑出来的结果是:4 次全落在 8090,8091 一次都没被用到。〔W13-2 p4〕

这不是 bug,是 gRPC 默认的负载均衡策略 pick_first:它尝试解析出的地址,选一个可用连接来承载请求,连接不可用时再尝试其他地址。它不负责把请求均匀分配到多个节点。下面的代码仅模拟“固定选一个”与轮询的区别,不模拟连接建立、故障切换或 gRPC 的内部实现:

go
package main

import (
	"fmt"
	"sync/atomic"
)

// SubConn 只是地址的简化表示,不实现 gRPC 的 balancer.SubConn。
type SubConn string

// Picker 对应 balancer.Picker:每次 RPC 调用它挑一个连接。
type Picker interface {
	Pick() SubConn
}

// pickFirst 在这个简化模型里固定选择第一个地址,假设列表非空且地址可用。
type pickFirst struct{ subConns []SubConn }

func (p *pickFirst) Pick() SubConn { return p.subConns[0] }

// rrPicker 是轮询:原子递增下标,对节点数取余。
type rrPicker struct {
	subConns []SubConn
	next     uint32
}

func (p *rrPicker) Pick() SubConn {
	i := atomic.AddUint32(&p.next, 1) % uint32(len(p.subConns))
	return p.subConns[i]
}

func main() {
	scs := []SubConn{"127.0.0.1:8090", "127.0.0.1:8091"}
	pf := &pickFirst{subConns: scs}
	fmt.Print("pick_first 连打 4 次: ")
	for i := 0; i < 4; i++ {
		fmt.Print(pf.Pick(), " ")
	}
	fmt.Println()
	rr := &rrPicker{subConns: scs}
	fmt.Print("round_robin 连打 4 次: ")
	for i := 0; i < 4; i++ {
		fmt.Print(rr.Pick(), " ")
	}
	fmt.Println()
}
text
pick_first 连打 4 次: 127.0.0.1:8090 127.0.0.1:8090 127.0.0.1:8090 127.0.0.1:8090
round_robin 连打 4 次: 127.0.0.1:8091 127.0.0.1:8090 127.0.0.1:8091 127.0.0.1:8090

同一个列表,pick_first 死磕一个节点,round_robin 才开始分流。所以这一节要回答的其实是三个连环问题:服务实例列表从哪来(服务注册与发现)；拿到列表之后这一次调谁(负载均衡)；gRPC 把这两件事各自抽象成了什么接口,我们又该怎么接进去。

一、服务发现:从写死 IP 到注册中心 ​

服务拆成多个实例之后,调用方要回答两个问题:这个服务现在有哪些实例(发现),这一次调哪一个(负载均衡)。两个答案都会随时间变,所以不能写死。解决"列表从哪来"有三代方案,演进主线就是"缓存与新鲜度"的权衡。

第一代:IP 直连。 配置文件里写死 10.0.0.1:8090,没有注册也没有发现。IP 会变、难维护,但联调时直接调同事电脑的 IP 方便对方本地 DEBUG,排查只出现在个别实例上的 bug 时也会定向发请求过去。〔W12-1 p5〕

第二代:域名 + DNS。 解析域名有开销,客户端一般会缓存解析结果,于是两难:不缓存,每次调用多一跳查询；缓存了,节点上下线无法及时反映到客户端列表里。〔W12-1 p6〕

第三代:注册中心。 服务端启动时注册；客户端查询并缓存实例列表,再通过监听变化更新缓存。它能缩短变更传播时间,但仍要处理断连、缓存过期和注册中心自身的可用性与扩容。〔W12-1 p7〕

数据量大了还有一步优化:服务自省(Dubbo 提出)。注册中心只存最小的定位数据,其余元数据变化少,放到独立的元数据服务里查一次就够。〔W12-1 p8〕

二、注册的完整生命周期 ​

注册什么、什么时候注册 ​

注册数据里关键的是定位信息(IP 加端口),其余是治理信息,比如分组、权重。〔W12-1 p13〕权重这条伏笔在第三节展开。

启动时机上,服务端连不上注册中心就应该直接失败退出:此时服务还没对外提供流量,失败代价最小,拖着带病上线反而危险。〔W12-1 p12〕还有个容易忽略的顺序细节:要先确保端口打开,再注册,否则客户端拿着列表打过来,连接被拒。〔W12-2 p14〕

注册地址要从客户端视角确认可达,跨主机访问通常不能使用 127.0.0.1。可以由平台配置或注入,也可枚举网卡、探测出口地址；多网卡、NAT 等环境下不能保证自动选出的第一个地址可达。课件的 GetLocalIP 枚举网卡,找不到时返回 ERR_NO_LOCAL_IP_FOUND。〔C:dachang/etcd/service_registration_center/common.go:25-51〕〔W12-2 p16〕

UDP 拨号的做法是用 net.Dial("udp", "8.8.8.8:80"),再从 conn.LocalAddr() 取本地地址。它通常不发送数据包,而是让内核按到该目标的路由选择出口地址；若客户端走另一条网络路径,这个地址未必可达,多网卡或 NAT 场景应以实际网络配置验证。〔W12-2 p16〕回环地址指向调用方自己的网络命名空间,一般不能作为跨主机服务地址。在 K8s 里应使用客户端可达的 Pod 地址,或使用 Service 名称访问；Pod 重建后 IP 可能改变。〔W12-2 p18〕

etcd 官方 SDK 怎么注册:Manager、Update 和退出清理 ​

etcd 直接提供了 gRPC 服务注册与发现的 Resolver 实现,服务端注册不用自己拼 etcd API,走 endpoints 包四步:〔W12-2 p7〕

  1. 创建 Manager:endpoints.NewManager(cli, "service/user"),第二个参数 target 就是服务名;
  2. 注册:em.AddEndpoint(ctx, key, endpoints.Endpoint{Addr: addr})。key 必须以服务名为前缀,实际 key = "service/user/" + addr(示例里 addr=127.0.0.1:8090,key 即 service/user/127.0.0.1:8090);Endpoint 的 metadata 一般是给客户端用的(比如后面第六节的权重);
  3. 注册数据有变动时调 Update。别扭之处:传入的是 endpoints.Add 操作,因为 key 已经存在,实际效果就是覆盖更新了数据。而且 etcd 这里没有提供 Edit 操作,作者原话是"无力吐槽"。课件里用 ticker 模拟元数据变化(更新 Metadata 时间戳),etcdctl get 同一个 key 能看到 Metadata 从 16:48:10 → 16:48:13 → 16:48:18 依次变化;〔W12-2 p8〕
  4. 正常退出按顺序做两件事:先 em.DeleteEndpoint(ctx, key) 删除自己注册的 Endpoint(取消注册),再 server.GracefulStop() 做 gRPC 优雅退出。顺序不能反:先停服务器再删,客户端会在删掉之前就开始拿到一个已死的地址。〔W12-2 p9〕

宕机残留:谁清理、客户端怎么感知 ​

上面这套注册没有租约,那进程被强制关闭(kill -9,走不到 DeleteEndpoint 的优雅退出路径)之后会怎样?作者用强制关闭服务器模拟宕机验证过:etcdctl get service/user/127.0.0.1:8090 在宕机后依然返回这个节点,Metadata 时间戳一直停留在同一时刻。注册残留没有被清掉。按理论宕机后注册数据应该没了,实际却还在。〔W12-2 p10〕

残留的因果:没有租约时,这条注册只是一条普通 KV,etcd 不会因为进程死亡而删它,唯一的删除路径就是优雅退出里的 DeleteEndpoint,进程崩溃时恰好走不到。谁最终清掉它?靠 Lease:注册数据挂上租约之后,进程死亡 → 无人续约 → 租约到期,etcd 按租约机制清掉挂在该租约上的 key。租约过期自动删除是 Lease 机制本身,不需要任何组件"发现"进程死了。〔W12-2 p10-11〕客户端这边感知变化不靠轮询:Resolver/SDK 封装了 Watch 加拉取,etcd 上节点一消失,客户端本地列表随之更新。但这条链路有秒级延迟窗口,窗口内调用方只会连不上,要靠自己的 failover 换节点重试。〔W12-2 p40〕

心跳就是租约续租 ​

注册成功不等于一劳永逸。注册机制的本质是租约:数据带过期时间,心跳就是续租。心跳有两种模式:服务端主动(只要没收到网络错误就当连接正常)或注册中心主动探测;心跳失败,注册中心就判定节点崩溃并通知客户端。〔W12-1 p14〕"失败"可以是一次,也可以是连续多次,这两个参数都是权衡:间隔越短压力越大;判定次数越少发现越快但越怕偶发抖动误踢,越多越稳但发现越慢。〔W12-1 p15〕

etcd 把这套机制做成 Lease 加 KeepAlive:先 Grant 创建带 TTL 的租约,Put 时用 WithLease 把 key 挂上租约,再 KeepAlive 自动续约;节点崩溃没人续租,key 到期自动消失。etcd 的 KeepAlive 默认每隔 ttl/3 续约一次,选项很少。大多数微服务框架直接用它的租约机制当心跳,实践中没什么问题,只是没有自定义重试和判定策略的空间。〔W12-2 p11-12〕课件里 etcd.go 的 keepAlive 函数演示了 Grant、Put 带租约、KeepAlive 的基本用法。〔C:dachang/etcd/etcd.go:59-85〕

落到课件的服务端示例,完整流程四步(TTL 示例取 5 秒):〔W12-2 p11〕

  1. 创建租约:var ttl int64 = 5,调 S.cli.Grant(ctx, ttl) 拿到 LeaseResp;
  2. 开启自动续约:kaCtx, kaCancel := context.WithCancel(context.Background()),起 goroutine 调 S.cli.KeepAlive(kaCtx, LeaseResp.ID),for resp := range ch 处理每次续约结果。作者建议只简单打个日志就够了。续约失败了实际上你也做不了什么;
  3. 对 Endpoint 的所有操作都带上租约 ID:em.AddEndpoint(..., clientv3.WithLease(LeaseResp.ID)),之后模拟元数据变化的 Update 也要带 clientv3.WithLease(LeaseResp.ID),否则新写入的数据不挂租约;
  4. 退出时三步按序:先 kaCancel() 取消 kaCtx 退出续约的 goroutine,再 em.DeleteEndpoint(ctx, key),最后 server.GracefulStop()。

租约过期还有个坑要预想到:租约一旦过期被回收,续约就再也续不上,只能整个重新注册。课件服务端对应的处理是续约收到 rpctypes.ErrLeaseNotFound 时把 leaseID 置 0,退回 Grant 加 Put 的注册分支重走一遍。〔C:dachang/etcd/service_registration_center/server/service_hub.go:54-84〕

优雅下线五步 ​

收到退出信号能不能立刻结束进程?不能:进程里可能还有读了一半的请求,客户端可能正发着下一个请求。完整流程是五步:通知注册中心自己要下线;不再接受新请求,网络上读了一半的请求读完即拒,不进业务代码;等在处理的请求和定时任务结束;结束运行;整个退出过程有超时控制,超时强退。〔W12-1 p18-19〕课件里的服务端收 SIGINT/SIGTERM 后先主动注销再退出,即使没来得及注销,最晚一个 TTL 之后注册中心也会把这个节点踢掉。〔C:dachang/etcd/service_registration_center/server/server.go:64-75〕

客户端发现的两个时机 ​

客户端做服务发现有两个时机:启动时发现,从配置或注册接口拿到全部要用的服务,初始化时就查好,失败就不启动;或者惰性发现,第一次真正调用某个服务时才去查。后者冷启动快,但首次调用会多一次查询延迟。另外客户端和注册中心之间也要保持连接(心跳),这样节点变动才能推得过来。〔W12-1 p20〕

etcd 客户端服务发现:一个 target 搞定 ​

对比服务端的一长串注册代码,客户端这边简单很多:客户端不需要关心同步数据之类的事情,SDK 都处理了(Watch、拉取等细节被 etcd 的 resolver 实现封装)。用法两步:〔W12-2 p13〕

go
etcdResolver, err := resolver.NewBuilder(cli)
cc, epr := grpc.Dial("etcd:///service/user",
    grpc.WithResolvers(etcdResolver), // 首先是三个,不要漏了
    grpc.WithTransportCredentials(insecure.NewCredentials()))
userClient := NewUserServiceClient(cc)
resp, err := userClient.GetById(ctx, &GetByIdReq{Id: 123})

target "etcd:///service/user" 的拆解:scheme 部分 etcd 对应 builder 的名字。resolver.NewBuilder(cli) 返回的 builder 其 Scheme() 方法就返回 "etcd";路径部分 service/user 是服务名,与服务端注册 key 的前缀对应。Dial 选项必须带上 grpc.WithResolvers(etcdResolver),原文提醒"首先是三个,不要漏了",还包括 grpc.WithTransportCredentials(insecure.NewCredentials())。拿到 cc 之后正常构造 client 调用,调用方感知不到背后走了注册中心。〔W12-2 p13〕

改造 ginx.Server:注册接进启动流程 ​

把这套东西接进自己的框架,核心修改是扩展 ginx.Server 的功能,让它负责和注册中心打交道,只改造了 Serve 方法。Serve 从创建 ctx 到阻塞的顺序:〔W12-2 p14〕

  1. ctx, cancel := context.WithCancel(...),存到 s.cancel,初始化一个控制整个过程的 ctx(也可以考虑让外面传进来);
  2. port := strconv.Itoa(s.Port),对端口做 net.Listen("tcp", ...);Listen 失败直接 return err;
  3. 确保端口打开(启动成功)之后才调用 s.register(ctx, port)。原文特别强调"我们是在确保端口打开之后才注册的",先确保启动成功再注册服务,否则客户端拿着列表打过来连接被拒;
  4. 最后 return s.Server.Serve(L) 阻塞。

register(ctx, port) 内部依次做:clientv3.NewFromURL("http://localhost:12379") 建 etcd 客户端存到 s.etcdClient;serviceName := "service/" + s.Name,endpoints.NewManager(cli, serviceName) 存到 s.etcdManager;ip := netx.GetOutboundIP() 获得自己的 IP;s.etcdKey = serviceName + "/" + ip,addr = ip + ":" + port;cli.Grant(ctx, s.EtcdTTL) 创建租约;cli.KeepAlive(ctx, LeaseResp.ID) 开启续约(goroutine 处理返回的 ch);最后 em.AddEndpoint(ctx, s.etcdKey, endpoints.Endpoint{Addr: addr}, clientv3.WithLease(LeaseResp.ID)) 添加服务节点。这里没有要提供的 metadata。〔W12-2 p15〕

作者指出这种写法的缺陷:Server 和 etcd 强绑定在一起;类似 go-zero、ego、Kratos 之类的框架都允许你使用不同的注册中心,但写法是类似的。〔W12-2 p15〕

三、拿 etcd 实现一遍 ​

etcd 是 Go 写的、基于 Raft 的强一致键值存储。用做注册中心的套路:服务端把 服务名/实例地址 当 key 写进去,挂上租约；客户端启动后把某服务名前缀下的 key 拉一遍建本地缓存,再装一个 Watcher,etcd 数据一变就更新缓存,平时调用根本不碰 etcd。

服务端这边,注册逻辑值得细看。第一次注册是 Grant 创建租约、Put 把 key 挂上租约；后续周期性触发时,同一个调用走的是 KeepAliveOnce 续约分支:

〔C:dachang/etcd/service_registration_center/server/service_hub.go:54-84〕

go
func (hub *ServiceHub) Regist(service string, endpoint string, leaseID etcdv3.LeaseID) (etcdv3.LeaseID, error) {
	ctx := context.Background()
	if leaseID <= 0 {
		// 创建一个租约，有效期为heartbeatFrequency秒
		if lease, err := hub.client.Grant(ctx, hub.heartbeatFrequency); err != nil {
			log.Printf("创建租约失败：%v", err)
			return 0, err
		} else {
			key := strings.TrimRight(service_registration_center.SERVICE_ROOT_PATH, "/") + "/" + service + "/" + endpoint
			// 服务注册
			if _, err = hub.client.Put(ctx, key, "", etcdv3.WithLease(lease.ID)); err != nil { //只需要key，不需要value
				log.Printf("写入服务%s对应的节点%s失败：%v", service, endpoint, err)
				return lease.ID, err
			} else {
				return lease.ID, nil
			}
		}
	} else {
		//续租
		if _, err := hub.client.KeepAliveOnce(ctx, leaseID); err == rpctypes.ErrLeaseNotFound { //续约一次，到期后还得再续约
			return hub.Regist(service, endpoint, 0) //找不到租约，走注册流程(把leaseID置为0)
		} else if err != nil {
			log.Printf("续约失败:%v", err)
			return 0, err
		} else {
			// log.Printf("服务%s对应的节点%s续约成功", service, endpoint)
			return leaseID, nil
		}
	}
}

注意 ErrLeaseNotFound 这个分支:租约一旦过期被回收,续约就再也续不上,只能整个重新注册。优雅下线对应的注销就是一个 Delete(UnRegist 函数,把 key 从 etcd 删掉),客户端这边则简单得多:SDK 把查询、缓存、监听全包了。〔C:dachang/etcd/service_registration_center/server/service_hub.go:85-96〕

四、etcd 注册中心崩了怎么办 ​

选型离不开 CAP:网络分区不可避免时,一致性和可用性只能保一个。ZooKeeper 是 CP,Eureka 是 AP,Nacos 两种模式都支持。面试标准答案是注册中心选 AP,务实的说法是小规模随便选,大规模优先 AP:拿到稍微过期的节点列表,通常好过完全拿不到列表。〔W12-2 p29-31〕ZooKeeper 是主从结构,缺点里有主节点选举期间集群不可用,材料据此判它是 CP；Eureka 是对等集群、选 AP；Nacos 同时支持两种。〔W12-2 p33-35〕

etcd 在 CAP 里应当归为 CP:它用 Raft 保证强一致,〔W12-2 p36〕发生网络分区时,拿不到多数派的那一侧不再服务,选择的是一致性而放弃了可用性。材料 W12-2 p30 把 etcd 说成"AC 模型,没有选择 P",这个说法不对:分布式系统里分区容错不是可以不选的选项,所谓"集群之间不能通信就不可用"恰恰是 CP 的表现。后面引用这一页时,以这里的说法为准。强一致对注册中心的实际意义是:你读到的列表来自多数派确认过的状态,第二节的代码因此可以写得简单。

注册中心崩溃期间,各方该怎么办值得单独想清楚,因为答案不是"全体重试":

  • 服务端：已注册的老节点继续服务,反正客户端还在用本地缓存；新节点注册失败就直接退出,和第二节"启动阶段连不上就退出"是同一条原则。〔W12-2 p43〕
  • 客户端：用本地缓存继续调用,发现连不上的节点就移出列表；全新服务没有任何缓存,只能返回错误,让调用方自己决定怎么办。〔W12-2 p42〕
  • 注册中心与服务端断连：注册中心会把活着的节点误判为崩溃,客户端在收到错误判定前照常能调用；服务端发现自己长时间续不上约,要告警并考虑是否退出。〔W12-2 p44〕

提高可用性的手段从轻到重:注册中心上集群或多活；双注册中心互为备份；按业务拆分注册中心,核心业务和别的业务隔离。〔W12-2 p41〕顺带一提 K8s:IP 直连、域名、注册中心三种方式在 K8s 里都能用,但注册的必须是 Pod 之间真实通信的 IP,且 Pod 重启后 IP 可能漂移,所以材料作者不太推荐在 K8s 里再跑注册中心,推荐直接用 Service 的名字(DNS)通信。〔W12-2 p18〕

五、负载均衡算法全景 ​

列表到手,这次请求发给谁?先摆正目的:负载均衡是手段不是目的,目的是把请求交给"最适合"处理的节点,内存密集的给内存多的,CPU 密集的给 CPU 空闲的。〔W13-1 p4〕

轮询与随机。 轮询是逐个轮流,应用最广,绝大多数情况下直接用不会出问题。它隐含两个假设:所有服务器处理能力一样,所有请求消耗资源一样。〔W13-1 p7〕随机更简单,生成随机数对节点数取余,假设与轮询相同。〔W13-1 p18〕

加权版本。 现实是机器有新旧、配置有高低,于是给每个节点一个权重,代表处理能力、重要性或优先级。加权轮询按权重分配请求次数；〔W13-1 p8〕加权随机计算总权重,随机数落在哪个区间就选哪个节点(这是对"随机数加权重"的常规做法,材料未展开)；哈希类算法用业务特征(业务 ID、外键、唯一索引)算哈希值代替随机数。权重从哪来?注册中心模型下由服务端注册时写入,随服务发现下发给客户端。〔W13-1 p9〕

一致性哈希。 普通哈希在节点数变化时几乎全部请求要重新映射；把哈希空间组织成环,哈希值落在某个区间就由负责该区间的节点处理,增减节点只有部分请求换节点。这就是它对有状态场景(缓存、分片)的价值。〔W13-1 p22〕

动态算法。 前面都是静态的,动态算法尝试实时估算节点负载,常见三种:最少连接数,挑当前连接数最少的,但在连接多路复用下会失真,一个连接可能被上百个请求复用；最少活跃数,数的是正在处理中的请求数,比连接数准；最快响应时间,挑历史上响应最快的,通常取平均或 99 线。〔W13-1 p25-27〕注意这三种的视角都只在客户端:客户端只知道自己发出去的连接、未归还会话和响应时间,看不到服务端的真实水位,这是框架级负载均衡的固有局限。〔W13-1 p30〕

设计自己的算法时回答四个问题就够了:要不要区分处理能力(加权与否)；选什么指标表达负载(不选指标就靠轮询这种统计意义上的均衡)；要不要区分请求消耗(大请求会打爆个别实例)；最后选哪个算法。实践口诀:遇事不决用轮询,出了问题再说。〔W13-1 p28〕

平滑加权轮询:权重 10:20:30 是怎么变成 C B A C B C 的 ​

普通加权轮询有个观感很差的缺陷:权重高的节点会连续收到请求,比如 B 连收两个、C 连收三个,瞬时压力集中。〔W13-1 p10〕平滑加权轮询(SWRR)解决的就是这个,它给每个节点引入"当前权重",流程四步:算总权重；每个节点当前权重加自己的初始权重；选当前权重最大的；选中的减去总权重。〔W13-1 p11〕

初始权重 10、20、30(总 60)时,前两次的推演:第一次三家加权重后是 10、20、30,C 最大被选中,C 减 60 变 -30；第二次加完是 20、40、0,B 最大被选中,B 减 60 变 -20。完整序列是 C、B、A、C、B、C；跨周期或其他权重下仍可能连续选中同一节点。直接看这组权重:

go
package main

import "fmt"

// 初始权重就是材料图里的:10、20、30,总权重 60
type node struct {
	name  string
	initW int // 初始权重(有效权重)
	curW  int // 当前权重
}

func pick(nodes []*node) *node {
	total := 0
	for _, n := range nodes {
		n.curW += n.initW // 1. 每个节点当前权重加上初始权重
		total += n.initW
	}
	best := nodes[0]
	for _, n := range nodes[1:] { // 2. 选当前权重最大的
		if n.curW > best.curW {
			best = n
		}
	}
	best.curW -= total // 3. 选中者减去总权重
	return best
}

func main() {
	nodes := []*node{{"A", 10, 0}, {"B", 20, 0}, {"C", 30, 0}}
	for i := 1; i <= 6; i++ {
		n := pick(nodes)
		fmt.Printf("第%d次:%s  ", i, n.name)
	}
	fmt.Println()
}
text
第1次:C  第2次:B  第3次:A  第4次:C  第5次:B  第6次:C

减总权重这一步是算法的灵魂。不减的话,C 的当前权重永远比 B、A 高出一大截,每次都是 C,权重失效；减了 60 之后,选中的节点"欠"了一次,下次轮到别人,6 次一轮恰好 C 出现 3 次、B 出现 2 次、A 出现 1 次,比例精确等于权重比,且分布是打散的。第四个请求选完后,A、B、C 的当前权重是 -20、20、0；材料的第五个请求图里,选择之前(各加一次初始权重后)是 -10、40、30,与此一致。〔W13-1 p15-16〕 理解了 SWRR,再看"结合调用结果动态调权"就顺理成章了:把返回错误的节点降权、熔断期间把权重压到极低,第七节把它加进上面的代码。〔W13-2 p31〕〔W13-2 p35〕

六、gRPC 怎么接负载均衡 ​

默认行为与内置算法 ​

回到开头的现象。gRPC 内置的算法都在 balancer 子包里:grpclb 是给集中式 LB 用的集成点；leastrequest 和 rls 是实验特性；round_robin 是轮询；weightedroundrobin 是加权轮询。除了 round_robin,其他一般用不上。〔W13-2 p10〕pick_first 虽然没列在这个清单里,但它是默认策略,这就是开头"4 次全打 8090"的原因。

换算法的方式很特别:传一段 JSON。这是 gRPC 一个容易写错的地方,round_robin 没有配置项,花括号里就是空的:〔W13-2 p5〕

go
grpc.WithDefaultServiceConfig(`{"loadBalancingConfig": [{"round_robin":{}}]}`)

带上这段配置后,当两个地址对应的连接都就绪时,调用会在它们之间轮询；连接建立期间和节点不可用时不保证四次恰好平均分配。〔W13-2 p5〕

自己写一个 Picker 有多难 ​

gRPC 把负载均衡拆成两个接口:Balancer 负责维护连接状态、创建 Picker；Picker 每次 RPC 选取一个可用的 SubConn。〔W13-2 p6〕版本差异值得留意:本机模块缓存的 gRPC v1.67.0 使用原子递增下标并随机选择起始位置；项目的 v1.84.0 则建立在 endpointsharding 之上。开头的 rrPicker 只是教学模型,不等同于任一版本的实现。SubConn 是 balancer 管理的逻辑子连接,不应直接理解成一个连接池。

自定义加权轮询的接入是三步:实现 PickerBuilder 接口(它唯一的 Build 返回一个 Picker)；把 PickerBuilder 包装成 balancer.Builder 注册进 gRPC 的全局表；Dial 时用上面那段 JSON 指定名字。注册靠算法包的 init 函数,业务代码匿名引入触发 init,之后按名字查找,这是 Go 生态的标准插件模式。〔W13-2 p16〕〔W13-2 p8〕权重数据则走服务发现返回的元数据:Resolver 返回的每个地址携带 attributes,注册中心里 metadata=weight=123 这类数据放进去,PickerBuilder 建立时取出；元数据在地址生命周期里不变,权重变了要靠 Resolver 触发地址更新来传播。〔W13-2 p13〕〔W13-2 p14〕

总结成一句话:绕不开 PickerBuilder 和 Picker 两个接口,接入方式基本都靠 WithDefaultServiceConfig 指定；现有的轮询和加权轮询已能覆盖绝大多数需求,真要自定义时才走这条路。以 gRPC 为底座的微服务框架(例如 go-zero)在服务注册发现上高度同构:必然实现 gRPC 的 Resolver 接口；必然有注册过程；必然有续约(自己写或靠 etcd 客户端)；想支持多种实现就会抽一层 Registry/Discovery 接口,学新框架沿这四点找源码很快能定位。〔W13-2 p25〕〔W12-2 p26〕

七、把动态调权加进 SWRR ​

第五节的 pick 里,选中的减总权重、出错的怎么办?让"有效权重"可变就行:某个节点连续失败,就把它的初始权重减半(下限 1,永不让权重归零,否则它永远选不中,也永远没有恢复的机会)；熔断恢复后再逐步升回来。〔W13-2 p31〕〔W13-2 p35〕〔W13-1 p29〕

go
package main

import (
	"errors"
	"fmt"
)

var errNoInstance = errors.New("no instance")

type picker struct {
	names []string
	w     []int // 各节点的动态权重(有效权重)
	cur   []int
}

func (p *picker) pick() (string, error) {
	if len(p.names) == 0 || len(p.w) != len(p.names) {
		return "", errNoInstance
	}
	total := 0
	for i, w := range p.w {
		p.cur[i] += w
		total += w
	}
	if total <= 0 {
		return "", errNoInstance
	}
	best := 0
	for i := range p.cur {
		if p.cur[i] > p.cur[best] {
			best = i
		}
	}
	p.cur[best] -= total
	return p.names[best], nil
}

// 熔断降权:连续失败就把有效权重减半,下限 1,永不归零
func (p *picker) penalize(i int) {
	if p.w[i] > 1 {
		p.w[i] /= 2
	}
	p.cur[i] = 0
}

func main() {
	p := &picker{names: []string{"A", "B"}, w: []int{30, 10}, cur: make([]int, 2)}
	for i := 0; i < 4; i++ {
		n, _ := p.pick()
		fmt.Print(n, " ")
	}
	fmt.Println()
	p.penalize(0) // A 连续出错,降权
	for i := 0; i < 4; i++ {
		n, _ := p.pick()
		fmt.Print(n, " ")
	}
	fmt.Println("A 的有效权重现在是", p.w[0])
}
text
A A B A
A B A B A 的有效权重现在是 15

降权前 A 拿走四分之三的流量；减到 15 后 A:B 变成 3:2,分流的正是从 A 挪走的那部分。total <= 0 的守卫对应的正是"权重全被调成 0"这种事故:不拦住,全零权重下依然会选出一个节点,流量被打给本该剔除的实例。〔W13-1 p29〕

小结 ​

  • 服务发现可用 IP 直连、DNS 或注册中心；都需要权衡缓存、新鲜度与故障处理。〔W12-1 p5-7〕
  • 注册生命周期:启动先开端口再注册、失败即退出；租约加续约当心跳；下线走五步,全程有超时。〔W12-1 p12-19〕〔W12-2 p14〕
  • etcd 实现三件套:Grant 建租约,KeepAlive(课件服务端用的是周期性 KeepAliveOnce)续约,Delete 注销；客户端查询建缓存再挂 Watcher。〔C:dachang/etcd/service_registration_center/server/service_hub.go:54-84〕〔C:dachang/etcd/service_registration_center/client/service_hub.go:96-106〕
  • 注册中心崩溃时的分工:老节点续服务、新节点注册失败即退出、客户端用缓存加 failover,小规模选型随意、大规模优先 AP。〔W12-2 p29-31〕〔W12-2 p42-44〕
  • 负载均衡算法按"是否考虑处理能力、用什么指标、是否区分请求消耗"三问选择,默认轮询；SWRR 用"加初始权重、选最大、减总权重"把比例分配打散,动态权重必须设上下限。〔W13-1 p28〕〔W13-1 p11〕〔W13-1 p29〕
  • gRPC 侧:默认 pick_first 会把流量全压到第一个地址；换算法传 JSON；自定义算法实现 PickerBuilder 加 Picker,匿名引入注册,权重走 Resolver 元数据。〔W13-2 p4〕〔W13-2 p25〕

常见坑 ​

  1. 忘了换默认负载均衡:两个节点只有一个收到流量,一查是 pick_first。多副本部署却没分流,先查这个。〔W13-2 p4〕
  2. 注册地址对客户端不可达:跨主机注册 127.0.0.1 或错误的网卡地址都会导致连接失败；配置或自动发现后都应验证实际可达性。〔W12-2 p16〕〔W12-2 p18〕
  3. 先注册后开端口:客户端拿着列表打过来连接被拒。要确保端口打开之后再注册。〔W12-2 p14〕
  4. 心跳参数拍脑袋:间隔、判定次数是"发现速度换系统压力"的定价,不是随手写的常数。〔W12-1 p15〕
  5. 动态权重没有上下限:权重滚雪球或归零,节点要么一直被选中要么永远没流量,降权要有下限。〔W13-1 p29〕
  6. 租约过期后还傻续:续约报 ErrLeaseNotFound 时必须整个重新注册,续是续不上的。〔C:dachang/etcd/service_registration_center/server/service_hub.go:54-84〕

判断题与答案 ​

  1. 租约 TTL 为 5 秒,服务端被 kill -9,客户端什么时候能把流量切走?有哪几段延迟? 答案:租约从最后一次成功续约后开始计时,宕机时剩余 TTL 不一定是 5 秒；到期删除、Watch 传播和客户端更新还需要时间。客户端也可能通过连接失败或健康检查提前切走,不必等注册记录消失。重试须考虑幂等性和调用截止时间。〔W12-1 p15〕
  2. 平滑加权轮询为什么要在选中后减去总权重? 答案:不减,当前权重最高的节点会一直最高,流量全压给它；减掉总权重相当于"记账",让别的节点有机会反超,最终选中比例严格等于权重比,且分布平滑。
  3. 注册中心崩溃期间上线的新服务,注册失败就退出,这个设计的理由是什么? 答案:此时客户端没有任何缓存可用,注册不成功就永远没人调它；而启动阶段失败代价最小,退出去靠重试或告警比带病挂着好。〔W12-2 p43〕
  4. 什么场景下哈希负载均衡比轮询更合适? 答案:同一请求需要落到同一节点的场合,比如本地缓存复用、有状态会话；用业务 ID 等特征做哈希,节点数稳定时映射关系不漂移,节点增减时用一致性哈希减少重映射。〔W13-1 p20〕〔W13-1 p22〕

W12-1 注册发现的边角与网关模型 ​

  • 网关模式:请求先找到网关(靠域名如 gateway.mycompany.com 或配置项),网关把请求转给真实服务端之前,还要再做一次服务发现(注册中心或 DNS)。严格说它不算注册发现模型,但实践里很常见。〔W12-1 p9〕
  • 高级心跳:双向心跳(两边都主动发),或单向心跳失败后另一边主动 ping(注册中心久未收到心跳时反过来联系服务端)。材料评价是少采用,性价比不高。〔W12-1 p16〕
  • 服务下线的普通版只有两步:通知注册中心,注册中心通知客户端把节点从可用列表挪走。五步优雅下线是它的精细化版本。〔W12-1 p17〕

W12-2 gRPC 接注册中心的另一半:默认方案、Manager 与客户端 ​

  • gRPC 默认的服务发现是域名解析策略:地址写成 user_svc.mycompany.com:8090 这种形态,传 IP 则连解析这步都省了;dnsResolver 定时访问 DNS 服务器刷新本地缓存的 IP 列表,K8s 里材料推荐就用这个形态。〔W12-2 p4-5〕
  • Resolver 是 gRPC 的核心抽象,代表"对服务的解析",产出定位信息在内的元数据;gRPC 根本不知道也不关心你用不用注册中心,它只提供客户端这边的 Resolver 接口,接注册中心=实现一个用注册中心的 Resolver。〔W12-2 p6〕
  • etcd 直接提供了现成的 Resolver:服务端用 endpoints.NewManager(cli, "service/user") 建 Manager,AddEndpoint 写入 key(必须是 service/user/ 前缀加地址);元数据变动调 Update(传 Add op,key 已存在所以实为覆盖,API 没有 Edit);退出 DeleteEndpoint 加 GracefulStop。〔W12-2 p7-9〕
  • 宕机残留坑:不走租约的注册只在优雅退出时干净,进程被强杀(模拟宕机)后 etcd 上节点还在,客户端会拿到死地址;Lease 就是用来兜这个底的,kill -9、OOM 全靠租约过期清理,TTL 直接决定检测延迟。〔W12-2 p10-11〕
  • 客户端比服务端简单得多:resolver.NewBuilder(cli) 建 etcd 解析器,grpc.Dial("etcd:///service/user", grpc.WithResolvers(etcdResolver)),数据同步全由 SDK 处理。〔W12-2 p13〕
  • 材料把 ginx 的 etcd 交互(注册、续约、退出清理)全塞进 Server,缺陷是与 etcd 强绑定;go-zero、ego、Kratos 都允许多注册中心,选 SDK 时要问四件事:有没有自动续约、间隔多长、续约失败 SDK 怎么处理、客户端多久能感知变化。〔W12-2 p14-15〕〔W12-2 p19〕
  • 选型对照除了 ZK/Eureka/Nacos:ZooKeeper 树形结构存节点(如 /app1/p_1),客户端收到 Watch 事件后主动拉数据,规避事件有序问题;优点是成熟、多语言客户端、Watcher push,缺点是 TCP 连接数撑不住超大集群、主从写瓶颈、脑裂、选举期间不可用。Eureka 对等集群选 AP,注册只写一个节点再扩散,所以发现慢,多语言客户端质量差。〔W12-2 p32-34〕
  • etcd 本身的边界:Go 编写、部署简单、大规模表现优秀,但网络稳定性差的环境不合适,因为强一致依赖多数派通信。〔W12-2 p36〕
  • 服务端崩溃到注册中心发现再到通知客户端,有秒级延迟窗口,这期间客户端只会连不上,要自己 failover 换节点重试。〔W12-2 p40〕
  • 高可用有一张"三边"的总图:三条通信边分别是注册中心↔服务端、注册中心↔客户端、客户端↔服务端,三种崩溃各砸一条边:服务端崩砸第一条(注册中心剔除加通知,有秒级窗口)、注册中心崩同时砸前两条(客户端靠本地缓存顶住)、客户端崩不用处理(断连即结束)。第四种故障"客户端↔服务端连不上"则靠 failover 兜底,正文分角色讲的应对方案就是按这张图展开的。〔W12-2 p39〕

W13-1 算法版图的补笔:统计学、多活权重与全局视角 ​

  • 静态算法的本质:完全不管节点实际负载,靠统计学,请求发得足够多就大概率均衡,材料形容为"摆烂但有效"。〔W13-1 p6〕

  • 动态算法的起点是一个坦白:节点负载没法被精确定量,所以才要挑一个指标当代理,常见三种就是最少连接数、最少活跃数、最快响应;指标选定之后,剩下的才是正文第七节的动态调权。〔W13-1 p24〕

  • 权重偶尔还有地理含义:多活场景下同机房、同城节点权重更高。〔W13-1 p8〕

  • 一致性哈希的适用边界:它解决的是扩缩容稳定性(数据、会话粘性场景),纯无状态 RPC 用它反而不如轮询。〔W13-1 p22〕

  • 自设计算法时指标的来源:错误率等服务指标、CPU/IO/网络等硬件指标;让客户端知道指标的三招是服务端写注册中心、响应头捎带指标(如 CPU 利用率)、从可观测性平台取数。〔W13-1 p31〕

W13-2 failover 与框架默认值:gRPC 里怎么兜底 ​

  • pick_first 并非一无是处:单节点加 K8s Service 场景下它就是正确行为,多实例才必须显式配 round_robin。〔W13-2 p4〕
  • 官方的加权轮询和手写的不是一回事:它不要注册中心传权重,客户端按每个节点的 QPS 与错误率自算(QPS 高权重大,错误率高权重低),再用 EDF(最早截止时间优先)挑选;要精确控制权重语义就得自定义 Picker。〔W13-2 p9〕
  • gRPC 里 failover 的落法:重试加负载均衡,缺一不可,只重试会反复撞死节点,只剔除则单次失败就丢请求;最简形态是 round_robin 加 retryPolicy 的 JSON 配置。字段有 name(指定哪些方法,service 名要去 proto 编译产物里找)、maxAttempts、initialBackoff/maxBackoff/backoffMultiplier(指数退避)、retryableStatusCodes(必须含 UNAVAILABLE 才会触发换节点重试)。手写 JSON 千万仔细,写错一个引号配置静默失效、悄悄退回 pick_first,建议放配置文件加单测校验。〔W13-2 p29-30〕〔W13-2 p5〕
  • 哈希负载均衡和本地缓存是配套设计:多实例下命中没有缓存数据的节点,就要重复加载缓存、内存翻倍;用业务主键做 key 做哈希,保证同一个 key(同一订单、同一用户)必命中同一节点。〔W13-2 p34〕
  • 框架默认值不同:Kratos 默认平滑 WRR,负载均衡封装成 Selector,filter 是分组/路由的统一抽象,指定算法走 selector.SetGlobalSelector(全局设置,不太符合直觉),内置 P2C/Random/WRR;go-zero 默认写死 P2C(随机选两个节点挑负载低的),要换只能传原生 WithDefaultServiceConfig 覆盖。〔W13-2 p21-24〕
  • 补页码引用:W12-1 p2 与 W12-2 p2 是两份单元的一句话总述(三代方案演进、gRPC 接注册中心全流程),逐项机制正文第一到四节均已展开,不另立条目;W13-1 p24 里"动态算法实时估算负载"的主干已并入上面的指标起点条与第五节动态算法段。省略未吸收:W12-1 的面试要点页(p22,问题清单,答案全在正文);W12-2 的作业(p50,换中间件写 demo)与面试要点页(p48);W13-1 的面试要点页(p33)与加权哈希细节(p21,一句话:哈希值替代随机数落权重区间);W13-2 的升职加薪页(p38,给核心业务补 failover、按业务挑算法)与面试要点页(p40)。其余必读条目已全部融入正文或本块。
