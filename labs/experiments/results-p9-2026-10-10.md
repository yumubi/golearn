## E6. worker pool vs goroutine-per-packet（P8 预测的验证）

P8 trace 给出的新断言: goroutine-per-packet 的税是"任务太碎"
（3 秒 48.5 万次上台, 每次只摊 ~13µs 有效功）, 预测固定 worker 池
吃 channel 能把 P50 再降 10-20%。

实现: `DNS_WORKER_POOL=N`（main.go Run 的 pool 分支）:
N 个 worker 吃 `chan packet`(buffered N), 读循环 `qch <-` 满时背压。
N=0 走原 goroutine-per-packet 分支。panic recover 语义两形态一致。

### 消融三轮（N=0/2/4/8/16, 每轮内所有档位同台）

| WORKER_POOL | R1 qps | R2 qps | R3 qps | R1 p50 | R2 p50 | R3 p50 |
|------------|--------|--------|--------|--------|--------|--------|
| 0 (per-packet) | 91.8k | 93.8k | 90.2k | 163µs | 161µs | 159µs |
| 2 | 96.9k | 101.5k | 80.5k | 154µs | 150µs | 177µs |
| 4 | 84.7k | 89.6k | 85.1k | 158µs | 154µs | 155µs |
| 8 | 83.9k | 92.1k | 92.5k | **124µs** | **113µs** | **114µs** |
| 16 | 95.1k | 74.0k | 95.9k | 158µs | 179µs | 157µs |

### 读数

1. **吞吐读数有重叠**：N=0 为 90–94k qps，各 pool 档位为 74–101k；三轮数据不足以证明背压抵消了 spawn 成本，需进一步测量。
2. **P50 改善只在本次 N=8 档稳定出现**：三轮为 113–124µs，N=0 为 159–163µs，约低四分之一。这是本机特定负载的结果，常驻 worker 和调度亲和性只是待验证的解释。
3. **goroutine 存量**: 负载中 QUIT dump, per-packet 69 个
   (≈ 8 常驻 + 每查询 1 个在飞 + runtime), pool 52 个(≈ 常驻 8 + runtime
   + 6 个 semacquire 的 worker)。**在飞 goroutine 从"每包一个"变成 0**：
   这是 trace 上台次数的量级差来源。
4. **N=16 的 P50 在这三轮更高**（157–179µs）。竞争和 channel 开销可能有关，但现有数据未证明具体原因，也不支持按 P 数直接选择池大小。

### Rust 对照

两种程序都可为每个包安排任务，但 runtime、任务模型和实现细节不同；这组 Go 实验不能证明 tokio 调度更轻，也不能推出调度形态只影响延迟、不影响吞吐。

### 方法论事故记录

第一版 pool 分支把 `buf := make(...)` 写在分支后面, pool 分支先用了它
：编译器抓住 undefined。教训: **Go 的声明顺序就是依赖顺序, 分支
提取时变量提升要自己负责**(Rust 同样, 但 borrow checker 会给出
更早的错误位置)。

## 综合结论(P6→P9 四个实验的因果链)

| 断言 | 来源 | 结果 |
|------|------|------|
| 省拷贝能提 qps | P6 LESSON 读数 2 | E4 的本次端到端实验未测出明显变化；不能推广到所有负载 |
| 分配/GC 是 P50 底噪来源 | P6 LESSON 读数 4 | E5 观察到 mark assist，但次数本身不能量化 P50 影响 |
| spawn 税是任务太碎 | P8 trace 推断 | 有调度活动证据；因果和吞吐影响仍需进一步对照 |
| pool 能降 P50 10–20% | P8 预测 | 本次 N=8 三轮 P50 下降约 25%；其他负载需复测 |
| GOMAXPROCS 是伪杠杆 | P8 消融 | 本次参数范围未见稳定影响，不构成普遍结论 |

本机实验的候选配置是 `DNS_HITPATH_POOL=1 DNS_WORKER_POOL=8`，不是通用生产配置：
p50 从 163µs 到 ~118µs(本机 B2 档), qps 持平 90k+。

与 GOMAXPROCS 的关系：worker 数 N=8 是"任务形态"的调参（spawn 税、
每任务时长），不是 CPU 并行度的调参：见 P8 消融（GOMAXPROCS
2-10 无稳定影响）。容器里跑时注意 Go 1.25 起 GOMAXPROCS 默认按
cgroup CPU 限额（`runtime/cgroup_linux.go`），N 与 GOMAXPROCS 独立
生效，两者别混为一谈。

## 复现

```sh
cd /Users/akka/Dev/learning/go
go run ./labs/experiments/hitpath-ab/fakeup -port 15300 &
cd dnsproxi-go
go build -o /tmp/dnsproxi-b .
for wp in 0 2 4 8 16; do
  DNS_LISTEN=:15353 DNS_UPSTREAM=127.0.0.1:15300 DNS_CACHE=1 DNS_CACHE_MAX=2048 \
    DNS_CACHE_SAMPLE_K=8 DNS_CACHE_ADMIT=tinylfu DNS_HITPATH_POOL=1 \
    DNS_WORKER_POOL=$wp /tmp/dnsproxi-b &
  sleep 2
  go run ./dnsq -target 127.0.0.1:15353 -dur 3s -conc 16 -names 100 | grep -E "qps|p50"
  kill %1; sleep 1
done
```
