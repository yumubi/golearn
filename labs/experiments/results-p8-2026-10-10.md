## E4. 命中路径省拷贝 A/B（hitpath-ab/）

P6 LESSON 读数 2 的遗留优化点：命中路径 Go 版比 Rust 版慢 2×，
怀疑是 `Entry.Reply()` 每命中一次的 make+copy 整包堆分配。

A（baseline）: `Reply()` 内部 `make([]byte, len)+copy`（原实现）
B（hitpath）  : `ReplyPool(query, buf)` 写进 sync.Pool 的 4KB buffer，
               WriteTo 完成后 Put 回。单次拷贝（e.Resp→pool buf），零堆分配。

### micro-benchmark（labs/experiments/hitpath-ab，benchtime=1000000x count=5）

| 形态 | ns/op 区间 | B/op | allocs/op |
|------|-----------|------|-----------|
| A: make+copy | 19.0-24.3 | 64 | 1 |
| B: pool buf | 11.7-14.7 | 0 | 0 |

B 在该微基准中约快 1.6×，且测得 0 allocs/op；64B/op 是该基准实际记录值。不能单凭这个数推断其他包长或整个 Rust 实现的分配情况。

### 端到端 A/B（真实代理 + fakeup + dnsq，交错两轮 × 各 3 发 3s）

| 变体 | qps 交错区间 | p50 |
|------|-------------|-----|
| A | 41.7k-53.8k | 244-290µs |
| B | 50.9k-53.5k | 267-280µs |

**结论诚实版：端到端 qps 差异在噪音内（区间几乎重叠），p50 差 ~3-10µs 且不稳定。**

一次可能的解释是，省去的分配与拷贝相对于整个 UDP 往返较小；但这组测量没有直接分解系统调用、GC 和调度各自的耗时，不能据此确认瓶颈或解释语言间差距。

**方法论**：微基准显著不等于端到端显著。估算优化项占比可以决定实验优先级，但实际效果仍需端到端测量。B 形态（`DNS_HITPATH_POOL=1`）未设为默认；是否值得使用取决于真实负载与复测结果。

### Rust 对照再校准

P6 提出的省拷贝优化在这组端到端测试中未显示稳定收益；它是否解释两版 B2 差距仍需控制更多变量，不能直接归因于调度路径。

## E5. GOMAXPROCS 消融 + trace 调度账（hitpath-ab/trace_test.go + QUIT dump）

### GOMAXPROCS 消融（两轮交错，B 形态，keyspace=100）

| GOMAXPROCS | 第一轮 qps | 第二轮 qps | p50 范围 |
|-----------|-----------|-----------|---------|
| 2 | 51.2k | 58.2k | 220-244µs |
| 4 | 53.1k | 42.4k | 263-290µs |
| 8 | 51.4k | 51.5k | 277-279µs |
| 10(全核) | 54.5k | 49.9k | 261-280µs |

**本次结果**：GOMAXPROCS 2–10 的 qps 读数没有显示稳定趋势，轮间波动较大。该结果不能排除调度或系统调用成为瓶颈，也不能证明调整 GOMAXPROCS 对其他 IO 密集服务无效。

适用边界：本表在 macOS 裸机上测（默认 GOMAXPROCS = 物理核）。Go 1.25 起
runtime 在 Linux 容器里默认按 cgroup CPU 限额取 GOMAXPROCS
（`$(go env GOROOT)/src/runtime/cgroup_linux.go`；GODEBUG
containermaxprocs 可关），容器里"默认值"可能显著低于核数，本消融
结论不能直接搬进容器。

### trace 调度账（TestTraceCapture：8 goroutine 轰炸真实 cache 3 秒）

用 `go test -run TestTraceCapture` 采出 23.7MB trace，
`golang.org/x/exp/trace` 解析（文本统计，不依赖 web viewer）：

```
total events: 4,465,045
goroutine →executing（调度上台）: 485,375 次
go→Running 484,993 | →Runnable 484,701 | →Waiting 343,452 | →Syscall 382
proc→Running/→Idle 各 68,422（4 个 P 各自忙闲切换 ~17k 次）
GC: mark phase 4,862 轮区间事件; mark assist 81,178; incremental sweep 1,227,318
```

三个读数：

1. **调度吞吐**：3 秒内 goroutine 上台 48.5 万次 ≈ 16 万次/秒，
   每次"上台→下台"一个来回只干了 ~13µs 的活（cache Get+Reply）：
   goroutine per packet 模型的税就是**任务太碎**：上台下台的固定成本
   摊在 13µs 的活上。
2. **GC mark assist 8.1 万次**：分配方被拉去帮 GC 干活 8 万次：
   这就是 E4 micro-benchmark 里 B 形态零分配的真正收益所在
   （mark assist 是 STW 外的隐形延迟税）。
3. **proc 忙闲各 68,422 次**：4 个 P 在 3 秒里各自 idle/run 切换 1.7 万次
   ：不是 P 不够，是任务不连续。加 P（GOMAXPROCS↑）只增加空转扫描，
   不增加吞吐，与消融实验互证。

### Rust 对照

tokio 的 task 模型在同样"每包一个任务"下也付上台下台税，
但 tokio task 更轻（无栈，尺寸显式）且 spawn 是显式的：
P6 压测 Rust P50 更低的机制现在有了量化方向：**单位任务有效功/调度成本比**。
验证留 E6（如做）：把 handleQuery 改成 worker pool 固定 N 个 goroutine
吃 channel（省 spawn+上台），预测 P50 可再降 10-20%。

## 复现

```sh
cd /Users/akka/Dev/learning/go

# micro A/B
go test -bench . -benchmem -benchtime=1000000x -count=5 ./labs/experiments/hitpath-ab/

# 端到端 A/B（先起 fakeup）
go run ./labs/experiments/hitpath-ab/fakeup -port 15300 &
cd dnsproxi-go
go build -o /tmp/dnsproxi-b .
# A: 不设 DNS_HITPATH_POOL；B: DNS_HITPATH_POOL=1
DNS_LISTEN=:15353 DNS_UPSTREAM=127.0.0.1:15300 DNS_CACHE=1 DNS_CACHE_MAX=2048 \
  DNS_CACHE_SAMPLE_K=8 DNS_CACHE_ADMIT=tinylfu DNS_CACHE_ACTIVE_TTL=1 \
  [DNS_HITPATH_POOL=1] /tmp/dnsproxi-b &
go run ./dnsq -target 127.0.0.1:15353 -dur 3s -conc 16 -names 100

# trace 采集 + 文本统计
go test -run TestTraceCapture -count=1 .    # 产出 /tmp/proxy.trace
# 解析: labs/experiments/traceparse（x/exp/trace Reader, 见 results 记录的脚本）
```
